## Clarifications

### Session 2026-07-22

- Q: 本地数据文件损坏时启动加载失败，应采用何种恢复策略？ → A: 仅重试读取——不创建自动备份，重试只是重新读同一个文件；损坏则提示"数据已损坏，需重新开始"，用户确认后以空数据启动
- Q: V1 预期卡片与类别的规模上限？ → A: ≤500 张卡片 / ≤50 个用户类别，JSON 文件存储可满足，无需引入 SQLite

- 审查修复 (2026-07-22): 交叉审查 PRD + DESIGN + EXPERIENCE → spec，修复阻断 2 项 (B1 S15 缺失, B2 未分类不可选)、重要 4 项 (I1 外部系统返回落点表, I2 搜索播报, I3 修复场景统一, I4 FR-组件映射)、建议 5 项 (S1 加载中禁用, S2 status-bar 计时, S3 排序播报级别, S4 设计基线, S5 UI 不得暗示同步)

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 文件收录与快速打开 (Priority: P1)

怡哥需要把分散在各处的常用文件收录到应用中，并通过卡片快速打开，不再记忆和翻找路径。这是整个产品的核心价值闭环：收录 → 定位 → 打开。

**Why this priority**: 没有卡片就没有导航对象，没有快速打开就失去了产品存在的意义。US1 是 MVP 的最小可交付单元——哪怕没有分类、搜索和修复，用户已经能获得"收录 + 快速打开"的核心价值。

**Independent Test**: 从空应用启动开始，选择一个本地文件，确认卡片名称和首个类别后保存，卡片出现在首页，点击卡片后文件由操作系统默认方式打开。整个流程可独立验证 5 秒/2 次操作的核心指标。

**Acceptance Scenarios**:

1. **Given** 首次启动的空应用，**When** 用户点击"选择文件"并通过系统文件选择器选取一个 HTML 文件（含有效 `<title>`），**Then** 确认模态框显示去除首尾空格后的页面标题作为默认卡片名称，类别列表为空且不预选。

2. **Given** 首次启动的空应用，**When** 用户选择非 HTML 文件，**Then** 默认卡片名称为不含扩展名的文件名。

3. **Given** 确认模态框已打开且无用户类别，**When** 用户在类别复选框中创建第一个类别并保存，**Then** 新类别自动选中。

4. **Given** 用户已确认名称和至少一个类别，**When** 用户点击"保存"，**Then** 卡片立即出现在"全部卡片"和每个所属类别的末尾，应用回到首页且卡片可见。

5. **Given** 系统文件选择器已打开，**When** 用户取消选择，**Then** 不创建任何记录，返回原触发界面（空状态或原类别视图）。

6. **Given** 首页显示了一张卡片，**When** 用户单击卡片主体或按 Enter，**Then** 应用不预判文件状态，直接请求操作系统按默认方式处理源文件。

7. **Given** 源文件存在且有关联默认应用，**When** 用户点击卡片，**Then** 文件由默认应用打开，总操作在 5 秒、2 次核心操作内完成（切换类别或输入搜索词计 1 次，点击卡片计 1 次）。

8. **Given** 源文件存在但没有默认关联应用，**When** 用户点击卡片，**Then** 系统显示"选择打开方式"对话框；用户选择应用后文件打开，或取消后回到原卡片状态不变。

9. **Given** 用户已选择了一个已被收录的源文件，**When** 系统检测到重复，**Then** 显示"该文件已收录"提示，并提供"查看原卡片"入口，不创建第二张卡片。

10. **Given** 用户尝试保存名称为空（去除首尾空格后）或仅含换行的卡片，**When** 提交，**Then** 就地显示校验错误，阻止保存，聚焦名称字段。

11. **Given** 用户尝试保存名称超过 80 个字符的卡片，**When** 提交，**Then** 显示"名称最多 80 个字符"，阻止保存。

12. **Given** 用户尝试保存与已有卡片完全同名的卡片名称，**When** 提交，**Then** 显示名称冲突提示，阻止保存并定位同名卡片。

13. **Given** 用户未选择任何类别，**When** 尝试保存，**Then** 显示"请至少选择一个类别"，阻止保存。

14. **Given** 用户在新增或编辑模态框中已实际修改了名称、备注或类别（与打开时的初始值不同），**When** 用户尝试关闭模态框（点击取消、按 Esc 或点击遮罩），**Then** 显示 S15 确认对话框，提供"继续编辑"和"放弃修改"；选择"继续编辑"回到表单且所有已填数据完整保留，选择"放弃修改"关闭模态框并回到触发前的上下文。无实际修改时直接关闭不弹确认。

15. **Given** 新增或编辑卡片的类别复选列表已展开，且"未分类"当前含至少一张卡片因此在列表中可见，**When** 用户浏览类别选项，**Then** "未分类"以禁用态呈现，不可勾选；用户不能主动将卡片加入"未分类"。

### User Story 2 - 分类管理与卡片排序 (Priority: P2)

随着收录的文件增多，怡哥需要用自建类别组织卡片，并手动调整卡片在各类别中的顺序，保持可找性。同一张卡片可以属于多个类别，在各自类别中有独立的显示顺序。

**Why this priority**: 当卡片超过一定数量（例如 20+），仅靠"全部卡片"网格已不够高效。分类和排序让用户按自己的心智模型组织导航库，是产品从"能用"到"好用"的关键一步。不阻塞 P1 核心闭环。

**Independent Test**: 在已有若干卡片和类别的前提下，创建/重命名/删除类别、将卡片加入多个类别、进入整理模式调整顺序、验证各视图顺序独立——全部可独立测试，不依赖搜索或修复功能。

**Acceptance Scenarios**:

1. **Given** 首页左侧栏，**When** 用户点击"＋"创建类别，**Then** 打开类别编辑浮层，名称字段获得焦点；输入有效名称（单行纯文字 ≤30 字符，非空）保存后类别出现在用户类别区，焦点回到"＋"按钮。

2. **Given** 用户尝试创建名称为"全部卡片"或"未分类"的类别，**When** 提交，**Then** 显示"保留名称，不可使用"，阻止保存。

3. **Given** 用户尝试创建与已有类别完全重名（去除首尾空格后）的类别，**When** 提交，**Then** 显示重复提示，阻止保存。大小写不同的名称可以并存。

4. **Given** 用户在类别更多菜单选择"重命名"，**When** 输入有效新名称并保存，**Then** 类别名称更新，卡片关系和顺序不变。

5. **Given** 用户在某类别更多菜单选择"删除"，**When** 确认对话框出现，**Then** 显示类别名、卡片总数，以及将失去所有用户类别而进入"未分类"的卡片数量。

6. **Given** 删除确认对话框已打开，**When** 用户确认删除，**Then** 类别被移除，其余用户类别卡片保留，失去全部用户类别的卡片进入"未分类"并追加到其末尾。若删除的是当前正在查看的类别，视图切换到"全部卡片"。

7. **Given** 删除确认对话框已打开，**When** 用户取消，**Then** 类别、关系和顺序全部保持不变。

8. **Given** 某类别"未分类"中有卡片，**When** 用户将其中一张卡片加入任一用户类别，**Then** 该卡片自动离开"未分类"。

9. **Given** 用户在某类别视图中点击"整理排序"，**When** 进入整理模式，**Then** 卡片主体不再响应打开操作；用户可用拖动手柄或上移/下移按钮调整卡片顺序，移动结果立即生效，并以礼貌级、不抢焦点方式播报名称、当前位置和总数。

10. **Given** 用户在"全部卡片"中调整了某卡片的位置，**When** 切换到包含该卡片的用户类别视图，**Then** 用户类别中该卡片的位置保持不变（各视图顺序独立）。

11. **Given** 一张卡片只属于当前这一个用户类别，**When** 用户打开该卡片的更多菜单，**Then** "移出当前类别"以禁用态显示并解释"请先加入其他类别"。

12. **Given** 一张卡片属于多个类别，**When** 用户在某个类别中执行"移出当前类别"，**Then** 卡片从当前网格消失，显示"已移出当前类别"状态条，其他类别中的同一张卡片不受影响。

13. **Given** 用户在类别整理模式中，**When** 拖动或按按钮调整用户类别顺序，**Then** "全部卡片"始终固定在顶部，"未分类"（若显示）固定在底部，用户类别在二者之间。

14. **Given** 用户类别为空，**When** 查看该类别，**Then** 显示空状态，提供"选择文件"主行动和"查看全部卡片"次行动。

### User Story 3 - 全局搜索与文件定位 (Priority: P2)

当卡片数量增多时，怡哥需要不切换类别就能按名称搜索任意卡片，以及能在文件管理器中定位源文件。

**Why this priority**: 搜索是切换类别之外的另一种快速定位方式，与 US2 互补；在文件管理器中显示是常用的辅助操作。两者不阻塞 P1 核心闭环，但显著提升大批量卡片场景的效率。

**Independent Test**: 在已有若干卡片的条件下，输入搜索词验证实时筛选和排序规则；对任意卡片执行"在文件管理器中显示"验证系统定位——均可独立测试。

**Acceptance Scenarios**:

1. **Given** 首页已显示卡片，**When** 用户在全局搜索框中输入非空文字，**Then** 主展示区实时切换为搜索结果，显示跨全部卡片名称包含该文字的卡片；同一卡片只出现一次，左侧当前类别不变。

2. **Given** 搜索已有结果，**When** 排序规则生效，**Then** 完整名称匹配优先，其次名称开头匹配，最后其他包含匹配；同一层级内沿用"全部卡片"的手动顺序。

3. **Given** 搜索框非空，**When** 用户清空搜索或按 Esc，**Then** 恢复原类别视图。

4. **Given** 搜索词无任何匹配，**When** 结果显示，**Then** 显示查询词并提供"清空搜索"操作。

5. **Given** 搜索输入首尾含空格或英文大小写不同，**When** 搜索执行，**Then** 忽略首尾空格，英文不区分大小写。备注、路径和类别名称不参与搜索。

6. **Given** 任意卡片，**When** 用户在卡片更多菜单选择"在文件管理器中显示"，**Then** 应用不预判文件状态，直接请求操作系统定位源文件：Windows 在资源管理器中定位，macOS 在 Finder 中定位。

7. **Given** 操作系统无法定位源文件，**When** 定位请求失败，**Then** 显示"无法定位文件。卡片仍被保留。"对话框，提供"重新选择文件"和"删除卡片"。

8. **Given** 搜索结果中，**When** 每张卡片最多显示两个类别标签，**Then** 超出两个的显示"+N"；标签仅用于识别，不可点击。

### User Story 4 - 失败处理与卡片修复 (Priority: P3)

当源文件因外接盘未连接、网络位置不可用、云盘未同步或被移动/删除而无法打开时，怡哥需要明确知道发生了什么，并能修复文件关联而不丢失已有的名称、备注、类别和排序。

**Why this priority**: 失败场景是产品韧性的关键——不能静默失败，不能因修复而丢失用户整理的数据。但它处理的是异常流程，不阻塞正常使用的 P1/P2 功能。

**Independent Test**: 模拟源文件不可访问（如重命名/移动文件），点击卡片验证失败反馈；通过"重新选择文件"修复关联，验证原有元数据保留——均可独立测试。

**Acceptance Scenarios**:

1. **Given** 一张卡片的源文件已被移动或删除，**When** 用户点击该卡片，**Then** 应用不预检查文件状态，直接请求系统打开；系统无法处理时显示"无法打开文件。卡片仍被保留。"对话框，提供"重新选择文件"、"删除卡片"和"关闭"。

2. **Given** 打开失败对话框已显示，**When** 用户关闭对话框，**Then** 卡片数据完整保留，用户可再次点击重试。

3. **Given** 打开失败对话框已显示，**When** 用户选择"重新选择文件"并通过系统文件选择器选取一个新的有效文件，**Then** 卡片关联更新为新文件，原名称、备注、类别关系和各视图顺序全部保留，显示"已重新关联"状态条。不自动重试打开。

4. **Given** 用户正在修复时选择了已被其他卡片收录的文件，**When** 检测到重复，**Then** 显示重复冲突对话框，原卡片继续关联原路径，提供"查看原卡片"、"重新选择"和"取消"。

5. **Given** 打开失败对话框已显示，**When** 用户选择"删除卡片"，**Then** 先进入删除确认，明确"将从所有类别移除，但不会删除、移动或修改源文件"；确认后删除，取消则回到失败对话框。

6. **Given** 系统文件选择器在修复过程中被取消，**When** 取消选择，**Then** 原文件关联和全部卡片数据保持不变，回到触发修复的原界面。

7. **Given** 应用启动时本地数据加载失败，**When** 加载出错，**Then** 显示稳定的应用壳和非技术化阻断反馈："无法加载本地数据"，初始焦点在"重试"（仅重新读取同一数据文件，不执行修复逻辑），另有"关闭应用"。连续重试仍失败后，提示"数据已损坏，需重新开始"，用户确认后以空数据启动（无卡片、无用户类别，等同于首次启动）。

8. **Given** 应用正在加载本地数据，**When** 加载中，**Then** 显示应用壳和"正在加载本地数据"，导航、搜索、工具和卡片区域的所有交互控件不可聚焦或激活。

### Edge Cases

- **空状态首次启动**: 无卡片、无用户类别，只显示"全部卡片"和引导文字"添加常用文件。应用不会扫描磁盘。"
- **HTML `<title>` 异常**: 无法读取 `<title>`、缺少 `<title>`、标题为空或仅含空白 → 回退到不含扩展名的文件名
- **卡片名称为纯空白**: 去除首尾空格后为空 → 阻止保存，提示"名称不能为空"
- **备注边界**: 500 字符上限含换行，纯空白视为未填写，首页展示最多两行摘要超出省略
- **名称唯一性冲突**: 新增和重命名同一规则；大小写不同的名称视为不同名称
- **类别名称冲突**: "全部卡片"和"未分类"为保留名；去除首尾空格后完全相同的类别名称不得重复
- **未分类的显示与隐藏**: 仅当"未分类"自身至少有一张卡片时才在左侧栏底部显示
- **新增卡片后落点**: 当前视图能展示新卡片则保持；否则切到"全部卡片"
- **最小窗口适配**: 约 760×560 时主区降至一列并纵向滚动，侧栏固定不折叠
- **系统安全提示**: 可执行文件/脚本允许收录但不绕过 OS 安全提示；安全提示结束后回原卡片主体
- **模态不堆叠**: 从错误对话框进入删除确认时替换而非叠加；同一时刻只有一个顶层模态
- **窗口缩放**: 不设 UX 最大宽度，大窗口增加卡片列数，小窗口减少至一列
- **数据独立**: 两台设备间无同步/导入/导出/迁移入口或暗示
- **卸载后数据**: V1 不保证卸载后保留数据，也不要求重装后恢复
- **数据文件损坏**: 启动时数据文件不可读或解析失败 → 阻断反馈"无法加载本地数据"，仅提供重试（同文件重读）和关闭应用；不自动备份、不尝试修复损坏数据、不创建恢复副本。用户确认重建后以空数据启动
- **Status-bar 计时与交互**: 非阻断成功反馈至少保持 8 秒，可手动关闭，礼貌级读屏播报且不抢焦点；键盘焦点位于状态条内或指针悬停时暂停自动消失；手动关闭或自动消失后，若焦点位于其中则回到触发该状态的稳定控件或对应卡片且不重复播报
- **累积打开失败**: 同一卡片连续 3 次主打开失败（每次关闭 S16 后再次点击卡片均失败），第 3 次关闭 S16 时 status-bar 提示"文件可能已移动，建议重新关联"。重试计数器随卡片重新关联或应用重启重置
- **系统托盘行为**: 关闭窗口 → 最小化到系统托盘，进程保持运行，数据保持在内存中；右键托盘图标 → 显示"退出"菜单项；点击托盘图标 → 恢复窗口到关闭前的大小、位置和界面状态。冷启动（进程首次启动）→ 窗口显示，进入"全部卡片"

## Requirements *(mandatory)*

### Functional Requirements

**卡片收录与管理**

- **FR-001**: 系统必须允许用户通过系统文件选择器一次选择一个任意类型的源文件
- **FR-002**: 系统必须在用户选择源文件后显示保存前确认步骤，包含可修改的卡片名称和可多选的用户类别
- **FR-002a**: 系统必须在新增或编辑模态框关闭时检测是否有实际修改（名称、备注、类别与打开时的初始值不同）；有修改时显示 S15 确认对话框"继续编辑 / 放弃修改"，无修改时直接关闭；"继续编辑"回到表单保留所有数据，"放弃修改"关闭并回到触发前的上下文
- **FR-003**: 系统必须对 HTML 文件优先采用有效 `<title>`（去除首尾空格后非空）作为默认卡片名称；无法读取或无效时回退到不含扩展名的文件名
- **FR-004**: 系统必须对非 HTML 文件采用不含扩展名的文件名作为默认卡片名称
- **FR-005**: 系统必须确保一个源文件只对应一张卡片；重复选择时提示"该文件已收录"并提供查看原卡片入口
- **FR-006**: 系统必须要求卡片名称为单行纯文字，去除首尾空格后非空、不超过 80 个字符、不与已有卡片名称完全相同
- **FR-007**: 系统必须允许用户通过编辑模态框修改卡片名称、备注、类别和重新选择关联源文件
- **FR-008**: 系统必须在编辑模态框中只读显示完整文件路径，并提供复制路径和在文件管理器中显示操作
- **FR-009**: 系统必须在以下三种场景中支持通过系统文件选择器重新关联源文件，且均保留原名称、备注、类别关系和各视图顺序：(a) 卡片编辑界面（S11）主动更换，(b) 打开失败对话框（S16）修复，(c) 定位失败对话框（S17）修复。新文件已被其他卡片收录时阻止更换/修复并进入 S18

**删除**

- **FR-010**: 系统必须允许用户全局删除卡片；删除前确认"将从所有类别移除，但不会删除、移动或修改源文件"
- **FR-011**: 系统必须在确认删除卡片后移除其全部类别关系和视图顺序，不修改源文件

**类别管理**

- **FR-012**: 系统必须允许用户创建、重命名、删除和手动排序用户自建类别
- **FR-013**: 系统必须要求类别名称为单行纯文字，去除首尾空格后非空、不超过 30 个字符
- **FR-014**: 系统必须保留"全部卡片"和"未分类"作为不可用于用户类别名称的保留名称
- **FR-015**: 系统必须允许一张卡片同时属于一个或多个用户类别，并在每个类别中独立展示；类别复选列表中"未分类"始终以禁用态呈现，不可勾选
- **FR-016**: 系统必须在新增或编辑时要求卡片至少保留一个用户类别；"移出当前类别"仅当卡片属于多个类别时可用
- **FR-017**: 系统必须在删除类别前确认，显示卡片总数和将进入"未分类"的数量；删除后失去全部用户类别的卡片进入"未分类"并追加到末尾
- **FR-018**: 系统必须仅在"未分类"自身至少有一张卡片时显示该系统恢复类别，固定在类别导航底部；卡片加入任一用户类别后自动离开

**视图与排序**

- **FR-019**: 系统必须由固定左侧栏（"全部卡片"顶部、用户类别中段、"未分类"底部）和右侧主展示区组成单窗口界面；关闭窗口时最小化到系统托盘而非退出进程，点击托盘图标恢复窗口
- **FR-020**: 系统必须在每次应用冷启动（进程启动后的首次窗口展示）时进入"全部卡片"，不恢复上次类别；从系统托盘恢复窗口时保持关闭前的界面状态
- **FR-021**: 系统必须为"全部卡片"、每个用户类别和"未分类"分别保存独立的卡片手动顺序
- **FR-022**: 系统必须在整理排序模式中禁止卡片主打开；移动结果立即生效；新卡片追加到各所属视图末尾

**搜索**

- **FR-023**: 系统必须提供常驻全局搜索，按卡片展示名称跨全部卡片实时匹配
- **FR-023a**: 系统必须在全局搜索中采用礼貌级 ARIA live region；短暂输入停顿后仅播报最新查询的结果数，不播报每张卡片内容；无结果时播报一次"无匹配结果"；清空搜索或 Esc 返回原类别时各播报一次上下文变化；实时搜索结果更新采用可取消、可合并的播报策略
- **FR-024**: 系统必须采用包含匹配，排序为完整名称匹配优先、名称开头匹配次之、其他包含匹配最后，同层级沿用"全部卡片"顺序
- **FR-025**: 系统必须在搜索时忽略首尾空格、英文不区分大小写；备注、路径和类别名称不参与搜索

**打开与定位**

- **FR-026**: 系统必须在用户点击卡片主体时直接请求操作系统按默认方式处理源文件，不预判文件状态
- **FR-027**: 系统必须在文件无默认关联应用时调用操作系统的"选择打开方式"
- **FR-028**: 系统必须为每张卡片提供"在文件管理器中显示"操作：Windows 用资源管理器，macOS 用 Finder

**失败处理**

- **FR-029**: 系统必须在操作系统无法处理打开请求时显示明确失败反馈，提供"重新选择文件"、"删除卡片"和"关闭"
- **FR-030**: 系统必须在操作系统无法定位文件时显示明确失败反馈，提供"重新选择文件"、"删除卡片"和"关闭"
- **FR-031**: 系统必须在重新关联文件成功时保留名称、备注、类别关系和各视图顺序，显示成功反馈，不自动打开或定位

**备注**

- **FR-032**: 系统必须允许每张卡片保存一段可选纯文字备注，最多 500 个字符（换行计入）
- **FR-033**: 系统必须在首页卡片名称下方展示最多两行备注摘要，超出省略；无备注不保留占位

**跨平台与持久化**

- **FR-034**: 系统必须提供 Windows 和 macOS 版本，两端能力与业务规则一致
- **FR-035**: 系统必须在两端独立维护本地数据，不提供迁移、同步、导入或导出功能；界面不得以任何形式（图标、文案、菜单项、空状态占位等）暗示用户存在同步、迁移、导入、导出或共享能力
- **FR-036**: 系统必须在正常关闭、重启和正常升级后保留全部应用数据
- **FR-036a**: 系统必须在启动时数据文件不可读或解析失败时，仅提供重试读取（同文件）和关闭应用选项；不自动备份、不尝试修复损坏数据；用户确认重建后以空数据启动
- **FR-036b**: 系统必须提供系统托盘图标；关闭窗口时最小化到托盘并保持进程运行；右键托盘图标提供"退出"菜单项；通过"退出"或进程终止信号退出时保存全部数据后退出

**无障碍**

- **FR-037**: 系统必须支持全部功能通过键盘（Tab、方向键、Enter、Space、Esc）完成，不依赖全局快捷键
- **FR-038**: 系统必须为错误、成功、警告、禁用和选中状态同时提供非颜色信号
- **FR-039**: 系统必须为每张卡片主体和更多按钮提供独立可访问名称
- **FR-040**: 系统必须在 200% 文本缩放或等效条件下无文字裁切、控件遮挡或功能丢失

### Key Entities

- **卡片 (Card)**: 指向一个源文件的唯一导航对象。属性：展示名称（≤80 字符）、纯文字备注（≤500 字符）、源文件关联（平台特有路径/标识符）、类别关系列表、在各视图中的独立顺序位置。
- **用户类别 (User Category)**: 用户创建的一级分类。属性：名称（≤30 字符）、手动排序位置、包含的卡片列表。删除只影响类别和关系，不删除卡片或源文件。
- **全部卡片 (All Cards)**: 系统视图，不可删除/重命名，汇总全部卡片且同一卡片只出现一次，固定在类别导航顶部。
- **未分类 (Uncategorized)**: 系统恢复类别，仅在含至少一张卡片时显示于类别导航底部，不可主动加入/重命名/删除。卡片加入任一用户类别后自动离开。
- **源文件关联 (File Reference)**: 卡片与操作系统可访问文件的关联。属性：平台特有路径或标识符、唯一性判定标识。重新关联时替换，其他卡片属性不变。
- **视图顺序 (View Order)**: 卡片在特定视图（全部卡片/用户类别/未分类）中的独立手动排序位置。新增卡片追加到末尾；调整一个视图不影响其他视图。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 在应用已启动、目标卡片已收录、源文件有效且已配置默认处理方式的前提下，用户从开始查找动作到文件成功交给操作系统，不超过 5 秒、不超过 2 次核心操作（切换类别或输入完整搜索词计 1 次，点击卡片计 1 次）。
- **SC-002**: 主打开动作的每一次执行，用户均得到明确结果——"成功交给系统处理"或"明确失败反馈及可执行后续动作"——静默失败率为 0%。
- **SC-003**: 应用在任何操作（新增、编辑、删除、排序、修复、重关联）中均不删除、移动、重命名或修改用户源文件，违规次数为 0。
- **SC-004**: 正常关闭、系统重启和应用正常升级后，所有卡片名称、备注、类别关系、视图顺序和文件关联完整保留并可用。
- **SC-005**: 全部 4 条用户旅程（首次收录、日常打开、整理排序、修复失败）在 Windows 和 macOS 上的功能和业务规则验收结果一致。
- **SC-006**: 全部功能可通过键盘独立完成，无需鼠标或触控；焦点状态在任何时候可由视觉外环明确识别。
- **SC-007**: 常规设计基线为 1024×720（主区约三列卡片网格）；在 200% 文本缩放和约 760×560 最小窗口条件下，主区降至一列并纵向滚动，UJ-1 至 UJ-4 全部旅程无文字裁切、控件遮挡或功能丢失。窗口放大时不设 UX 最大宽度，按可用宽度增加卡片列数。

## Assumptions

- 用户具有基本的桌面应用操作经验（使用文件选择器、理解类别概念）
- 目标设备运行 Windows 10+ 或 macOS 12+，具备系统文件选择器、默认应用关联和资源管理器/Finder
- 用户的数据目录（外接磁盘、网络位置、云盘同步目录）可能暂时不可用——应用不主动检测，只在操作实际失败时反馈
- V1 设计承载规模为 ≤500 张卡片、≤50 个用户类别；超出此规模不保证性能，但不设硬性阻断上限
- 桌面框架（Electron/Tauri）、数据存储格式（JSON/SQLite）、文件唯一性算法在 plan 阶段收敛
- 应用自身 UI 仅简体中文，不计划国际化
- 单用户、单设备使用场景，无多用户、权限或协作需求
- 用户理解应用不备份源文件，卸载可能导致导航数据丢失
