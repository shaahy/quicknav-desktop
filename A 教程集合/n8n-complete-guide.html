把重复工作
变成可观察的流水线

一份面向 OPC 与技术型业务操作者的 n8n 中文工程手册：先判断值不值得自动化，再从数据流、节点与表达式一路做到可恢复、可维护的生产工作流。

阅读路线 A · 新手按 01 → 07 顺序，完成所有实验。
阅读路线 B · 已上手直接查节点、错误处理和部署章节。
页面能力全文搜索、复制代码、深浅主题、打印 PDF；全部离线运行。
版本提示：本教程按 n8n 2.x 时代的官方文档与主仓库整理。n8n 更新频繁，节点参数和界面文字可能变化；生产升级前务必阅读对应版本 Release Notes。页面不加载任何在线依赖，文末链接仅用于主动查证。
01 / DECISION

先判断：n8n 是不是正确工具

n8n 最擅长的不是“替人点鼠标”，而是把有 API、Webhook、数据库或结构化文件的系统串成一条可观察的数据流水线。它处在 SaaS 集成平台与手写后端代码之间。

很适合

  • 多个系统之间同步、清洗和路由数据
  • 定时汇总日报、对账、线索分发
  • Webhook 驱动的事件处理
  • AI 模型调用前后的检索、加工与审核
  • 需要自托管、控制数据位置的自动化
  • 原型验证后仍需保留可视化运维入口

谨慎或不适合

  • 毫秒级实时、高吞吐核心交易链路
  • 复杂长事务且要求强一致回滚
  • 只能靠脆弱网页点击、没有稳定接口
  • 大量 CPU/内存密集型计算或媒体渲染
  • 逻辑规模已像大型软件系统，却没有工程治理
  • 把 n8n 白标后直接向客户收费——需先核对许可

OPC 场景地图

场景典型流程价值风险点
内容生产选题库 → 素材抓取 → 草稿 → 人审 → 分发高频、跨工具事实核验与平台规则
销售线索表单 → 去重 → 评分 → CRM → 跟进提醒响应速度隐私、重复触达
客户交付订单 → 建项目 → 建目录 → 通知 → 归档减少漏项幂等与权限
经营分析多源取数 → 统一口径 → 汇总 → 报告固定节奏数据延迟与口径漂移
运维监控定时检查 → 阈值判断 → 告警 → 升级可观测告警风暴
自动化优先级 = 频率 × 单次耗时 × 标准化程度 × 错误成本 ÷ 维护成本

经验法则：每月只做一次、规则还在快速变化的工作，先写清 SOP；稳定重复后再自动化。

02 / MENTAL MODEL

工作流到底在运行什么

一个工作流是节点与连接组成的有向图。触发节点创建一次 execution（执行）；数据以一个或多个 item（条目）向后流动。每个 item 通常包含 json，也可包含 binary。

TRIGGER何时开始
→
INPUT ITEMS接收数据
→
LOGIC转换与分支
→
SIDE EFFECT写入或通知

Workflow

定义“怎么做”。n8n 2.x 保存并发布（Publish）后由生产触发器驱动，也可手动测试。

Execution

一次具体运行，包含状态、开始时间、每个节点的输入输出与错误。

Item

最小数据单位。多数节点会对输入 items 逐条或批量处理。

// 一个节点收到的 2 个 items（概念示意）
[
  { "json": { "leadId": "L-1001", "email": "a@example.com", "score": 82 } },
  { "json": { "leadId": "L-1002", "email": "b@example.com", "score": 46 } }
]
最重要的调试动作：每添加一个节点就执行到此处，打开 OUTPUT 面板确认“条目数量、字段名、字段类型”都符合预期，再继续连接下一个节点。
Item linking：n8n 会记录输出 item 来自哪个输入 item，让后续节点能引用更早节点的对应数据。Code 节点若自行新增、合并或重排 items，复杂场景需正确设置 pairedItem，否则会出现无法确定配对数据的映射错误。
03 / BOOT

15 分钟启动本地 n8n

学习阶段可用 npx 或 Docker。Docker 更接近后续部署方式，且通过 volume 保存工作流、凭据和设置。

方案 A：Docker（推荐学习路径）

docker volume create n8n_data
docker run -it --rm --name n8n \
  -p 5678:5678 \
  -v n8n_data:/home/node/.n8n \
  docker.n8n.io/n8nio/n8n

PowerShell 可把反斜杠续行改为一整行，或使用反引号。启动后访问 http://localhost:5678，按界面创建 owner 账号。

方案 B：npx（快速体验）

npx n8n
不要把裸露的 5678 端口直接暴露到公网。公开部署需要 HTTPS、反向代理、强认证、正确的 Webhook URL 和备份。生产方案见第 09 章。

第一次进入后认识 5 个区域

Canvas

拖放节点、连线与查看分支。

Node panel

配置参数、凭据、输入输出。

Executions

查历史运行、错误与每步数据。

Credentials

集中保管系统连接信息，避免硬编码。

04 / BUILD METHOD

把 SOP 翻译成工作流

先写契约

写清触发条件、输入样例、成功输出、失败动作与数据负责人。没有样例数据就先别画节点。

按四段式切开

触发 → 获取/校验 → 决策/转换 → 副作用。把通知、写库、发邮件等不可逆动作放在末端。

用真实样例逐段测试

成功、空值、重复、超时、权限失败各准备一条样例；需要时固定（pin）测试数据，但上线前确认不会误用。

添加防护栏

去重键、批次大小、重试上限、超时、错误出口、告警和人工复核点。

再发布

先用测试 Webhook 与手动执行，确认副作用目标是沙箱；发布前清掉调试地址和临时凭据。n8n 2.x 使用 Publish/Unpublish 模型。

05 / DATA

数据映射与表达式

参数可用固定值，也可切换为 Expression。表达式用双花括号求值；最常用入口是当前 item 的 $json。

目的表达式示例
当前字段{{ $json.email }}
嵌套字段{{ $json.customer?.company ?? '个人' }}
拼接文本{{ 'LEAD-' + $json.id }}
转为数字{{ Number($json.amount) }}
读取指定节点{{ $('Normalize lead').item.json.email }}
当前时间{{ $now.toISO() }}
环境变量{{ $env.MY_VARIABLE }}（可用性受实例配置限制）
表达式陷阱：字符串 "0"、数字 0、布尔值 false 和空值不是一回事。进入 IF/Switch 前，先在 Edit Fields 或 Code 节点统一类型。

Code 节点：只放真正需要代码的转换

// Run Once for All Items
return items.map(item => {
  const email = String(item.json.email ?? '').trim().toLowerCase();
  const amount = Number(item.json.amount ?? 0);
  return {
    json: {
      ...item.json,
      email,
      amount,
      isQualified: email.includes('@') && amount >= 1000
    }
  };
});

优先使用 Edit Fields、IF、Switch 等声明式节点；Code 用于复杂转换。越多代码，越需要测试、评审和版本控制。

Error TriggerStop And Error

HTTP Request 的生产级检查

  • 认证放 Credentials，不写死在 URL、Header 或代码
  • 设置合理 timeout；只对可安全重试的请求启用重试
  • 处理 429 的 Retry-After 和 API 限速
  • 分页时设置明确终止条件，并限制最大页数
  • 记录业务 ID、状态码和响应摘要，不把密钥写入日志
07 / LABS

五个递进实战

01

第一条数据流水线

Manual Trigger → Edit Fields → Code → IF

目标

构造订单样例、计算含税金额，并分成高价值与普通订单。

  1. 新建工作流，加入 Manual Trigger。
  2. 加入 Edit Fields，创建 orderId=O-1001、amount=1200、taxRate=0.06。
  3. 加入 Code，选择 Run Once for Each Item，返回以下对象。
const amount = Number($json.amount);
const total = Math.round(amount * (1 + Number($json.taxRate)) * 100) / 100;
return { json: { ...$json, total, processedAt: new Date().toISOString() } };

连接 IF：条件 {{ $json.total }} 大于等于 1000。执行后确认 true 分支有 1 item。

通过标准：字段类型是 Number；total 为 1272；节点名称已改成业务动作，而不是默认编号。
02

Webhook 线索接入与校验

Webhook → Normalize → IF → Respond to Webhook

创建 POST Webhook，Path 设为 lead-intake。开发时先点击 Listen for test event，再用本机终端发送：

curl -X POST "http://localhost:5678/webhook-test/lead-intake" \
  -H "Content-Type: application/json" \
  -d "{\"email\":\" YIGE@example.com \",\"source\":\"landing-page\",\"budget\":5000}"

注意测试 URL 通常含 /webhook-test/，工作流发布后生产 URL 使用 /webhook/。用 Edit Fields/Code 统一 email、budget 类型；IF 校验 email 非空且含 @。成功返回 202 与业务 ID，失败返回 400 和可读错误。官方 Webhook 默认最大 payload 为 16 MB，自托管虽可调整，入口仍应主动限制大小。

安全升级：公网 Webhook 应验证签名或共享密钥、限制 body 大小、校验 Content-Type，并对重复事件使用上游 event ID 做幂等。
03

定时批处理与限流

Schedule → Fetch → Loop Over Items → Write → Summary
  1. Schedule Trigger 每工作日 09:00 运行，确认实例时区。
  2. 从表格、数据库或 API 获取待处理记录；测试阶段限制 10 条。
  3. Loop Over Items 设置批次大小，例如 20；循环内执行写入或 API 请求。
  4. 在写入前生成稳定幂等键，如 source + ':' + recordId。
  5. 结束出口汇总成功、跳过和失败数量，再发送一条摘要。

不要为了“逐条处理”无条件加 Loop；很多节点本身就会处理所有输入 items。Loop 主要用于批次控制、限速或明确的分页迭代。

04

集中错误工作流

Error Trigger → Redact → Notify → Persist incident
  1. 新建 [Ops] Workflow error handler | PROD。
  2. 以 Error Trigger 开始，提取工作流名、执行 ID、节点名、错误消息和执行链接。
  3. 先删除 token、authorization、password 等敏感字段。
  4. 通知到你的告警渠道，并写入事件表。
  5. 在业务工作流 Settings 中把该工作流设为 Error workflow。
告警必须可行动：包含“哪里失败、影响什么、是否会自动重试、谁负责、从哪里重跑”，而不只是“出错了”。注意 Error Trigger 只响应自动执行失败；手动执行失败不会触发它，错误工作流本身无需发布。
05

把规范化逻辑封装成子工作流

Execute Workflow Trigger → Validate → Normalize → Return

把多个流程共用的“线索规范化”抽出：定义输入字段 email/source/budget，输出固定 schema，并用 Stop And Error 拒绝缺失 email 的输入。父流程通过 Execute Sub-workflow 调用。

契约内容
输入email:string, source:string?, budget:number?
输出emailNormalized, sourceNormalized, budget, qualified
失败VALIDATION_EMAIL_MISSING / VALIDATION_BUDGET_INVALID

子工作流不是“让画布更漂亮”，而是稳定边界：调用方只依赖输入输出，不依赖内部节点。

08 / RELIABILITY

从“能跑”到“值得托付”

风险设计手段验证方式
重复触发事件 ID / 业务主键做幂等；写入使用 upsert同一 payload 连发两次，只产生一个结果
临时故障超时 + 有上限的指数退避；尊重 429模拟一次 500 后恢复
永久故障明确失败、进入死信/待处理队列、告警错误凭据不会无限重试
部分成功逐项记录状态；副作用拆分；提供补偿动作第 6/10 项失败后可只补跑失败项
数据漂移入口 schema 校验、默认值、版本字段缺字段与类型变化能被识别
误操作预览模式、审批门、沙箱凭据、最小权限测试执行不会触达真实客户

重试前先问：这个动作安全吗？

GET 通常可安全重试；创建订单、扣款、发消息未必。对有副作用的 POST，优先使用服务提供的幂等键；否则先查询状态或在自己的状态表中登记。

业务日志

executionId、workflowVersion、businessKey、输入摘要、结果状态、耗时。避免保存明文密钥和不必要的个人信息。

运营指标

成功率、P95 耗时、积压量、重试率、人工接管量、每次执行成本。

09 / DEPLOY

自托管：从单机到生产

单机 Docker Compose 基线

services:
  n8n:
    image: docker.n8n.io/n8nio/n8n:2.30.5
    restart: unless-stopped
    ports:
      - "127.0.0.1:5678:5678"
    environment:
      - TZ=Asia/Shanghai
      - GENERIC_TIMEZONE=Asia/Shanghai
      - N8N_ENFORCE_SETTINGS_FILE_PERMISSIONS=true
      - N8N_ENCRYPTION_KEY=${N8N_ENCRYPTION_KEY}
      - N8N_HOST=automation.example.com
      - N8N_PROTOCOL=https
      - WEBHOOK_URL=https://automation.example.com/
      - N8N_PROXY_HOPS=1
    volumes:
      - n8n_data:/home/node/.n8n

volumes:
  n8n_data:

示例固定为制作日查得的 2.30.5；部署时应换成你已验证的具体版本号，不使用浮动的 latest 或 next。把固定、随机且足够长的 N8N_ENCRYPTION_KEY 放入服务器秘密管理或受权限保护的 .env，不要提交仓库。N8N_PROXY_HOPS 必须与真实反向代理层数匹配。

团队规模、执行量和可用性要求上升后，再评估 Postgres、queue mode、Redis 与 worker。队列模式把执行交给 worker，适合水平扩展，但增加组件、监控与恢复复杂度；不要为未来的假想规模过早引入。

必须备份

  • 数据库或 .n8n 持久卷
  • 加密密钥（与数据分开保管）
  • 工作流导出与外部配置
  • 凭据依赖清单及恢复文档

必须演练

  • 在隔离环境恢复
  • 重新连接 Webhook 与反向代理
  • 验证凭据可以解密
  • 抽样运行关键工作流
只“有备份文件”不等于可恢复。丢失原来的 encryption key，备份中的凭据可能无法解密；恢复演练才是验证。

执行历史与容量

默认清理旧执行，但数据库仍可能快速增长。按审计需要配置成功/失败/手动执行的保存策略；官方默认年龄阈值为 336 小时（14 天），数量阈值为 10,000，实际值以部署版本配置为准。关键业务证据不要只依赖 n8n 的 Executions 页面。

# CLI 备份示例：先在隔离路径验证输出
n8n export:entities --outputDir=/backup/entities
n8n export:workflow --backup --output=/backup/workflows
n8n export:credentials --backup --output=/backup/credentials

不要随意使用 --decrypted：它会导出明文凭据。导入前还要检查 ID 冲突，避免覆盖现有实体。

什么时候进入 Queue mode

组件职责关键约束
Main编辑器、触发与创建执行与所有进程共享 encryption key
Redis保存待执行 ID不是业务数据的最终存储
Worker从数据库读取并执行工作流官方默认并发 10；结合数据库连接池调节
Postgres工作流、凭据和执行状态Queue mode 推荐 Postgres 13+，不推荐 SQLite
Webhook processor可选的入口水平扩展生产 Webhook 可分流，测试 Webhook 留在 main

Queue mode 不支持 filesystem 二进制存储；需要持久化二进制时按当前版本选择数据库或受支持的外部存储。多 main 高可用和某些外部存储能力属于 Enterprise 功能。

10 / GOVERNANCE

安全、隐私与许可边界

  • 凭据使用专用 Credentials；工作流 JSON、代码和日志中不出现密钥
  • 每个系统创建自动化专用账号，并按读写范围最小授权
  • 公网入口启用 HTTPS、鉴权/签名、限流、输入校验和 body 大小限制
  • 限制可安装的 community nodes；安装前审查来源、权限和维护状态
  • 用 NODES_EXCLUDE 阻止不需要的高风险节点，例如命令执行与本地文件读写
  • 定期运行 n8n audit 检查凭据、数据库、文件系统、节点和实例风险
  • 按数据分类设置执行数据保留时间，减少不必要的个人信息
  • 生产与测试使用不同实例或至少不同凭据、目标和标识
  • 定期升级 n8n 与镜像；先在预生产回放代表性工作流

“源码可见”不等于 OSI 开源

n8n 主仓库采用 Sustainable Use License 与 Enterprise License。内部业务使用、个人/非商业使用通常在许可范围内；把 n8n 白标收费、托管后向客户收费，或产品价值主要来自 n8n 功能时可能需要商业协议。官方 FAQ 还特别区分终端用户提交自己的第三方凭据与使用服务方公司凭据的产品后端场景。具体项目应阅读当前许可并向 n8n 确认，本教程不构成法律意见。

11 / DEBUG

故障排查顺序

从输入向输出逐节点查，不要一上来重启所有组件。

确认测试/生产 URL 是否混用；测试监听是否仍在等待；生产工作流是否已发布；反向代理是否转发路径和协议；上游能否访问公网域名；签名/认证是否通过。检查 executions 中是否已有失败记录。
依次检查实例时区、工作流时区、容器 TZ/GENERIC_TIMEZONE 与夏令时。用一次临近时间的小测试验证，不要只靠心算。
看输出 item 数量是否为 0；IF/Switch 是否走了另一分支；字段路径和大小写是否正确；Merge 模式是否要求两边都有匹配数据。固定上游样例逐段执行。
编辑器预览所用 item 可能与实际配对不同。确认当前 item、目标节点是否在同一执行路径、是否有多 items，以及字段是否只在部分分支存在。使用可选链和明确默认值，但别用默认值掩盖必填数据缺失。
固定镜像版本；阅读从当前版到目标版的 breaking changes；备份；在预生产导入并回放成功、空值、失败三类样例；确认节点版本和凭据兼容后再切换。
先定位慢节点和外部 API；观察 item 数、批次、响应体大小和重试；减少大 binary 在内存中传递；优化数据库查询。只有确认瓶颈是执行并发后，再考虑 queue mode/worker 扩容。
