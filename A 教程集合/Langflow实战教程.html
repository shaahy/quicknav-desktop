01

它解决的核心问题

AI 应用的难点通常不是一次模型调用，而是多环节如何稳定协作。

一句话：Langflow 把模型、提示词、Agent、工具、数据处理和向量检索变成带类型的可连接组件，让你更快地组合、观察、调试并通过 API 发布 AI 工作流。

组合成本高

用 Flow 直接看到数据从哪里来、经过什么组件、最后到哪里去。

调试像黑盒

逐组件 Run、查看状态与输出，再进入 Playground 做端到端验证。

原型难交付

验证通过后，可从 Publish/Share 获取 API 调用方式，让前端或业务系统接入。

边界：Langflow 是可视化开发与运行平台，不会替你完成需求判断、数据治理、权限设计和生产运维；复杂逻辑仍可能需要自定义组件或代码。
02

什么时候适合用

判断标准：你是否需要快速验证“多个 AI 能力如何连接”。

✓ 适合

  • RAG 知识库问答、文档检索与总结
  • 带工具调用的 Agent 和多步骤自动化
  • 提示词、模型、检索策略的快速对比
  • 把已验证 Flow 暴露为 API 或嵌入现有系统
  • 团队演示、教学和流程沟通

△ 不应直接当作

  • 零设计即可上线的生产系统
  • 强事务、高并发核心业务的唯一后端
  • 数据权限、审计与安全治理的替代品
  • 完全不需要代码的承诺
  • 模型效果与数据质量的自动保证
03

标准工作流

从“能跑”到“可用”，每一步都有明确出口。

1

安装与启动 环境

可选 Desktop、Docker 或 Python。初学者优先 Desktop；团队环境优先容器化。只使用与 1.11.x 对应的正式文档。

2

先写输入与输出 设计

例：输入“用户问题 + FAQ 文档”，输出“只依据文档的答案 + 无答案时明确拒答”。

3

搭建 Flow 构建

从组件面板拖入节点，按照数据类型连接。复杂任务拆成摄取、检索/生成等独立 Flow。

4

Run 与 Inspect 单测

逐个组件运行，先确认文件被读取、切片合理、检索命中，再检查模型回答。

5

Playground 联调

用正常问题、边界问题和无答案问题测试端到端行为，记录预期与实际。

6

Publish / API access 交付

入门优先稳定的 v1 /api/v1/run/{flow_id}；v2 Workflow API 在当前文档中仍为 Beta。

7

部署与观测 生产

配置认证、密钥、反向代理、HTTPS、日志与资源限制；升级前备份 Flow 并做回归。

06

实战：本地 FAQ 问答

目标：只根据给定资料回答；资料没有写，就明确说不知道。

A摄取 Flow（先运行一次）
Read File→ Split Text→ Embedding Model→ Vector Store / Ingest
→
B问答 Flow（每次提问运行）
Chat Input→ Vector Store / Search→ Parser→ Prompt→ LLM→ Chat Output
为什么拆成两个 Flow？ 文档切片和向量写入不应在每次提问时重复执行。拆开后更容易检查、复用和控制成本。
01

准备最小测试资料

复制下面内容保存为 faq-demo.txt。先用极小、答案确定的数据验证链路。

faq-demo.txt
退款规则：商品未拆封且不影响二次销售，可在签收后 7 天内申请退款。
客服时间：工作日 09:00—18:00，法定节假日除外。
发票规则：订单完成后，可在订单详情页申请电子发票。
02

搭建摄取 Flow

  1. 新建空白 Flow，添加 Read File、Split Text、Embedding Model 和一个可用的 Vector Store。
  2. 读取 faq-demo.txt；切片可先设 chunk size 500、overlap 50。
  3. Vector Store 的集合名设为 faq_demo；如使用本地持久化存储，同时记下目录。
  4. 逐节点 Run/Inspect，确认产生 3 条左右的有效内容，再执行写入。

模型与向量库可按你的环境替换；关键是问答 Flow 使用相同 Embedding 配置、集合名和持久化位置。

03

搭建问答 Flow

用 Chat Input 的问题触发向量检索，把命中 Data 经 Parser 合并为 context，同时把原问题作为 question 传给 Prompt。

Prompt 模板
你是 FAQ 助手。只根据“资料”回答，不补充资料外的事实。
如果资料中没有答案，回复：“现有资料无法回答这个问题。”

资料：
{context}

问题：
{question}

05

发布并调用稳定的 v1 Run API

从 Publish / API access 复制你当前 Flow 的实际端点和请求体。下面只展示结构，切勿把真实密钥写入教程或 Flow 导出文件。

PowerShell
$headers = @{
  "x-api-key" = $env:LANGFLOW_API_KEY
  "Content-Type" = "application/json"
}
$body = @{
  input_value = "未拆封商品几天内可退？"
  input_type  = "chat"
  output_type = "chat"
} | ConvertTo-Json

Invoke-RestMethod `
  -Uri "http://127.0.0.1:7860/api/v1/run/<FLOW_ID>" `
  -Method Post -Headers $headers -Body $body

Codex 桌面端实战

把 Codex 当作可读取工程证据的协作者，而不是替你盲点鼠标的自动化脚本。

1. 先做结构审查

导出两个 Flow JSON，拖入 Codex 任务或告诉它绝对路径。

可复制提示词
检查这两个 Langflow 1.11.x Flow JSON。
目标：FAQ RAG，摄取与问答分离。
先只读审查，不修改文件。
请列出：组件链、关键配置、连接类型不匹配、重复摄取风险、密钥泄露风险。

2. 用日志定位红叉

把节点错误全文、发生步骤和相关 Flow JSON 一起给 Codex。

可复制提示词
使用 $diagnosing-bugs。
现象：Vector Store 查询节点运行失败。
附件：Flow JSON 与完整错误日志。
先建立证据链，区分凭据、维度、集合名、依赖和数据为空；给出最小验证命令，不要直接改配置。

3. 生成最小 API 验证

让 Codex 根据 Publish 面板复制出的真实结构生成测试脚本。

可复制提示词
根据我粘贴的 Langflow v1 API 示例，生成 PowerShell 测试脚本。
密钥只从 $env:LANGFLOW_API_KEY 读取。
覆盖：正常问题、资料外问题、HTTP 非 200、超时；输出简洁测试报告。

4. 完成前验收

把成功标准写死，防止“能返回文本”被误判为完成。

可复制提示词
完成前验证以下标准：
1. 摄取只执行一次且集合有数据；
2. 三个基准问题输出符合预期；
3. 资料外问题明确拒答；
4. v1 API 可调用且错误可读；
5. Flow JSON、日志、脚本不含明文密钥。
逐项给出证据，未验证项不要标记通过。
08

常见错误与上线检查

先判断故障在哪一层，再改参数。

文件已上传，但检索不到内容
依次 Inspect：文件正文是否为空 → Split Text 是否产生 Data → 向量写入是否成功 → 查询 Flow 是否使用同一集合、持久化位置和兼容的 Embedding 模型。
模型回答很流畅，但经常编造
先检查检索结果，再检查 Prompt。降低随机性；加入“仅依据 context、无答案明确拒答”；使用资料外问题做负向测试。不要只改模型。
导入 Flow 后出现缺失组件或参数
通常与版本、提供商依赖或自定义组件有关。确认导出和导入环境版本，查看组件安装状态；不要把 1.12 的 /next 文档配置照搬到 1.11.x。
API 返回 401、404 或请求体错误
401 查 API key 与认证头；404 查 Flow ID 和端点；请求体错误则以当前 Publish / API access 生成的示例为准，确认 input/output type。
能否把 7860 端口直接暴露到公网？
不建议。生产环境至少关闭自动登录、设置非默认 secret、启用认证，并通过反向代理和 HTTPS 暴露；同时限制网络、资源与日志中的敏感信息。
版本与正式文档线一致
密钥使用 Secret / 环境变量
Flow 导出不含明文凭据
正常、边界、无答案均测试
API 有认证、超时和错误处理
升级前备份并回归
