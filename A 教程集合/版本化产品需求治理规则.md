# 版本化产品需求治理规则

## 核心原则

- **当前全量 Spec**：记录最新已批准目标版本的全部有效需求，是产品行为的首选权威；开发期间可以领先于已发布代码。
- **版本增量 Spec**：独立记录本版本相对当前全量 Spec 的新增、修改和删除。
- **历史 Spec 与 Ticket**：发布后永久冻结；后续版本不得回写，错误通过勘误或新版本修正。
- 每个版本使用独立的 Spec 和 Ticket 文件，实际目录由项目自行规定。

## 版本与变更

- 增量 Spec 必须声明目标版本、基线版本和基线提交。
- 需求和变更使用稳定且唯一的 ID。
- 变更只分为 `Add`、`Modify`、`Remove`。
- `Modify` 和 `Remove` 必须写明原行为、最终行为、影响，并用 `Supersedes` 指向被替代的旧条款。
- 增量 Spec 定稿后，先将全部变化合并到当前全量 Spec，再生成 Ticket 和实施。
- 当前全量 Spec 必须标明目标版本和状态，避免把待开发需求误认为已发布能力。
- 实施期间如发生语义变化，必须同步更新增量 Spec、当前全量 Spec、相关 Ticket、测试和验收依据。
- 发布后将增量 Spec 标记为 `released`、Ticket 标记为 `resolved`；已发布 Git Tag 不移动、不重建。

## 冲突与权威

- 新版本只覆盖其通过 `Supersedes` 明确指定的旧条款；未被触及的旧需求继续有效。
- 发现未声明冲突时，先列出冲突条款和影响范围，由需求决策者确认后再继续。
- 冲突未解决前，不得生成或实施 Ticket。
- 增量 Spec 定稿并完成合并后，当前全量 Spec 负责完整目标行为；增量 Spec 负责说明本版本的变更范围和来源。
- Ticket、设计系统和 ADR 不得覆盖 Spec；发生冲突时先修正文档权威。
- 不得通过实现选择或测试预期静默解决需求冲突。

## Ticket

- 每个版本使用独立 Ticket 集合，编号可重新开始。
- Ticket 必须包含需求/变更 ID、依赖关系、完整验收标准、Test seam 和目标版本。
- Ticket 必须自包含，实施者无需自行拼接历史 Spec 才能判断完成条件。
- 当前全量 Spec 未完成更新或仍有冲突时，不得生成 Ticket。
- 完成时记录实现提交和验证证据。

## 发布

增量 Spec 定稿后、生成 Ticket 前：

1. 将 `Add` 加入当前全量 Spec。
2. 用 `Modify` 的最终行为替换旧表述。
3. 将 `Remove` 的需求移出当前全量 Spec。
4. 保留所有未被触及的有效需求。
5. 标明目标版本和当前状态，确认全量 Spec 完整且无冲突。

发布时只做最终一致性确认：实现与当前全量 Spec 一致后，更新发布状态和应用版本，冻结版本 Spec 与 Ticket，并创建发布 Tag。

只有以下条件全部成立才允许发布：

- 当前全量 Spec 单独可读、完整且无冲突。
- 当前全量 Spec 已准确合并增量 Spec 的全部变化。
- 每项变更均可追溯到需求、Ticket、实现和验证证据。
- 所有 Ticket 已通过验收。
- 兼容或迁移、自动化测试、必要的真实环境测试和人工验收均已完成。
- 当前全量 Spec、应用版本、发布记录和 Git Tag 一致。
- 历史文件与 Tag 未被改写，发布候选工作区干净。

任一条件不成立时，保持未发布状态并先修正问题。
