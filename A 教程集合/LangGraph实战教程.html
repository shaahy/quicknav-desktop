LangGraph 不是“又一个聊天机器人框架”。它是一套低层编排运行时：把状态、步骤、分支、暂停与恢复写成一张可控制的图。

01 / FIT

它解决的不是“生成”，而是“过程失控”

当任务从一次模型调用变成多步骤、会分叉、要等待、可能失败的过程，LangGraph 才开始体现价值。

适合使用

  • 长时间运行，中断后必须从检查点恢复
  • 确定性业务步骤与智能体决策混合
  • 高风险动作前需要人工批准或修改
  • 多角色协作、并行任务、循环质检
  • 需要逐节点流式展示状态与结果

暂时别用

  • 一次模型调用就能完成的简单问答
  • 只有固定直线步骤，普通函数已经清晰
  • 团队尚未定义状态、失败策略和结束条件
  • 误以为框架会自动设计提示词与业务架构
  • 只想快速得到标准工具调用 Agent
边界：LangGraph 管“怎么运行与恢复”，不替你选择模型、编写提示词或定义业务正确性。标准 Agent 可先用更高层的 LangChain；需要低层控制时再下沉到 LangGraph。
02 / MODEL

记住三个词，就能读懂一张图

State 是共享工作台，Node 是干活的人，Edge 是调度规则。节点完成后只返回状态更新，由边决定下一站。

State

当前任务快照。输入、阶段产物、判断结果都放在有明确 schema 的状态中。

Node

普通 Python 函数：读取当前状态，执行计算或副作用，返回需要更新的字段。

Edge

固定连线或条件路由。决定下一个节点，也可以形成循环、并行分发或结束。

compile → invoke

先把图编译为可运行对象，再用 invoke / stream 提交输入。编译时可挂载 checkpointer。

draft产生草稿

03 / PATTERNS

六种常用编排模式

先选最小可行拓扑。能用顺序就不要上 Agent，能用明确路由就不要让模型自由决定一切。

P-01

顺序链

步骤确定，前一步产物进入下一步。

清洗 → 提取 → 总结
A ─→ B ─→ C
P-02

条件路由

根据状态选择专门处理路径。

售后问题按退款 / 换货分流
A ─┬→ B
　 └→ C
P-03

并行化

互不依赖的任务同一 super-step 执行。

同时检查事实、格式和语气
A ─→ B + C + D
P-04

编排者—执行者

动态拆分未知数量子任务，再汇总。

长报告按章节并行撰写
PLAN ⇢ SEND[n] ⇢ MERGE
P-05

评估—优化循环

用明确标准打分，不达标就带反馈重做。

翻译、代码修复、内容质检
MAKE ↔ CHECK → END
P-06

Agent 循环

模型动态选择工具，直到满足停止条件。

方案和路径无法预先确定
MODEL ↔ TOOLS → END

一份可独立运行的最小图

保存为 review_graph.py。HTML 没有加载它；它只是教程中的文本代码。

PYTHON · review_graph.py
from typing import Literal, TypedDict
from langgraph.graph import StateGraph, START, END
from langgraph.checkpoint.memory import InMemorySaver
from langgraph.types import Command, interrupt

class ReviewState(TypedDict, total=False):
    topic: str
    draft: str
    risk: str
    approved: bool
    final: str

def draft_node(state: ReviewState):
    return {"draft": f"关于{state['topic']}的内容草稿"}

def risk_check(state: ReviewState):
    risky_words = ("删除", "转账", "发布")
    level = "high" if any(w in state["topic"] for w in risky_words) else "low"
    return {"risk": level}

def approval_node(state: ReviewState):
    approved = interrupt({"question": "是否批准？", "draft": state["draft"]})
    return {"approved": bool(approved)}

def publish_node(state: ReviewState):
    return {"final": f"已完成：{state['draft']}"}

def after_check(state: ReviewState) -> Literal["approval", "publish"]:
    return "approval" if state["risk"] == "high" else "publish"

def after_approval(state: ReviewState) -> Literal["publish", END]:
    return "publish" if state["approved"] else END

builder = StateGraph(ReviewState)
builder.add_node("draft", draft_node)
builder.add_node("check", risk_check)
builder.add_node("approval", approval_node)
builder.add_node("publish", publish_node)
builder.add_edge(START, "draft")
builder.add_edge("draft", "check")
builder.add_conditional_edges("check", after_check)
builder.add_conditional_edges("approval", after_approval)
builder.add_edge("publish", END)
app = builder.compile(checkpointer=InMemorySaver())

config = {"configurable": {"thread_id": "review-001"}}
first = app.invoke({"topic": "发布新品公告"}, config=config)
print("暂停结果：", first)
final = app.invoke(Command(resume=True), config=config)
print("恢复结果：", final)

运行时要看什么

第一次调用遇到 interrupt() 后返回暂停信息；同一 thread_id 携带 Command(resume=True) 再调用，图从检查点继续。

POWERSHELL
python review_graph.py
  • 输入“产品介绍”：risk=low，直接出现 final
  • 输入“发布新品公告”：返回 __interrupt__，尚无 final
  • resume=True：进入 publish，得到 final
  • resume=False：到 END，不产生 final
关键：thread_id 是恢复同一条执行线程的指针。换一个 ID 就是新任务。

06 / CHECK

上线前，先排除这六个坑

图能跑通不等于生产可用。状态设计、恢复语义和副作用边界往往比节点数量更重要。

01 · 状态变成杂物箱

只保存跨节点需要共享或恢复的数据；大对象放外部存储，状态里留引用。

02 · 没有明确结束条件

循环必须有次数、分数、预算或人工决策上限，避免无限执行。

03 · interrupt 前副作用不幂等

恢复时节点会从头执行。中断前的写库、扣款、发信必须可安全重放。

04 · 把内存存储用于生产

InMemorySaver 适合演示与测试；生产使用持久化 checkpointer。

05 · 所有判断都交给模型

权限、额度、合规等硬规则用确定性代码；模型负责模糊判断。

06 · 只测“批准”路径

至少覆盖直达、暂停、批准、拒绝、节点失败及恢复后的重复副作用。

最后用四问做决定

  1. 任务是否真的需要多个步骤或动态路径？
  2. 是否需要保存状态、暂停并在稍后恢复？
  3. 是否需要人工介入、流式进度或故障恢复？
  4. 团队是否愿意显式定义状态、边和结束条件？

前两问都是否：先写普通函数。前三问多数为是：LangGraph 值得进入技术验证。
