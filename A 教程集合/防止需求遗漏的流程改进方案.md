# FR 可追溯性机制 — 防止需求遗漏的流程改进方案

**问题**: 本项目开发完成后，发现 HTML title 自动读取等功能遗漏——PRD 阶段确认过的需求，在 Superpowers SDD 执行中丢失。
**目标**: 设计一套可复用的机制，在后续项目的 Speckit → Superpowers 衔接点插入强制验证，确保 0 遗漏。
**日期**: 2026-07-23

---

## 1. 根因定位

需求→实现的翻译链路存在四个断裂点：

| 断裂点 | 本项目的表现 | 通用化问题 |
|--------|------------|-----------|
| **A. Dispatch prompt 信息衰减** | Controller 的 prompt 只写了"addCard → HTML title"，未在 card-form-dialog 的 prompt 中重复此约束 | 每个 task 的 subagent 只看到自己的 prompt 片段，看不到完整 spec |
| **B. 缺少 agent 级 FR 自检** | 96 个 task 完成后，没有任何 agent 逐条对照 FR 清单验证"我负责的 FR 真的实现了吗？" | SDD 的"完成"标准是 tsc + test pass，不是 spec 覆盖 |
| **C. E2E 测试未覆盖 UI 集成层** | E2E 测试 mock 了 IPC，HTML title 预填这一真实用户旅程未被自动化验证 | 组件集成层的端到端行为落在单元测试和 mock E2E 之间 |
| **D. Controller 最终验证只跑自动化** | vitest run + tsc --noEmit 通过就宣布完成，没有人对照 spec SC 逐条做验收 | 自动化测试覆盖了代码正确性，没覆盖需求完整性 |

---

## 2. 核心机制：FR 可追溯性 Gate

在每个项目 Standard 执行流程中，插入三个强制 Gate：

```
Speckit (需求)                          Superpowers (实现)
    │                                        │
    │  ① FR-Task 映射文件                     │
    │  ┌──────────────────────────────┐       │
    │  │ 每条 FR → 负责的 task IDs     │       │
    │  │ 每条 FR → 验收条件（1句话）   │       │
    │  │ 每条 FR → E2E 覆盖（是/否）   │       │
    │  └──────────────────────────────┘       │
    │        │                                │
    │        ▼                                │
    │  ② Dispatch Prompt 模板                  │
    │  ┌──────────────────────────────┐       │
    │  │ 每个 task prompt 必须包含：   │       │
    │  │ - 该 task 负责的 FR 列表      │       │
    │  │ - 每条 FR 的验收条件          │       │
    │  │ - 关联的 E2E 测试要求         │       │
    │  └──────────────────────────────┘       │
    │        │                                │
    │        ▼                                │
    │  ③ FR Gate 检查脚本                      │
    │  ┌──────────────────────────────┐       │
    │  │ 实现完成后运行：              │       │
    │  │ - 每条 FR 是否有 task 覆盖？  │       │
    │  │ - 每条 FR 是否有测试验证？    │       │
    │  │ - 缺失的 FR → 阻断合并        │       │
    │  └──────────────────────────────┘       │
    │                                        │
```

## 3. 落地步骤

### 3.1 产出物：FR-Task 映射表

**时机**: `speckit-tasks` 完成后 **立即** 生成，不能跳过。

**格式** (`specs/<feature>/fr-task-map.md`):

```markdown
| FR | 简述 | 负责 Task | 验收条件 | E2E 覆盖 |
|----|------|----------|---------|---------|
| FR-003 | HTML 文件取 `<title>` 为默认名 | T037 (S10 surface), T032 (card-form-dialog) | 选 HTML 文件后表单预填页面标题 | ✅ uj1-first-card.spec.ts |
| FR-005 | 源文件唯一性 | T024 (useCards.addCard), T037 (S10) | 选已收录文件时弹冲突对话框 | ❌ 需补充 |
| FR-015 | 未分类不可选 | T030 (category-checklist), T025 (useCategories) | 类别复选列表中"未分类"灰显不可勾选 | ❌ 需补充 |
```

**关键规则**:
- 每条 FR 至少对应 1 个 Task
- "E2E 覆盖"列显式标记是否已有自动化验证——❌ 的行必须在 Phase 7 之前补齐
- 该文件作为 `speckit-tasks` 的输出物，不能事后补

### 3.2 产出物：Dispatch Prompt 模板增强

**时机**: 每个 SDD task dispatch 之前。

**当前模板**（问题版本）:
```
Implement toolbar-button React component.
Props: label, variant, onClick, disabled, icon.
Create: src/renderer/components/toolbar-button.tsx
```

**增强模板**（新版）:
```
Implement toolbar-button React component.

## 本 Task 负责的 FR
- FR-xxx: [一句话验收条件]

## 接口契约
Props: ...

## 验收自检（完成后逐条确认）
- [ ] FR-xxx: [具体行为] — 如何验证？
- [ ] `npx tsc --noEmit` 通过
- [ ] 覆盖本 task 的单元测试通过

## 文件
Create: src/renderer/components/toolbar-button.tsx
```

**关键规则**: 每条 FR 必须在 **至少一个** task dispatch prompt 中出现。如果一条 FR 跨多个 task，每个相关 task 的 prompt 都要包含该 FR。

### 3.3 产出物：FR Gate 检查脚本

**时机**: `superpowers:finishing-a-development-branch` 之前，作为合并门禁。

**脚本** (`scripts/fr-gate-check.ts`):

```typescript
// 读取 fr-task-map.md 和 spec.md
// 逐条检查：
// 1. FR 是否有 task 覆盖
// 2. FR 是否有测试（单元或 E2E）
// 3. E2E 标记为 ❌ 的 FR → 检查是否已补充
// 输出: PASS (全部覆盖) / FAIL (列出缺失项)

interface FRGateResult {
  fr: string        // FR-003
  description: string
  tasks: string[]
  hasTest: boolean
  e2eCovered: boolean
  status: 'PASS' | 'MISSING_TASK' | 'MISSING_TEST' | 'MISSING_E2E'
}
```

**关键规则**: 任何 `MISSING_*` 状态 → **阻断合并**。必须修复后才能 `finishing-a-development-branch`。

## 4. 修正后的 Standard 流程

在现有流程中新增三个强制节点（🔒 标记为 Gate，不可跳过）：

```
① using-git-worktrees
② writing-plans
③ subagent-driven-development
    └── 每个 dispatch prompt 使用 FR 增强模板  ← 🔒 新增
④ FR-Task 映射表生成                           ← 🔒 新增 (在 tasks 完成后)
⑤ test-driven-development (hooks + 组件)
⑥ requesting-code-review
⑦ FR Gate 检查                                 ← 🔒 新增 (在 finish 之前)
⑧ finishing-a-development-branch
```

---

## 5. Controller 检查清单

每次作为 Controller 执行 SDD 时，必须完成：

- [ ] `speckit-tasks` 完成后，生成了 `fr-task-map.md`？
- [ ] 每条 FR 在 map 中至少对应 1 个 task？
- [ ] 每个 dispatch prompt 包含了该 task 负责的 FR + 验收条件？
- [ ] 最终审查前，运行了 FR Gate 检查脚本？
- [ ] FR Gate 输出为 PASS（0 个 MISSING）？
- [ ] E2E 测试覆盖了所有 4 条 User Journey 的 Climax 点？

---

## 6. 成本估算

| 新增步骤 | 额外时间 | 说明 |
|---------|---------|------|
| fr-task-map.md 生成 | 5-10 min | 从 tasks.md 自动提取 + 人工补齐 E2E 列 |
| Dispatch prompt 增强 | 2 min/task | 每个 prompt 多写 5-8 行 FR 约束 |
| FR Gate 检查脚本 | 一次性编写，后续复用 | 通用工具，不随项目变化 |
| FR Gate 运行 | 30 sec | 自动化脚本 |

**总增量**: 项目级约 15-20 min 额外投入，换来 0 遗漏保证。投入产出比极高。
