Brownfield-first · OPSX · 单仓库实战

已上线 MVP v1.0，如何用 OpenSpec 安全做下一次增量

不重写旧系统，不补一套假文档。只把这一次真实变更的意图、行为、设计、任务与验证证据放进同一个 Change，再让实现围绕它推进。

贯穿案例

任务管理工具 v1.0 已经上线。v1.1 要增加“任务优先级 + 优先级筛选”，同时保证旧数据可读、旧接口兼容、失败可回滚。

01 · Mental model

先建立正确心智模型

OpenSpec 不是替代 PRD、Issue、Git 或测试。它是你与编码智能体之间的“变更级约定层”：先对这次改什么达成一致，再让代码、测试和文档围绕同一份约定收敛。

openspec/specs/

当前事实

系统现在承诺什么行为。按领域组织，例如 tasks/、auth/、billing/。

openspec/changes/

拟议变更

一次增量的 proposal、delta specs、design、tasks。归档后，Delta 才折叠进当前事实。

存量项目第一原则

不要先给 8 万行旧代码补全规格。只描述本次要改的切片：新增什么、修改什么、移除什么。每完成并归档一个 Change，主规格自然长出一圈。

1

Change 是工作单元

一个可独立理解、实现、验证、归档的增量。不要把季度路线图塞进一个 Change。

2

Delta 描述差异

用 ADDED、MODIFIED、REMOVED 描述变化，不重写整个目标系统。

3

产物是活计划

实现中发现新事实，可以回去修 proposal、specs、design、tasks。

4

归档闭合循环

只有代码通过验证、Delta 与现实一致后，才同步事实并归档 Change。

不要把 OpenSpec 当成自动批准器

/opsx:apply 完成任务不等于可以上线；/opsx:verify 也不替代项目自己的测试、代码审查、灰度和产品验收。

02 · Bootstrap

安装与存量项目接入

以下命令输入在 PowerShell、Terminal 或 IDE 终端中。OpenSpec 当前要求 Node.js 20.19.0 或更高版本。

PowerShell / Terminal · 环境检查与安装
node --version
npm install -g @fission-ai/openspec@latest
openspec --version

cd path/to/your-existing-project
openspec init

openspec init 会创建 openspec/，并为所选编码助手生成技能或命令文件。初始化本身不会要求你先描述整个旧系统。

建议立刻补一份项目上下文

openspec/config.yaml 会把技术栈、工程约束和每类产物的规则注入后续生成过程。这里只写稳定事实，不放临时需求，也不要复制整份 PRD。

openspec/config.yaml
schema: spec-driven

context: |
  Product: 已上线的任务管理 MVP v1.0
  Stack: TypeScript, React, Node.js, PostgreSQL
  API: REST + JSON；现有客户端仍依赖 v1 字段
  Testing: Vitest 单测；Playwright 关键路径回归
  Release: 数据库迁移必须向后兼容并提供回滚说明

rules:
  proposal:
    - 明确用户价值、范围外事项和回滚触发条件
    - 列出对已上线 v1.0 用户的影响
  specs:
    - 场景必须包含旧数据与异常输入
  design:
    - 说明数据迁移、接口兼容和可观测性
  tasks:
    - 每组任务必须带验证方法，不能只写实现动作

命令输入位置

openspec init、openspec show、openspec validate 输入终端；/opsx:explore、/opsx:propose、/opsx:apply 输入支持 OpenSpec 的 AI 编码助手对话框。

Core 与 Expanded 怎么选

配置适合主要命令
默认 Core希望快速跑通第一个增量explore、propose、apply、update、sync、archive
Expanded需要逐份产物控制、结构化 verify 或批量归档new、continue、ff、verify、bulk-archive、onboard

本教程以 Core 为主线，把 Expanded 的 /opsx:verify 作为推荐增强项。启用方式：

PowerShell / Terminal · 配置工作流后刷新项目指令
openspec config profile
openspec update

03 · Baseline

建立 v1.0 真实基线

增量开发最大的风险不是不会写新功能，而是不知道旧版本已经承诺了什么。先建立可复现基线，再讨论 v1.1。

  • 记录当前分支、提交 SHA、部署版本和数据库 schema 版本。
  • 执行仓库真实可用的 lint、typecheck、unit、integration、e2e 或 build。
  • 跑通至少一条线上核心路径：创建任务 → 编辑 → 完成 → 重启后仍存在。
  • 记录当前 API 样例与旧数据样例，后续用来证明向后兼容。
  • 确认回滚方式：应用回滚、功能开关、数据库 down migration 分别怎么做。
PowerShell / Terminal · 示例基线证据
git status --short
git rev-parse HEAD
npm run lint
npm run typecheck
npm test
npm run build

# 可选：把结果记录到 Change 外的项目交付系统或 PR
# 不要伪造项目里并不存在的命令

基线失败怎么办

先区分“原本就红”与“本次改红”。若基线本来失败，把失败项、错误文本和风险写进 proposal；不要把既有失败偷偷算成本次完成，也不要为了全绿擅自扩大范围修一大片旧问题。

04 · Explore

Explore：调查真实代码，但不建立承诺

/opsx:explore 是无承诺的调查动作。它适合在你知道用户目标、但还不知道代码插入点、兼容成本或方案优劣时使用。

AI 对话框 · 调查任务优先级增量
/opsx:explore

项目已上线 MVP v1.0。我准备增加任务优先级与筛选，但先不要写代码，
也不要创建 Change。请只读调查并回答：

1. 任务实体、数据库表、API DTO、前端状态分别在哪里；
2. 新字段从数据库到 UI 的完整数据路径；
3. 旧数据没有 priority 时，哪个默认值最安全；
4. 哪些旧客户端、缓存、导入导出和排序逻辑会受影响；
5. 现有测试和发布机制可以提供哪些验证证据；
6. 给出 2 个实现方案、取舍、推荐项及回滚路径。

Explore 结束时，你应该拿到什么

现状地图
具体到文件、表、接口和关键函数，而不是“修改后端和前端”这种空话。
影响半径
写路径、读路径、排序、过滤、缓存、导入导出、旧客户端和数据迁移。
关键未知
需要产品决定、真实环境验证或外部负责人确认的问题。
方案比较
至少包含用户影响、工程成本、兼容风险和回滚难度。
建议边界
这次 Change 做什么，哪些能力放到独立后续 Change。
退出 Explore 的标准

不是“聊得差不多”，而是你已经能用一句话说清用户问题、成功标准、范围、约束和推荐方案。仍有关键未知时，继续调查，不要急着 propose。

05 · Propose

Propose：把一个增量装进一个 Change

当目标和边界已经清晰，使用 /opsx:propose。默认 spec-driven schema 会生成 proposal、delta specs、design、tasks，直到满足实现依赖。

AI 对话框 · 创建 Change
/opsx:propose add-task-priority-filter

为已上线任务管理 MVP v1.0 增加：
- priority 字段：low / medium / high，旧数据默认 medium；
- 创建与编辑任务时可选择优先级；
- 列表可按优先级筛选；
- 保持现有 API 字段兼容；
- 数据迁移可回滚；
- 本次不做多级排序、批量修改、自动优先级推荐。

成功标准：
旧数据无损；旧客户端继续可用；刷新和重启后优先级仍存在；
筛选为空时有明确空状态；质量门全部通过；具备回滚证据。
openspec/ ├─ config.yaml ├─ specs/ ← 已归档的当前事实 └─ changes/ └─ add-task-priority-filter/ ├─ .openspec.yaml ├─ proposal.md ← 为什么做、做什么、不做什么 ├─ specs/ │ └─ task-priority/ │ └─ spec.md ← 行为增量与场景 ├─ design.md ← 技术方案、兼容、迁移、回滚 └─ tasks.md ← 可验证的实现清单

四类产物怎么评审

不要看到文件生成就直接 Apply。生成只代表“有草稿”，不代表“已达成约定”。

1. proposal.md：评审意图与边界

  • 用户问题是否真实，价值是否可观察？
  • 范围内与范围外是否能阻止“顺手多做一点”？
  • 是否点明已上线用户、旧数据、旧客户端和运营影响？
  • 成功标准是否可以验证，回滚触发条件是否明确？

2. delta spec：评审外部可观察行为

specs/task-priority/spec.md · 示例片段
## ADDED Requirements

### Requirement: Task priority
系统 SHALL 为每个任务提供 low、medium、high 三种优先级。

#### Scenario: Existing task without priority
- **GIVEN** 数据库中存在 v1.0 创建且没有 priority 的任务
- **WHEN** 用户升级后首次打开任务列表
- **THEN** 系统将该任务解释为 medium
- **AND** 任务标题、状态与创建时间保持不变

### Requirement: Priority filter
系统 SHALL 允许用户筛选指定优先级的任务。

#### Scenario: No task matches the selected priority
- **WHEN** 用户选择 high 且没有匹配任务
- **THEN** 页面显示明确空状态
- **AND** 用户可以一键清除筛选

场景写用户可观察行为，不写“调用某函数”“增加一个下拉框”。技术细节属于 design 或 tasks。

3. design.md：评审实现方向和风险

  • 数据模型：字段类型、默认值、约束、索引和迁移顺序。
  • 兼容：旧 API 请求不带字段、旧响应消费者忽略新字段时会怎样。
  • 前端：状态来源、筛选状态、空状态、错误恢复与无障碍。
  • 发布：先迁移还是先发应用，是否需要功能开关，如何观察异常。
  • 回滚：应用回滚后新字段数据如何处理，down migration 是否会丢数据。

4. tasks.md：评审实现顺序和证据

tasks.md · 推荐颗粒度
## 1. 数据与领域模型
- [ ] 1.1 增加可回滚迁移；验证旧数据映射为 medium
- [ ] 1.2 扩展领域类型与序列化；覆盖非法值

## 2. API
- [ ] 2.1 创建/更新接口接受 priority；旧请求保持成功
- [ ] 2.2 列表查询支持 priority；覆盖空结果与非法参数

## 3. 前端
- [ ] 3.1 表单增加可访问的优先级控件
- [ ] 3.2 列表增加筛选、清除与空状态

## 4. 验证与发布
- [ ] 4.1 单测、集成、E2E、构建通过
- [ ] 4.2 旧数据、旧请求、重启持久化验证通过
- [ ] 4.3 记录发布、观测与回滚步骤

评审 Gate

只有当四类产物互相一致、关键未知已解决、成功标准可验证，并且你明确同意方案后，才进入实现。OpenSpec 的流动性允许随时编辑，但不等于跳过人类决策。

06 · Apply

Apply：分批实现，不要把任务清单当黑箱

/opsx:apply 会读取当前 Change 并按 tasks 推进。对于已上线项目，建议按“数据 → API → UI → 全链验证”分批，每批都保持可检查、可恢复。

AI 对话框 · 明确本批范围
/opsx:apply add-task-priority-filter

先只执行 tasks 1.x：数据迁移与领域模型。
约束：
- 不修改 2.x、3.x；
- 每完成一项就更新 tasks.md；
- 运行相关单测与迁移往返验证；
- 展示修改文件、验证结果、风险与可恢复检查点；
- 发现设计与真实代码冲突时停止实现，先报告并更新 Change。
Batch 1迁移、模型、序列化
Batch 2API 写入、读取、兼容
Batch 3表单、筛选、空状态
Batch 4回归、E2E、构建
Release观测、回滚演练

每一批结束都检查五件事

  1. Diff：只改了本批授权范围吗？有没有顺手重构？
  2. 行为：新增、旧行为和失败路径分别有什么证据？
  3. 契约：代码仍符合 delta spec 与 design 吗？
  4. 状态：tasks 勾选是否与实际完成一致？部分完成有没有被伪装成完成？
  5. 恢复：当前提交或工作区能否安全继续、撤销或交接？

任务勾选的含义

[x] 应表示“实现完成且对应验证已通过”，不是“文件改过了”。无法验证时保留未完成，并说明缺少的环境、凭据或外部条件。

07 · Update

Update：实现中发现新事实，先校正规划再继续

OPSX 是动作式、可迭代工作流。发现设计假设错误时，不必假装规划从未变化，也不需要重开一个“修正规划阶段”。用 /opsx:update 修订已有规划产物并保持相互一致；它只改规划文件，不改代码。

AI 对话框 · 学习驱动的修订
/opsx:update add-task-priority-filter

实现中确认：移动端 v1.0 客户端会严格校验任务响应字段，
直接返回 priority 会导致解析失败。

请先提出对 proposal、delta specs、design、tasks 的一致性修订方案：
- 保持本次用户目标不变；
- API 通过版本化或显式 opt-in 返回 priority；
- 增加旧客户端兼容场景与验证任务；
- 不修改代码，逐项展示拟议编辑，等我确认后再写入规划产物。
情况处理判断理由
同一意图，补边界或改实现方案Update 当前 Change历史思路仍有价值，更新后故事更完整
范围收窄，但原目标不变Update 当前 Change例如 v1.1 先做手动优先级，自动推荐推迟
用户问题已经改变新建 Change例如从“增加优先级”变成“重做整个任务分类系统”
原 Change 可以独立完成，新需求独立成立完成并归档原 Change，再新建保持每个 Change 可理解、可关闭
实用判断法

意图相同、范围重叠超过一半、原 Change 不做这项就无法算完成，倾向 Update；反之倾向 New Change。更新保留上下文，新建提供清晰度。

08 · Evidence

Verify：用多层证据证明“真的完成”

验证顺序应从工程事实到规格一致性，再到用户验收。任何一层通过，都不能替代其他层。

第一层：项目自身质量命令

PowerShell / Terminal · 以仓库实际脚本为准
npm run lint
npm run typecheck
npm test
npm run test:integration
npm run test:e2e
npm run build

第二层：兼容、迁移与真实运行验证

  • 迁移前的 v1.0 数据升级后可读，标题、状态和时间没有漂移。
  • 旧请求不带 priority 仍成功，旧客户端响应契约不被破坏。
  • 新增字段保存后刷新、重启服务或重启桌面端仍然存在。
  • 非法 priority 得到稳定、可理解的错误，不写入脏数据。
  • 筛选无结果、请求失败、加载中和清除筛选均有正确 UI。
  • 回滚步骤在副本或测试环境中走通；明确是否有数据损失。

第三层：OpenSpec 规格一致性检查

如果已启用 Expanded 工作流，可以运行：

AI 对话框 · 结构化核对实现与产物
/opsx:verify add-task-priority-filter

重点阅读三类结果：

Completeness
tasks、requirements、scenarios 是否都有实现与证据。
Correctness
实现行为是否真的满足需求和具体场景。
Coherence
proposal、specs、design、tasks 与最终代码是否相互一致。

第四层：人工产品验收

让产品负责人按用户任务验收，而不是按文件列表验收：

  1. 打开升级后的旧账号，确认旧任务正常显示为 medium。
  2. 新建 high 任务，刷新后仍为 high。
  3. 编辑为 low，筛选 low 能看到，筛选 high 看不到。
  4. 清除筛选恢复完整列表；空状态不会让用户误以为数据丢失。
  5. 使用旧客户端或契约样例，确认核心路径仍可工作。

不要制造比证据更强的结论

单测通过只能说单测通过；测试环境迁移成功不能说生产迁移获批；Verify 通过不能说产品已验收。最终状态必须保留尚未完成的 Gate。

09 · Close the loop

Sync 与 Archive：把已证实的变化折叠进当前事实

完成实现与验证后，Delta Spec 应进入主规格，Change 则移入带日期的 archive。这样 openspec/specs/ 才描述新的当前事实。

大多数单一 Change

AI 对话框 · 归档完成的增量
/opsx:archive add-task-priority-filter

Archive 通常会检查是否需要同步 Delta，并在确认后完成合并与移动。归档前重新核对：

  • 所有 tasks 的勾选与证据一致；
  • 最终实现没有留下未写回 specs/design 的偏差；
  • 主规格合并后不会覆盖其他并行 Change 的事实；
  • Change 名称、日期和 Git 记录能够互相追溯。

什么时候单独 Sync

/opsx:sync 会把 Delta 合并进主规格，但保留 Change 继续存在。适合长周期 Change 中某段行为已经稳定，或团队希望先让其他 Change 基于新事实规划。不要为了“看起来进度快”提前同步尚未实现的行为。

Deltachanges/name/specs
Sync合并到 specs 当前事实
Archivechanges/archive/date-name

10 · Branches

异常分支与边界：什么时候不要机械跑主流程

场景建议动作不要做
线上 P0 故障先按事故流程止血；为较大修复补紧凑 Change，并在事后同步真实规格为了文档完整延误恢复服务
一行拼写或无行为变化直接修复并走仓库正常审查为任何微小编辑强建 Change
实现中出现重大新需求停止当前 Apply，判断 Update 还是新 Change把 scope explosion 偷塞进原 tasks
外部 API、账号或生产数据不可用保留未验证状态，列出所需权限与补验步骤用 mock 绿灯冒充真实环境通过
多个 Change 修改同一主规格先处理依赖和合并顺序，逐个验证 Delta并行归档后才发现规格互相覆盖

常见失败与纠正

Proposal 太大
拆成能独立提供价值、独立验证和独立回滚的 Change。
Spec 写实现
把函数、表结构、组件名移到 design；spec 只保留可观察行为。
Tasks 不可验证
每项补“完成后如何证明”，不要只写“实现筛选功能”。
Apply 越界
停止、展示额外 diff，恢复到授权范围；必要时新建 Change。
产物与代码漂移
判断哪个方向才是真实意图，再更新规划或代码；不要双边都保留。
Archive 太早
恢复 Change，补齐验证和主规格一致性后再归档。

11 · Team practice

团队落地：让 OpenSpec 接入已有工程制度

OpenSpec 最适合成为已有 Issue、分支、PR 和发布流程的中间层，而不是另造一套孤岛。

P

产品负责人

确认问题、范围、成功标准、范围外事项与人工验收，不批准技术细节的假确定性。

E

工程负责人

确认设计、迁移、兼容、观测、回滚和任务颗粒度，守住生产约束。

A

编码智能体

读取真实仓库，生成和维护产物，按任务实现并提供证据；遇到冲突必须暴露。

R

审查者

检查代码、测试和 Change 是否一致；Verify 报告是输入，不是审查结论。

建议的 Git 关联

命名约定示例
OpenSpec Change: add-task-priority-filter
Git branch:       feat/add-task-priority-filter
Issue:            MVP-142
PR title:         feat(tasks): add priority and filtering
Archive:          2026-07-28-add-task-priority-filter

并行 Change 的三条规则

  1. 每个 Change 有明确能力边界和主负责人。
  2. 若共享同一数据模型、API 或主规格，先记录依赖与合并顺序。
  3. 归档前基于最新主规格重新核对 Delta，不能只相信创建时的上下文。

跨仓库提醒

OpenSpec Stores 可以把规划放进独立仓库并被多个代码仓库引用，但该能力仍标注为 Beta。单仓库 MVP 不要过早升级复杂度；先把一个仓库内的 Change 循环跑顺。

12 · Checklist

一页速查与完成门槛

时机动作完成信号
接入安装、init、配置 context/rulesAI 能读到真实工程约束
需求模糊/opsx:explore现状、影响、未知、方案、边界清楚
目标明确/opsx:propose四类产物生成且人工评审通过
实现/opsx:apply按批完成，tasks 与证据同步
发现新事实/opsx:update 或新 Change规划与真实意图重新一致
验证项目测试 + 兼容/迁移 + verify + 人工验收每个结论都有匹配强度的证据
闭环/opsx:sync、/opsx:archive主规格成为新事实，Change 可追溯

Definition of Done

  • Proposal 的用户问题、范围和最终实现没有漂移。
  • 每条 Requirement 和 Scenario 都有实现与验证证据。
  • 旧数据、旧客户端、异常路径和回滚路径已验证或明确标为未验证。
  • 项目真实质量命令通过；没有把历史失败冒充本次通过。
  • tasks.md 的每个勾选都对应已完成且已验证的工作。
  • 最终代码偏差已经写回 specs/design，不存在双重事实。
  • 产品人工验收通过；发布和生产批准仍按团队制度执行。
  • Delta 已正确进入主规格，Change 已按可追溯名称归档。
最后只记住这一句

对已上线 MVP，OpenSpec 的价值不是写更多文档，而是让每一次小改动都有清晰边界、活的约定、匹配强度的证据，以及一个能回到“当前事实”的闭环。
