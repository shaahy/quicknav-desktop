01 / 先选对层级

别一上来就堆框架

LangChain、LangGraph、Deep Agents 不是互相替代的三个品牌，而是不同抽象层。按任务复杂度选最薄的一层。

30 秒判断固定工具、单用途 Agent → LangChain；复杂分支、循环、暂停恢复 → LangGraph；长任务、规划、文件和子 Agent → Deep Agents。若只是一次模型调用，甚至不需要 Agent。
本教程主线01

LangChain

高层 Agent 框架。模型、工具、结构化输出和中间件组合快速，适合先跑通业务闭环。

控制更精细02

LangGraph

低层编排运行时。适合确定性步骤与 Agent 混合、复杂状态、持久化和人工中断。

长任务套件03

Deep Agents

内置计划、文件系统、上下文管理与子 Agent。能力更全，但当前仍是 pre-1.0。

02 / 适用场景

什么时候值得用？

判断标准不是“是否用了大模型”，而是是否需要模型在受控边界内选择工具、读取数据，并多步完成任务。

固定工具的业务助手

订单查询、报价建议、工单分类、文件问答。工具少而明确，Agent 循环清楚。

模型需要可替换

希望在 OpenAI、Anthropic、Google、Ollama 等模型之间切换，而不重写业务骨架。

可靠的机器输出

用 Pydantic、dataclass、TypedDict 或 JSON Schema 约束字段，而不是从自然语言里硬解析。

文档知识接入

需要 Load → Split → Embed → Store → Retrieve → Generate 的 RAG 管线。

只问模型一句话

没有工具循环、检索或可复用编排时，直接调用模型接口更轻。

复杂确定性审批流

大量分支、并行、失败续跑和精确恢复点，应直接使用 LangGraph。

机器没有任何模型

LangChain 是框架，不自带推理模型。云模型需要网络，本地模型需要已安装服务。

高风险动作只靠提示词

支付、发信、删除、写生产库必须增加人工审批、最小权限和审计。

05 / Codex 桌面端实战

做一个订单风险分诊助手

案例数据写在本地代码中，不访问网页或数据库。它会查订单、计算可退金额，并输出结构化建议；不会真的退款。

1. 先写清楚契约

输入“检查 A1002，告诉我风险和下一步”
输出订单号、风险级别、原因、建议、是否人工复核
安全边界只读、不退款、不联网、查不到不编造

高金额、争议状态或规则外情况必须要求人工复核。模型只负责判断与解释，业务事实由工具返回。

3. 核对最小实现

Codex 生成的核心代码应接近下面的结构。模型名只是当前示例，可换成你已有且支持工具调用与结构化输出的模型。

agent.py
import json
from typing import Literal
from pydantic import BaseModel, Field
from langchain.agents import create_agent
from langchain.tools import tool

ORDERS = {
    "A1001": {"amount": 199.0, "days_since_purchase": 3, "status": "delivered"},
    "A1002": {"amount": 3899.0, "days_since_purchase": 42, "status": "disputed"},
}

@tool
def get_order(order_id: str) -> str:
    """读取指定订单；订单不存在时返回明确错误。"""
    order = ORDERS.get(order_id.upper())
    return json.dumps(order, ensure_ascii=False) if order else "ERROR: order not found"

@tool
def calculate_refund(order_id: str) -> float:
    """按演示规则计算可退金额；只计算，不执行退款。"""
    order = ORDERS.get(order_id.upper())
    if not order:
        raise ValueError("order not found")
    return order["amount"] if order["days_since_purchase"] <= 30 else 0.0

class TriageResult(BaseModel):
    order_id: str
    risk_level: Literal["low", "medium", "high"]
    reason: str
    recommended_action: str
    needs_human_review: bool = Field(
        description="高金额、争议或规则外情况必须为 true"
    )

agent = create_agent(
    model="openai:gpt-5.5",  # 可替换为你已有的受支持模型
    tools=[get_order, calculate_refund],
    response_format=TriageResult,
    system_prompt=(
        "你是订单风险分诊助手。必须先查订单；不得编造。"
        "你只能给建议，不能执行退款。高金额、争议或规则外情况要求人工复核。"
    ),
)

result = agent.invoke({
    "messages": [{"role": "user", "content": "检查 A1002，告诉我风险和下一步"}]
})
print(result["structured_response"])

5. 三层验证，不伪造成功

① 纯工具测试订单存在、未知订单、30 天边界、退款金额规则。无需模型。
② Fake model 单测验证 Agent 结构与预期工具调用，快速、免费、可重复。
③ 真实集成测试验证模型兼容性；断言字段与工具参数，不硬匹配整段回答。

最终让 Codex 报告：执行了哪些命令、哪些测试真实通过、哪些因缺少密钥或模型服务没有运行。

06 / 常见避坑

少踩四个坑

LangChain 的问题往往不在“能不能跑”，而在依赖边界、工具描述、安全动作和测试方法。

工具越多越好吗？

不是。工具过多或描述相似会增加误选。每个工具保持单一职责，函数名、参数名和 docstring 要准确说明“何时使用、输入什么、返回什么”。

换模型只改一行就行？

接口层通常可替换，但工具调用、结构化输出、流式等能力并不完全等价。换模型后必须重跑集成测试。

LangSmith 是必需的吗？

不是。它是可选的在线追踪、调试与评估平台。最小 LangChain Agent 可以不接 LangSmith。

现在该学旧版 Chain API 吗？

新教程应以 LangChain 1.x 的 create_agent() 为主线。旧 langchain-classic 不再增加新功能，不适合作为新项目起点。

Deep Agents 更强，是否直接上？

只有任务确实需要计划、文件系统、子 Agent 和长上下文时才值得。它仍是 pre-1.0，小版本间可能变化。

怎样保管 API key？

只通过环境变量或被 .gitignore 排除的本地配置读取；不要写入代码、教程、日志、截图或提交历史。
