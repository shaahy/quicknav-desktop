Spec-driven development · Incremental delivery

Flow-Forward不是新开一个分支。

它是一条不可覆盖的产品与工程演进链。Git 分支隔离本次工作；新的 feature 目录保存这次变化为什么发生、承诺了什么，以及项目如何走到今天。

01

Mental model

先把三个对象彻底分清

Flow-forward 的历史单元是 specs/<feature>/。Git 分支和当前 feature 状态都服务于这次工作，但它们不是同一个东西。

Feature artifact

specs/002-add-task-priority/
长期保留，解释本次需求、计划、任务与决策。

Git feature branch

feat/add-task-priority
隔离代码和评审；合并后可按团队规则删除。

Active feature state

.specify/feature.json
告诉后续命令当前使用哪个 feature 目录。

当前官方行为 /speckit.specify 总会创建新的 spec 目录和 spec.md。是否创建 Git 分支，取决于可选 Git 扩展的 before_specify hook。分支名不决定 spec 目录名。
001
任务管理 MVP已经发布 · 基础行为
specs/001-task-manager-mvp/
002
新增任务优先级Extends 001 · 保留原有权限与任务流程
specs/002-add-task-priority/
003
调整优先级提醒Extends 002 · Supersedes 001 的提醒规则
specs/003-adjust-priority-reminders/
模型需求变化时怎么做最适合主要风险
Flow-forward创建新的 feature 目录，旧目录保持历史原样审计、跨团队、已上线产品当前行为分散，需要演进索引
Living spec先修改现有 spec.md，再传播到 plan/tasks规格本身必须永远代表当前合同重生成时可能丢失历史理由
Flow-back允许从 spec、plan、tasks 或代码任意处开始，再人工对齐小团队、快速探索容易产生无声漂移
02

Scenario decision

什么情况应该新建 feature？

不是每次改代码都要向前创建。关键看：原 feature 是否已经成为历史、用户可见行为是否改变、这次变化能否独立验收或回滚。

三问判断器

依次选择最符合当前情况的答案，页面会给出建议。判断器只帮助分类，最终仍以团队治理规则为准。

1. 原 feature 已合并或上线了吗？
2. 这次变化会改变用户、API、数据或权限行为吗？
3. 它需要独立验收、发布或回滚吗？

快速场景表

场景建议理由
上线后新增用户可见能力新建 feature这是新的产品事实，需要独立历史
修改已上线 API、权限、状态流或数据字段新建 feature涉及兼容、迁移、发布和回滚
当前 feature 内澄清同一目标更新当前 artifact它还没有冻结为历史；更新后重新 analyze
代码没有实现已批准的 spec修实现偏差不要把缺陷伪装成产品新需求
纯内部重构且外部行为不变通常不新建产品 feature按团队工程变更流程处理
上线后撤销功能新建 revert/disable feature撤销本身也是发生过的产品变化
目标从“固定 P0-P3”扩大为“可配置工作流”停止扩大，拆新 feature新目标已能独立产生价值和风险

Git 分支由谁创建？

让 hook 拥有分支创建权 不要提前执行 git switch -c。before_specify 会在 specification 前创建或切换编号分支。
PowerShell · 检查并回到基线
specify extension list
Get-Content -Encoding utf8 .specify\extensions.yml
Get-Content -Encoding utf8 .specify\extensions\git\git-config.yml

git switch <default-branch>
git pull --ff-only
git status --short
人工创建专用分支 这不影响 Flow-forward。新 spec 目录仍由 speckit.specify 创建，分支名与目录名可以不同。
PowerShell · 手动分支
git switch <default-branch>
git pull --ff-only
git status --short
git switch -c feat/add-task-priority
为什么不建议在产品 feature 中顺手安装 Git 扩展？

扩展会改变 `.specify/extensions/`、hook、命令或 skill 行为，这是团队工具链治理变更。把它与产品需求混在同一个 PR，会让评审者难以区分“工具变化”和“产品变化”，也增加回滚耦合。

更稳妥的做法是单独建立流程分支，执行 specify extension add git，审查差异并验证团队工具后再合并。

Review & release

让 PR 讲清楚完整变化

PowerShell · 最终范围检查
git status --short
git diff --stat <default-branch>...HEAD

# 旧 feature 应无输出
git diff <default-branch>...HEAD -- specs\001-task-manager-mvp

# 审查新 feature
git diff <default-branch>...HEAD -- specs\002-add-task-priority
避免 git add . 按 artifact、源码、测试和迁移路径明确暂存，防止把无关本地文件掩盖进提交。

推荐评审顺序

  1. spec.md：产品行为、边界和历史关系是否正确。
  2. plan.md：方案、迁移、兼容、回滚和性能是否合理。
  3. tasks.md：是否漏项、越界或依赖错误。
  4. 测试：是否真正证明核心场景和失败路径。
  5. 代码：是否忠实实现已经批准的 contract。
  6. Converge 与发布方案：是否仍有缺口或无证据勾选。

调整任务提醒规则，使提醒时间与任务优先级关联。

历史关系：
- Extends: specs/002-add-task-priority/spec.md
- Supersedes: specs/001-task-manager-mvp/spec.md 中统一提前 24 小时提醒的规则
- Preserves: 任务创建、优先级编辑、通知渠道和权限

目标行为：
- P0/P1 提前 48 小时提醒；
- P2/P3 提前 24 小时提醒；
- 优先级或截止时间改变时，重新计算尚未发送的提醒；
- 已发送提醒不重复；
- 完成或取消的任务不再提醒；
- 明确时区、夏令时、重试和去重规则；
- 存量任务按新规则重新计算；
- 回滚后恢复统一提前 24 小时。

不修改旧 feature 目录。只定义产品行为和验收标准。

Failure recovery

并行、错误与恢复

错误 1：手动建分支后，Git hook 又创建了分支

原因是没有先检查 Git 扩展。暂停生成，确认两个分支和未提交文件分别在哪里，再选择正确分支。不要使用 git reset --hard 粗暴恢复。

错误 2：新需求直接修改了 001/spec.md

把新内容迁移到新的 feature spec；旧目录恢复为默认分支原样；新 spec 添加 Extends、Supersedes 与 Preserves 关系。

错误 3：分支名和 spec 目录名不同，以为工具坏了

这是允许的正常行为。检查 .specify/feature.json；后续命令以其中的 feature directory 为准。仅切换 Git 分支不会自动切换 active feature。

错误 4：从旧 feature 分支创建下一个 feature

这会产生隐含依赖。除非团队明确使用 stacked branches，否则回到最新默认分支后重新创建。不要在不清楚提交关系时强行 rebase。

错误 5：tasks 全勾选就准备合并

tasks 可能漏项，勾选也可能没有真实证据。必须运行真实测试、人工验收和 Converge，并抽查需求到证据的映射。

错误 6：Spec Kit 升级与产品 feature 混在一个 PR

拆成工具升级 PR 与产品 feature PR。强制刷新项目文件前保护 constitution、templates、scripts 等自定义内容。

并行 feature 与编号冲突

  • 创建前更新默认分支并检查远程已有 feature。
  • 使用 Git 扩展时，让扩展管理编号与分支创建。
  • 高并发团队可评审采用 timestamp numbering。
  • PR 中检查 specs/<编号-名称>/ 是否冲突。
  • 目录重命名时同步检查 .specify/feature.json 和交叉链接。
两个编号轴 当前版本中，feature 目录编号由 .specify/init-options.json 的 feature_numbering 控制；Git 扩展分支编号由 .specify/extensions/git/git-config.yml 的 branch_numbering 控制。不要把二者混为一个设置。

推荐团队约定

Flow-Forward Working Agreement
1. 每个上线后的用户可见变化创建新的 feature 目录。
2. 已完成 feature 目录是不可改写的历史记录。
3. 每个 feature 使用专用 Git 分支。
4. Git 扩展启用时由 hook 创建分支，否则人工创建。
5. Git 分支名与 feature 目录名相互独立。
6. 新 feature 标明 Extends、Supersedes、Preserves 与 Related。
7. Spec Kit 工具升级与产品 feature 分开评审。
8. 实现前运行 Analyze；实现按高风险边界暂停。
9. 真实测试与 Converge 均通过后才能合并。
10. 已发布后的回滚也记录为新的 forward feature。
11. specs/README.md 维护演进关系与发布状态。
