Independent comparison tutorial

不要问谁最好，
先问你要交付什么。

Huashu Design、Taste Skill 与 UI UX Pro Max 不是同一种工具：一个偏成品视觉交付，一个偏营销前端审美，一个偏系统化 UI/UX 规则与跨技术栈实现。

给怡哥的默认选择
以 UI UX Pro Max 作为日常产品界面的默认技能；需要营销页个性时临时启用 Taste。Huashu 不再作为本项目的设计方法。

一次任务只指定一个“审美主责”。第二个技能最多承担审查，不要让三套规则同时争夺页面控制权。

01 / Method

我们比较的不是 Star，而是任务适配度

公开资料里没有一项可信的、控制变量一致的三方盲测。因此，本教程不制造“总冠军”，而是把官方能力、社区采用量与实际工作场景分开判断。

EVIDENCE 01

官方能力

检查 SKILL.md、仓库结构、支持技术栈、工作流和明确写出的限制。这决定“它声称能做什么”。

EVIDENCE 02

采用信号

GitHub Star、skills.sh 安装量只说明传播与尝试规模，不等于同一提示词下的输出质量。

EVIDENCE 03

场景判断

把任务拆成视觉成品、营销审美、产品系统、可访问性和工程落地，再决定由谁主责。

没有公开三方盲测。 下文的“更好”均表示在特定任务上更适配，而不是证明某个技能在所有模型、提示词和项目上下文中绝对胜出。

03 / Project anatomy

三个项目，三种“设计能力”

理解定位差异，比背诵功能列表更重要。下面分别说明它们如何工作、擅长什么，以及什么时候不该用。

01

Huashu Design

从方向探索到多格式视觉成品
成品导向HTML / PPTX / 动画

Huashu 把设计视为一套交付流程：先探索多个真实视觉方向，再根据选择产出可点击原型、幻灯片、信息图、GIF/MP4 等结果，并强调品牌资产、真实内容和浏览器验证。

核心角色
视觉设计师与成品制作流程
优势
交付类型广、中文场景友好、方向确认机制完整
限制
流程和上下文都较重；官方也承认缺少品牌输入时存在质量上限

优先使用

  • 高完成度视觉演示
  • 管理层汇报材料
  • 需要多方向探索
  • HTML 与演示文稿联动
不适合：方向不明确但又不愿经过选择闸门，或者只想快速建立稳定产品界面规则。
02

Taste Skill

反模板化的营销前端审美约束
审美导向Landing / Portfolio / Redesign

Taste 通过明确的“禁止清单”和风格分支，压制常见 AI 页面套路，例如平均三卡片、紫色渐变和虚假的产品截图。它更关注页面的构图、节奏、动画骨架与品牌个性。

核心角色
有强烈主张的前端艺术指导
优势
对营销前端的模板味诊断具体，适合重设计和作品型网站
限制
官方明确说明主要面向落地页、作品集和改版，而非仪表盘、数据表与多步骤产品 UI

优先使用

  • 品牌落地页
  • 作品集与创意网站
  • 旧官网视觉重构
  • 去除 AI 模板感
不适合：严格遵守既有企业设计系统，或复杂后台、数据表和流程型产品。v2 当前仍带实验性标签。
03

UI UX Pro Max

可检索设计知识库、设计系统生成器与工程护栏
系统导向84 styles / 22 stacks

Pro Max 不是单一视觉风格，而是一套本地可检索的设计决策库。它根据产品类型生成样式、颜色、字体、布局、反模式和交付检查表，再结合不同技术栈给出实现规则。

核心角色
设计系统顾问、UX 检查员与跨栈实现导航
优势
覆盖可访问性、响应式、图表、产品类型和 22 种技术栈；本地搜索不联网
限制
规则广不等于自动拥有独特品味；字体推荐可能指向 Google Fonts，需要按离线约束替换

优先使用

  • 后台与仪表盘
  • 桌面和移动产品
  • 设计系统与规范
  • 可访问性与交付审查
不适合：把它当作品牌资产生成器。开源基础版不包含完整品牌、Logo、CIP、演示文稿等高级资产能力。

06 / Recommended workflow

正确的组合不是“三个都开”

技能叠加会带来上下文膨胀和规则冲突。更稳妥的方式是先锁定项目事实，再指定一个审美主责，最后让第二个技能做有边界的审查。

STEP 01

锁定事实

用户、任务、内容、品牌资产、技术栈与离线限制先成为源事实。

STEP 02

选择主责

产品系统选 Pro Max；营销个性选 Taste；视觉成品选 Huashu。

STEP 03

生成与实现

只让主责技能决定结构、视觉令牌和交互，避免混合美学。

STEP 04

边界审查

第二技能只检查指定维度，例如可访问性或营销首屏个性。

本教程自身就是示例：由 UI UX Pro Max 生成 Trust & Authority 设计系统；在线字体被离线约束否决，Tailwind 写法被转换为原生 CSS；Huashu 不再参与视觉决策。

07 / Prompt recipes

可以直接复用的三类提示词

高质量输出依赖具体上下文。把品牌、受众、技术栈、内容和验收标准写清楚，比单独说“做得高级一点”有效得多。

产品界面 · Pro Max
使用 UI UX Pro Max，为【产品】设计【页面】。 目标用户：【用户】；核心任务：【任务】。 技术栈：【栈】；品牌令牌：【颜色/字体/组件】。 先生成设计系统，再实现页面。 必须满足：键盘导航、4.5:1 对比度、375/768/1440 响应式、无横向溢出。 不要引入未授权的在线资源。
营销页面 · Taste
使用 Taste Skill 重构【品牌】的【落地页/作品集】。 品牌资产：【链接或本地文件】；受众：【人群】。 保留：【必须保留内容】；转化目标：【CTA】。 明确避开：平均三卡片、AI 紫色渐变、虚假产品 UI。 先审计当前模板味来源，再给出一个主方向并实现。
视觉成品 · Huashu
使用 Huashu Design，为【主题】制作【HTML/PPTX/信息图】。 唯一内容基线：【文件】；受众：【对象】。 品牌资产：【文件夹】；尺寸与格式：【规格】。 先给 3 个真实方向截图，等待我选择后再制作最终稿。 验收：真实内容、浏览器截图、无溢出、交付文件可编辑。
08 / Final recommendation

给怡哥的综合建议

默认 Pro Max，按需 Taste，不再默认 Huashu

这是结合你的反馈与当前工作类型得出的个人化路由，不是对三个项目的绝对排名。

日常默认UI UX Pro Max。适合教程、工具、后台、桌面产品、复杂流程和需要明确验收规则的工作。
临时增强Taste 只在官网、落地页、作品集或“去模板味”改版任务中担任审美主责。
Huashu 处理本项目停止使用。未来只有当你明确需要幻灯片、信息图、动画等视觉成品，并认可其方向闸门时再单独启用。
不要这样做不要全局常驻三个技能；不要把 Star 或安装量当成质量分；不要让技能覆盖项目已经批准的设计系统。
