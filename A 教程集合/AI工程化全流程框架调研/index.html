01

先看结论

六套框架分别占据不同层级。真正的工程化来自职责边界、工件链路和质量门禁，不来自安装数量。

如果只能选一套

完整产品从 0 到 1：选 BMAD。它在六者中对分析、PRD、UX、架构、Epic/Story 和实施跟踪的覆盖最完整。

已有产品持续改造：选 OpenSpec。它把当前事实与拟议变更分开，最适合 1→n 演进。

明确的新功能工程交付：选 Spec Kit 或 Superpowers，分别解决契约与执行纪律。

如果要搭教程与长期系统

使用“分层组合”，但每层只设一个权威：

产品事实源 BMAD变更账本 OpenSpec工程循环 SuperpowersSpec Kit 作为替代引擎PM / Matt 增强

最危险的误区

BMAD PRD、PM Skills PRD、Spec Kit spec、OpenSpec delta、Matt to-spec 全部并行维护。结果不是更严谨，而是多个“真相”逐渐分叉。每个 feature 必须在 OpenSpec 与 Spec Kit 中二选一。

六者共同缺口

没有任何一套核心框架能自动替你完成真实生产运维。云资源、CI/CD、密钥、迁移、可观测性、告警、回滚、SLO、成本治理仍要按项目补齐。Spec Kit 可通过社区扩展增强，但扩展需独立审计。

一句话选型你不是要选“最强框架”，而是要确定：谁拥有产品意图，谁把意图变成特性契约，谁约束代码生产，谁负责上线后的学习闭环。

六套框架逐一拆解

1. mattpocock/skills

可组合、可修改的“真实工程师技能包”

作者明确反对让大框架接管全部过程，主张小而可改的技能。核心围绕澄清、共享语言、领域建模、研究、工单拆分、TDD、调试、代码审查和架构改善。

工程增强高控制权Issue 驱动Agent Skills

典型流

grill-with-docs → to-spec → to-tickets → implement → tdd → code-review；大项目可先用 wayfinder 建调查工单地图。

代表技能

grill-me、grill-with-docs、research、domain-modeling、prototype、to-spec、to-tickets、implement、tdd、diagnosing-bugs、code-review、improve-codebase-architecture。

适合

能读代码、重视自主控制、已有工程工作流、希望把好习惯装成能力模块的个人或团队。

不适合

期待开箱即用的市场研究、PRD、UX、发布运营全流程；或者希望框架自动告诉你每一步的人。

优势
小、透明、容易替换；工程基本功强；共享语言和 ADR 思路有长期复利。
代价
需要操作者自己编排；产品与运营覆盖弱；与 Spec Kit/Superpowers 有大量重叠。

官方依据：README 与技能目录。

2. BMAD-METHOD

上下文工程驱动的完整产品开发方法

通过专业 Agent、结构化工作流和逐步累积的工件，把分析、规划、方案设计与实施连接起来。官方 V6 文档给出 Quick Flow、BMad Method、Enterprise 三种复杂度轨道。

端到端主干专业 Agent规模自适应工件链

典型流

brainstorm/research → product-brief → PRD → UX → architecture → epics & stories → readiness → sprint → story/dev/review → retrospective。

代表 Agent / Skill

Analyst、PM、Architect、Developer、UX Designer、Technical Writer；bmad-help、bmad-prd、bmad-ux、bmad-architecture、bmad-create-epics-and-stories、bmad-check-implementation-readiness、bmad-dev-story、bmad-code-review。

适合

0→1 产品、复杂平台、跨角色协作、非纯工程背景 DRI、需要清晰阶段和正式工件的团队。

不适合

几小时即可完成的简单改动却走全流程；对流程负担极敏感；不愿维护规划工件的团队。

优势
六者中生命周期最完整；PRD/UX/架构/故事衔接清晰；有 readiness gate 与路线导航。
代价
学习成本最高；长流程易仪式化；需用新对话隔离阶段；生产运维仍需项目级补充。

官方依据：Workflow Map、Getting Started。

3. phuryn/pm-skills

产品经理的模块化方法库与工作流市场

当前 README 标示 9 个插件、68 个 PM skills、42 个链式工作流，覆盖发现、战略、研究、数据、执行、GTM、增长和 AI shipping。强项是“选一个 PM 方法立即使用”。

产品增强发现与战略GTM/增长AI shipping

典型流

/discover → /strategy → /write-prd → /write-stories → /test-scenarios → /ship-check → /plan-launch → /north-star。每个命令可链多个技能。

代表技能

机会树、假设识别、实验设计、用户画像、市场规模、竞品、产品战略、PRD、用户故事、测试场景、北极星指标、GTM、A/B 测试、security/performance static audit。

适合

PM、创始人、产品型 DRI；需要快速调用成熟框架，补齐发现、战略、指标、发布与运营能力。

不适合

把它当成完整编码执行引擎；期望它独立解决架构、TDD、代码集成与生产部署。

优势
产品方法覆盖最广；模块独立、易学易试；Codex/Claude 均可使用 skills；新增 AI shipping 恢复代码可审查性。
代价
方法多容易“框架购物”；slash command 在不同宿主表现不同；PRD 能力会与 BMAD 重叠。

官方依据：README、AI Shipping Kit。

4. github/spec-kit

把规格变成可执行开发契约的 SDD 工具链

核心思想是 Spec-Driven Development：规格不再是写完即丢的说明，而是驱动计划、任务、实现和收敛验证的可执行上下文。2026 文档已扩展为 integration、extension、preset、workflow、bundle 体系。

规格驱动可追踪跨 Agent组织治理

完整流

constitution → specify → clarify → plan → checklist → tasks → analyze → implement → converge。其中 analyze 只读检查跨工件一致性，converge 对照实现补任务直到收敛。

扩展机制

Integration 适配编码 Agent；Preset 覆盖模板和规则；Extension 增加能力；Workflow 支持条件、循环、并行和人工检查点；Bundle 打包整套组织配置。

适合

需求已经进入工程交付、重视可追踪性、跨工具团队、需要标准化 feature delivery 与组织治理的场景。

不适合

前期商业发现、深入产品策略、完整 UX 探索；对一个小修复强行生成全套工件。

优势
特性级契约最强；跨 Agent 兼容广；组织级可扩展；converge 让“实现完成”回到规格证据。
代价
核心仍偏工程；扩展质量不一且需审计；与 BMAD 的 spec/architecture/tasks 边界必须明确。

官方依据：Quick Start、官方文档。

5. Fission-AI/OpenSpec

面向 brownfield 的轻量变更规格与演进账本

OpenSpec 把 openspec/specs/ 定义为系统当前行为事实源，把每项拟议修改放入独立的 openspec/changes/<change>/。proposal、delta specs、design、tasks 随变更同行；完成后通过 sync/archive 把增量语义合入当前规格并保留审计历史。

Brownfield-firstDelta SpecsLiving Specs轻量变更流

当前 OPSX 主线

核心 quick path：explore（可选）→ propose → apply → archive；sync 用于在归档前把 delta 同步进 current specs。需要逐步控制和显式验证时启用 expanded profile：new → continue/ff → apply → verify → archive。OpenSpec 1.0 已移除旧的 /openspec:* 命令。

关键工件与机制

proposal.md 解释 why/scope，delta spec 以 ADDED/MODIFIED/REMOVED/RENAMED 描述行为变化，design.md 记录技术方案，tasks.md 跟踪实施。verify 检查 completeness、correctness、coherence，但默认不会阻止 archive。

适合

已有系统持续迭代、并行变更、跨多个 capability 的修改、需要“为什么改/改了什么/最终事实是什么”审计链的个人与团队。BMAD 已承担完整规划时，它尤其适合作为下游轻量变更层。

不适合

前期市场与产品发现、完整 UX、强制 TDD；需要默认硬门禁时还必须由 CI 或 DRI 政策补上，因为 verify 可以带 warnings 归档。

优势
当前事实与提案分离；delta 合并适合 1→n；每个 change 自包含、易审查；上手轻，跨 Agent 支持广。
代价
产品层较薄；verify 非硬阻断；任务粒度与测试纪律不如 Superpowers；与 Spec Kit 同时使用会产生双规格源。

官方依据：README、Concepts、Workflows、1.0 Changelog。

6. obra/superpowers

强制执行好工程习惯的 Agent 开发方法

它不是产品管理框架，而是一套会自动触发的研发方法：写代码前先 brainstorming，批准设计后写细粒度计划，再用 worktree、subagent、TDD、双阶段审查和完成前验证推进。

工程执行强约束TDDSubagent

基本流

brainstorming → using-git-worktrees → writing-plans → subagent-driven-development → TDD → requesting-code-review → finishing-a-development-branch。

代表技能

systematic-debugging、verification-before-completion、dispatching-parallel-agents、receiving-code-review、test-driven-development、finishing-a-development-branch。

适合

已有代码仓库、要求高质量实现、愿意严格执行 TDD 与审查、支持 subagent 的开发环境。

不适合

非技术产品发现、商业/市场/运营；团队明确不采用测试优先；无法接受技能自动介入流程。

优势
执行纪律最强；失败路径和完成声明有证据门禁；任务隔离与双审查适合长时间自治。
代价
控制感可能偏低；流程有强意见；subagent 成本更高；与 Matt 的 TDD/调试/审查高度重复。

官方依据：README、Release Notes。

04A

规格引擎决策：OpenSpec 还是 Spec Kit

两者都优秀，但解决的是不同阶段的问题。生产项目应二选一；可以在一次性实验分支中比较，不应让同一 feature 同时维护两套契约。

Brownfield强项 以现状 + delta 演进可用，但完整 feature 工件更重持续迭代、维护型 SaaS、多个并行 change 选 OpenSpec

质量门禁/opsx:verify 检查完整性、正确性、一致性，但警告不硬阻止 archivechecklist/analyze/converge 强调跨工件一致与完成证据用 OpenSpec 时必须把 verify + CI 设为你自己的强制 Gate

没有跨场景的统一默认。新产品缺少稳定 current specs，需要从意图建立完整 feature 包，默认选 Spec Kit；已有产品已经存在被用户依赖的行为，需要审清“相对现状改了什么”，默认选 OpenSpec。判断依据是事实状态，而不是项目大小或个人偏好。
一个仓库可以迁移，但一个 feature 不能双写。迁移时先冻结旧引擎、确定新事实源、只迁移仍有效的行为与未关闭变更，再用一次完整验收确认。不要自动把历史草案都升级为当前事实。
05

两套推荐组合架构

新产品需要先建立完整的产品与系统事实；已有产品需要保护现状、控制差量。两种场景不能套用同一条规格路径。

架构 A · GREENFIELD

新产品 / 新项目组合架构

适合：问题、范围、UX、架构和首批 feature 尚未形成稳定事实的新项目。
01
PM Skills · 机会与产品决策

用户、问题、假设、实验、战略、指标。它提供决策输入，不另建正式 PRD。

02
BMAD · 产品与系统主干

Brief → final PRD → UX → Architecture → Epics/Stories → Readiness。

03
Spec Kit · Feature 执行契约

从已确认 Story 派生 specify → clarify → plan → checklist/tasks → analyze；适合尚无稳定 current specs 的完整 feature 定义。

04
Superpowers · 工程执行

隔离工作区、细粒度计划、TDD、系统化调试、规格审查、代码审查与完成前验证。

05
PM AI Shipping + CI/CD · 发布与学习

动态测试、ship-check、灰度、回滚、指标与复盘；结论回流 BMAD 或新的 feature。

权威链：BMAD final PRD 管产品范围 → Architecture/ADR 管系统决策 → Spec Kit spec 管单个 feature → tests/review/CI 管完成证据。
架构 B · BROWNFIELD

已有产品增量迭代组合架构

适合：已有用户、生产代码、约束和稳定行为，需要连续小步新增、修改或移除能力。
01
PM Skills · 信号与优先级

汇总指标、反馈、事故与商业目标，确认问题及成功标准；不从“想做功能”直接开工。

02
现有事实源 + BMAD Correct Course

以 final PRD、Architecture/ADR、现行文档、测试和生产行为校准基线；只有范围或系统级决策变化才升级回 BMAD。

03
OpenSpec · 语义差量账本

explore → propose；用 ADDED/MODIFIED/REMOVED/RENAMED delta 描述相对 current specs 的变化。

04
Superpowers · 小步实施与验证

按 OpenSpec tasks 执行 TDD/review/debug，再用 OPSX apply/verify + CI/E2E 检查实现与差量一致。

05
OpenSpec Archive + 运营闭环

只在上线证据成立后 archive，将 delta 合入 current specs；运营结果再生成下一项 change。

权威链：BMAD/现有批准文档管产品边界 → OpenSpec current specs 管当前行为 → 活跃 delta 管拟议变化 → tests/review/CI 管完成证据 → archive 更新事实源。
选择规则项目启动时产品与系统事实尚未建立，选架构 A；已经有生产事实并且本次工作可表达为“相对现状的语义差量”，选架构 B。若增量变更发展为用户、商业模式、核心范围或系统边界重构，先回到 BMAD Correct Course / PRD / Architecture，再决定继续 OpenSpec，还是作为新项目流进入 Spec Kit。

两条路线的边界与冲突消解

如何选择搭建方式

不要一开始就做“满配”。先选择强度档，再逐层加门禁。

A. 学习 / 小工具

1 人 · 1–15 stories · 风险低

组合：PM Skills 按需 + BMAD Quick Flow + OpenSpec 最小 change + Superpowers TDD。

保留：proposal/delta、测试、review、部署/回滚清单。

不做：完整 PRD、复杂架构评审、多 Agent 并行。

B. 产品型 DRI 标准版

推荐 · 个人主导 + AI Agent · 中等复杂度

新产品：BMAD 主干 + Spec Kit feature 契约 + Superpowers 实施 + PM Skills 运营。

已有产品：现有事实源/BMAD Correct Course + OpenSpec change + Superpowers；Matt 按缺口选装。

门禁：上层事实确认、analyze 或 validate/verify、测试/审查、ship-check、灰度与回滚。

C. 企业 / 高风险

多人 · 合规 · 多租户 · 高变更成本

组合：BMAD Enterprise + OpenSpec schema/stores，或 Spec Kit 组织 preset/bundle + 独立安全/QA/DevOps。

增加：威胁建模、数据分类、SLO、审批、审计证据、SBOM、灾备演练。

原则：先验证 beta/社区扩展；AI 生成建议，人类 DRI 对风险接受与上线负责。

我的明确建议先用 B 版完成一个真实小型 SaaS 或内部工具。跑通一次后再决定哪些工件过重、哪些门禁不足。不要先花数周“设计完美流程”却没有完成一次真实发布。

四周实战教程路线

用一个真实但可控的产品跑通全链路。建议项目：“小团队 AI 发布检查台”，可以上传项目清单、执行发布检查、生成证据包并跟踪结果。

第 1 周：问题与产品合同

目标：从原始想法得到可验证问题、假设实验、Brief 与 final PRD。

练习：PM Skills discover → BMAD product brief → PRD Create/Validate。

验收：非目标明确；至少 5 个关键假设；FR/NFR 可测试；没有 Agent 替你做未确认决策。

第 2 周：UX、架构与实施就绪

目标：打通“创建检查→查看风险→补证据→批准发布”的旅程。

练习：BMAD UX → Architecture → Epics/Stories → Readiness。

验收：关键异常态完整；租户与权限边界清楚；readiness 无阻断项。

第 3 周：Change 契约与 TDD

目标：交付一个纵向切片，例如“创建一次发布检查”。

练习：OpenSpec propose/apply/verify → Superpowers worktree/TDD/review。可在一次性练习分支用 Spec Kit 重做规格来比较，但生产流只保留一个引擎。

验收：至少一次真实 RED；API/页面可运行；验收标准逐项有证据；不存在只勾任务未实现。

第 4 周：上线、归档与学习闭环

目标：形成 release packet，灰度发布，把已验证 change 合入 current specs，并用数据做第一次迭代决策。

练习：ship-check → CI/E2E → migration/rollback drill → OpenSpec archive → metrics/cohort → retro。

验收：可回滚；告警有效；事实源已更新；指标口径固定；至少一个运营结论回流为变更信号。

教程要刻意记录失败每周保留一份“Agent 误判日志”：它为什么误判、哪条上下文缺失、哪个门禁应该更早发现。这比展示一条完美成功路径更能教会工程化。
10

质量治理与 DRI 控制面

AI 可以完成工作，但不能自证正确。质量来自可重复执行的外部检查。

完成定义（Definition of Done）

  • 需求有唯一来源和稳定 ID
  • 每个验收条件有测试或明确人工验证
  • 所有测试在当前提交上实际运行
  • 静态检查、类型检查、单测、集成/E2E 分层通过
  • 用户可见主路径经过真实浏览器/设备验证
  • 权限和租户隔离有负向测试
  • 数据迁移有备份、演练与失败恢复
  • 秘密不进入仓库、日志或 Agent 输出
  • 性能基线包含 P50/P95/P99 和容量假设
  • 上线前有可执行回滚步骤
  • 监控、日志、trace、告警覆盖关键故障
  • 变更说明与已知限制写清
  • spec、plan、tasks、code 没有阻断冲突
  • DRI 对残余风险明确接受或拒绝

Agent 权限分级

级别Agent 可自主执行必须人工确认证据
L0 只读搜索、分析、测试读取、报告任何写入来源与复现步骤
L1 工作区写分支内代码/文档/测试删除、覆盖、依赖大升级diff + tests
L2 集成开 PR、更新 issue、触发 CI合并主分支、对外通知review + CI
L3 发布执行已批准的可逆灰度生产迁移、全量切换、回滚豁免审批 + runbook + observation
L4 不可逆无删库、永久删除、财务、法律、代表 DRI 沟通双人确认/变更单

建议的最小 CI 门禁

概念性 pipeline，按技术栈替换命令
1. format-check + lint + typecheck
2. unit tests + coverage delta
3. integration tests with isolated database
4. contract/schema compatibility checks
5. dependency + secret + SAST scan
6. build reproducibility
7. E2E critical journeys
8. spec trace / acceptance evidence
9. migration dry-run

任何步骤失败：禁止 Agent 用“看起来已修复”覆盖红灯。
