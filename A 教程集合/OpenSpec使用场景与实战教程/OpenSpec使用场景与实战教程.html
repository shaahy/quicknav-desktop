01 · Mental model

一句话理解 OpenSpec

OpenSpec 是代码仓库里的轻量“变更协议层”：先对这次变化达成一致，再让 AI 或开发者写代码。

核心心智模型

openspec/specs/ 描述系统现在真实的行为。

openspec/changes/<change-name>/ 描述某一次准备发生的变化。

实现完成并归档后，变化折叠回主规格，成为新的系统事实。

它不是替代 PRD、测试或代码评审的万能文档工具。它解决的是一个更具体的问题：当产品需求、技术设计和 AI 实现分散在聊天记录里时，团队怎样给“一次变更”建立一个稳定、可审查、可追溯的事实边界。

先纠正一个常见误解

OpenSpec 不是“写完规格就能自动证明实现正确”。openspec validate 主要检查产物结构；verify 是 AI 辅助核对。真实测试、代码评审、迁移演练和产品验收仍然不可替代。

02 · Use cases

什么时候该用，什么时候不要用

OpenSpec 最自然的场景不是从零写一套百科全书，而是给已上线产品的下一次增量建立清晰边界。

GOOD FIT · 01

已上线项目的小步增量

新增字段、权限、筛选、状态流转、通知规则，或者修改超时、排序、兼容行为。每次只规格化当前切片。

GOOD FIT · 02

需求会在实现中校正

artifact 是普通 Markdown，可以在发现新事实后返回修订，不需要强行维持单向瀑布流程。

GOOD FIT · 03

需要变更级审计

每个 Change 独立保存 proposal、delta spec、design、tasks，归档后既有当前事实，也有历史决策。

GOOD FIT · 04

多个增量并行推进

每个 Change 独立评审、实现和归档；只要提前识别它们是否修改同一 domain spec。

这些情况先别急着用

情况为什么不合适更好的处理
问题仍完全开放直接 propose 会把猜测固化成貌似完整的方案。先用 explore 查代码、比较选项。
想一次补全整个旧系统成本高、很快过时，也与 brownfield-first 思路相反。只规格化当前准备修改的切片。
纯内部重构且外部行为不变复杂 delta spec 可能只会制造文档负担。用精简 design/tasks，明确“不改变的行为”。
团队需要强制治理但不愿定制默认工作流较轻，不会自动提供组织级门禁。先建立 schema、规则和评审责任人。
只想让 AI 快点写代码跳过评审会让 artifact 变成装饰品。小修可直接开发；重要增量才进入 OpenSpec。
新手判断口诀

如果这次改动会改变用户、运营人员、外部 API 或系统可观察到的行为，而且值得在写代码前确认边界，就适合建立一个 Change。

03 · Core objects

先认识五个核心对象

项目结构
openspec/
├─ specs/                         # 当前系统行为，source of truth
│  └─ tasks/
│     └─ spec.md
├─ changes/                       # 尚未完成的变更
│  └─ add-task-priority/
│     ├─ proposal.md              # 为什么改、改什么、边界是什么
│     ├─ design.md                # 技术方案和关键取舍
│     ├─ tasks.md                 # 实现与验证清单
│     └─ specs/
│        └─ tasks/
│           └─ spec.md            # 只描述本次变化的 delta
└─ config.yaml                    # 项目上下文与定制配置（可选）
proposal为什么做、范围和影响
delta specs行为将如何变化
design准备怎样实现
tasks按什么顺序执行和验证
对象回答的问题不应该承载
proposal.md为什么做、改什么、边界和影响是什么大量类名、函数名和逐行实现
Change specs用户或系统可观察行为如何变化纯内部实现细节
design.md怎么实现、有哪些技术取舍未经批准的新产品需求
tasks.md按什么顺序实现和验证“完成全部开发”这类模糊动作
Main specs系统当前已经承诺的真实行为尚未实现的愿望和路线图

Delta spec 通常使用四类动作：

  • ADDED：增加全新行为。
  • MODIFIED：替换已有要求，必须写出修改后的完整要求。
  • REMOVED：移除已有行为，说明影响和迁移。
  • RENAMED：只改变名称，不暗中改变语义。
04 · Setup

安装与初始化

先完成两个终端步骤，之后大部分工作都发生在 AI 助手的对话或 skill 中。

1. 检查运行环境

当前官方要求 Node.js 20.19.0 或更高版本。

PowerShell · 终端
node --version
npm --version

2. 安装 CLI

PowerShell · 终端
npm install -g @fission-ai/openspec@latest
openspec --version

团队项目建议记录实际版本，并先在测试项目验证升级结果；不要让同一仓库长期混用差异过大的全局版本。

3. 在真实项目里初始化

PowerShell · 终端
Set-Location E:\path\to\task-manager
git status --short
openspec init

openspec init 会创建 OpenSpec 目录，并按你选择的 AI 工具生成相应 skills 或命令文件。完成后先查看实际生成内容，再提交到版本库。

4. 升级后刷新项目指令

PowerShell · 终端
npm install -g @fission-ai/openspec@latest
openspec update
非交互初始化

脚本或 CI 场景可以使用 openspec init --tools codex --profile core。实际支持的 tool ID 和参数可能随版本变化，自动化前应以当前 openspec --help 为准。

05 · Command surfaces

命令究竟在哪里输入

这是新手最容易踩的坑：openspec ... 是 CLI；opsx 工作流由 AI 助手执行。不同 AI 工具的展示形式并不完全相同。

TERMINAL

在 PowerShell / Terminal 输入

openspec init、list、show、validate、view、update 等 CLI 命令。

AI ASSISTANT

在 AI 对话或 Skills 输入

propose、explore、apply、verify、archive 等让 AI 读写 artifact 和代码的工作流。

终端命令示例
openspec list
openspec show add-task-priority
openspec validate add-task-priority
openspec view
支持 slash command 的 AI 对话框
/opsx:explore
/opsx:propose add-task-priority
/opsx:apply add-task-priority
/opsx:archive add-task-priority

Codex 用户特别注意

OpenSpec 当前会为 Codex 生成项目级 skills，位置通常是：

Codex 项目目录
.codex/skills/
├─ openspec-explore/
├─ openspec-propose/
├─ openspec-apply-change/
├─ openspec-archive-change/
└─ ...

因此，在 Codex 中应从可用 skills 调用对应的 openspec-* 能力，具体名称以 openspec init 实际生成结果为准。不要看到其他工具使用 /opsx:propose，就假设 Codex 里也一定是同一种输入形式。

错误示范

直接在 PowerShell 输入 /opsx:propose，或者在 AI 对话框输入 openspec validate ... 并期待它像 CLI 一样运行。先判断这条命令属于“管理工具”还是“AI 工作流”。

06 · Profiles

两套工作流，新手先用 Core

模式典型路径适用情况代价
Core（推荐起步） explore → propose → apply → archive 单仓库、小到中型、目标较清晰的产品增量 propose 一次生成全部规划产物，需要你主动逐项评审
Expanded new → continue/ff → apply → verify → archive 复杂、高风险、多角色或希望逐个批准 artifact 命令更多，流程更长

默认全局 profile 是 core。要启用 expanded 命令：

PowerShell · 终端
openspec config profile
openspec update
选择规则

第一次使用：先用 Core 完成一个真实但可控的 Change。

高风险变更：使用 new + continue，逐个评审 artifact。

需求已经充分澄清：可用 new + ff 快速生成，但仍不能跳过人工审查。

07 · Case study

贯穿案例：任务优先级

我们不做玩具 Demo，而是在一个已经上线的单仓库任务管理系统里完成真实产品增量。

CHANGE · add-task-priority

产品目标

  • 成员可以给任务设置 P0–P3 优先级。
  • 任务列表默认按“优先级 → 截止时间 → 创建时间 → ID”稳定排序。
  • 旧任务默认迁移为 P2。
  • 管理员可关闭前端入口，但必须保留已经存储的 priority。
  • 旧 API 客户端不传 priority 时仍能正常工作。

明确不做

  • 不支持自定义优先级等级。
  • 不根据文本自动推断优先级。
  • 不做跨项目优先级模板。
  • 不顺手重构整个任务查询模块。

为什么这是一个合适的首个 Change

它同时覆盖数据模型、迁移、API、排序、前端和测试，足以展示 OpenSpec 的价值；但产品目标仍然单一，不需要跨仓库或跨季度规划。

08 · Baseline

第 0 步：建立真实基线

不要把项目原有失败误判成这次 Change 引入的回归。开始前先记录工作树、分支和质量基线。

PowerShell · 终端
git status --short
git switch -c feat/add-task-priority
npm ci
npm test
npm run build

记录以下证据：

  • 当前线上 tag 或 commit。
  • 安装、测试和构建的真实命令。
  • 已有失败项，以及它们是否与本次功能有关。
  • 本地数据库、环境变量或外部服务限制。
不要掩盖基线失败

如果测试本来就失败，把它记录为已知基线；不要为了得到全绿结果而随手修改无关测试，也不要在最后把旧失败算成本次 Change 已验证通过。

09 · Explore

第 1 步：先探索真实代码

explore 是无承诺的思考阶段。它可以读代码、比较方案、指出未知，但不应该创建 Change 或修改代码。

AI 对话 / OpenSpec Explore skill
我们准备在已上线任务管理系统增加 P0-P3 优先级，
并调整列表默认排序。

先不要创建 Change，也不要改代码。请读取：
- 任务数据模型与迁移规范；
- 创建、编辑和查询 API；
- 列表筛选、分页和排序；
- 项目功能开关；
- 相关单元、集成和端到端测试。

输出：
1. 当前真实行为；
2. 对应文件路径；
3. 受影响模块；
4. 未知问题；
5. 兼容、迁移和性能风险。

无法从代码确认的内容标记为“未知”，不得猜测。

Explore 结束时，你应该拿到什么

  • 现有任务表字段、约束、迁移约定和真实数据规模。
  • API 当前如何处理缺失字段和未知字段。
  • 默认排序、空截止时间和分页稳定性的实际实现。
  • 功能开关是只隐藏 UI，还是会阻止后端读写。
  • 可以复用的测试工具，以及当前缺口。
人工 Gate

只有当 Explore 对“系统现在怎样工作”的描述与代码和线上事实一致时，才进入 propose。仍有高风险未知，就继续调查或找负责人确认。

10 · Propose

第 2 步：建立 Change

AI 对话 / OpenSpec Propose skill
/opsx:propose add-task-priority

目标：
成员能设置 P0-P3 优先级，列表按优先级和截止时间稳定排序。

范围：
- 新建、编辑、展示和筛选 priority；
- 默认 P2，P0 最高、P3 最低；
- 排序为 priority 升序、due_at 升序、无 due_at 最后、
  created_at 升序、ID 最终稳定排序；
- 管理员关闭功能后，前端隐藏入口，但后端保留字段和值；
- 旧任务迁移为 P2，迁移可回滚；
- 兼容不传 priority 的旧 API 客户端。

不做：
自定义等级、自动推断、跨项目模板。

验收：
原有权限、分页、筛选和性能不得退化。

Core profile 下，预期一次生成：

openspec/changes/add-task-priority/
proposal.md
design.md
tasks.md
specs/
└─ tasks/
   └─ spec.md
生成完成不等于批准

propose 只是把初稿集中到可评审的位置。下一步不是马上 apply，而是逐项检查 proposal、delta specs、design 和 tasks。

11 · Artifact review

第 3 步：评审四类产物

OpenSpec 的质量主要发生在这里。AI 写得流畅不代表边界正确；你的任务是找出遗漏、冲突、偷换概念和无法验证的句子。

3.1 评审 proposal

  • Change 是否只有一个主要产品目标。
  • 用户价值、范围和不做什么是否清楚。
  • 是否明确迁移、兼容、回滚和风险。
  • 是否出现未经批准的“顺手重构”或新功能。
  • 影响面是否与 Explore 得到的真实代码一致。

3.2 评审 delta spec

specs/tasks/spec.md · 简化示例
# Delta for Tasks

## ADDED Requirements

### Requirement: Task priority
The system SHALL allow authorized users to assign P0, P1, P2, or P3
to a task.

#### Scenario: Default priority
- GIVEN an authorized user creates a task without specifying priority
- WHEN the task is saved
- THEN the task priority is P2

#### Scenario: Feature disabled
- GIVEN task priority is disabled for the project
- WHEN a user views or edits a task in the UI
- THEN priority controls are not displayed
- AND the stored priority value is preserved

## MODIFIED Requirements

### Requirement: Default task ordering
The system SHALL order tasks by priority ascending, due date ascending
with missing dates last, creation time ascending, then task ID.

#### Scenario: Stable tie-break
- GIVEN two tasks share the same priority and due date
- WHEN the task list is loaded
- THEN the earlier-created task appears first
- AND task ID resolves any remaining tie deterministically
MODIFIED 的高频错误

不要只写“默认排序增加 priority”。归档时 MODIFIED 可能替换原要求，因此它必须包含修改后的完整行为，包括空值、并列、稳定排序和权限边界。

3.3 评审 design

design.md 至少要回答：

  • priority 的存储类型、默认值、约束和序列化方式。
  • 旧数据迁移规模、锁表风险、发布顺序和回滚方式。
  • API 怎样兼容旧客户端。
  • 数据库和应用层怎样实现确定性排序。
  • 功能开关关闭后的读写行为。
  • 测试策略、监控信号、回滚触发条件。
  • 被否决方案及原因。

3.4 评审 tasks

tasks.md · 推荐顺序
## 1. Contract and tests
- [ ] 1.1 Add compatibility tests for missing and present priority
- [ ] 1.2 Add failing ordering and feature-flag scenarios

## 2. Data
- [ ] 2.1 Add priority column, constraint, and justified index
- [ ] 2.2 Add forward and rollback migrations
- [ ] 2.3 Verify existing rows become P2

## 3. Backend and frontend
- [ ] 3.1 Implement validation and serialization
- [ ] 3.2 Implement deterministic ordering
- [ ] 3.3 Add UI controls and disabled-state behavior

## 4. Verification and release
- [ ] 4.1 Run regression and performance checks
- [ ] 4.2 Rehearse migration and rollback
- [ ] 4.3 Update release and monitoring notes
可执行任务

一条好任务应当让执行者知道：改什么、如何证明完成、依赖什么。

“完成后端开发”“处理测试”“完善体验”都不是可验证任务。

12 · Validate

第 4 步：先检查结构，再写代码

PowerShell · 终端
openspec list
openspec show add-task-priority
openspec validate add-task-priority

validate 可以帮助发现 OpenSpec artifact 的结构和格式问题，例如缺失 Requirement、Scenario 或不合法的 delta 结构。但它不会判断：

  • 产品需求是否真的有价值。
  • 排序规则是否符合业务。
  • 迁移方案是否会锁表。
  • 测试是否真的覆盖边界。
  • 代码是否正确实现规格。
进入实现前的 Gate

proposal 范围已批准；scenario 可验证；design 基于真实代码；tasks 有顺序、有测试、有回滚；validate 通过。缺一项就先修 artifact。

13 · Apply

第 5 步：分批实现，不要黑箱执行

apply 会读取未完成 tasks、修改代码并勾选进度。对于真实产品增量，最安全的用法是明确分批和暂停点。

AI 对话 / OpenSpec Apply skill
/opsx:apply add-task-priority

分四批执行，并在每批完成后暂停：
1. 契约和失败测试；
2. 数据迁移与回滚；
3. 后端；
4. 前端、回归和发布准备。

每批报告：
- 修改文件；
- 已完成 tasks；
- 实际运行的测试命令与结果；
- 与 design 不一致的地方；
- 新发现的风险或未知。

未经确认不得扩大范围。

每一批你要检查什么

批次必须看到的证据不要接受
契约与测试新增失败测试，能描述旧客户端、排序和开关行为只写实现，没有先证明测试会失败
迁移前向/回滚脚本、现有行校验、锁表或耗时评估“迁移很简单，应该没问题”
后端校验、序列化、查询计划、稳定排序和兼容测试只在 UI 层实现 priority
前端与发布开关行为、空态、权限、回归、监控和回滚说明看到界面能点就宣告完成
复选框不是证据

tasks.md 被勾选只说明执行者认为任务完成。你仍需检查 diff、测试输出、迁移演练和关键产品行为。

14 · Change control

实现中发现新事实，怎么办

OpenSpec 允许返回修改 artifact，但“允许变化”不等于“任何变化都塞进同一个 Change”。

变化类型处理方式例子
同一目标，方案更好更新当前 Change枚举改为受约束小整数，产品行为不变
范围缩小更新当前 Change，剩余部分另建本期取消批量设置优先级
问题本身变了停止并新建 Change固定 P0–P3 变成可配置工作流系统
代码偏离已批准 design先判断正确事实，再对齐另一侧实现用了 Tailwind，而 design 写 CSS variables
更新现有 Change
/opsx:update add-task-priority

数据库不允许新增枚举类型，改为受约束的小整数；
产品行为保持不变。

请更新 design 和相关 tasks。
不要修改 proposal 与 delta spec 中未受影响的内容。
先展示各 artifact 将如何变化，逐项确认后再写入。

update 只应调整规划产物，不直接修改代码。更新后再次运行 apply，让实现重新对齐。

15 · Verification

第 6 步：用多层证据证明完成

第一层：项目自己的质量命令

PowerShell · 终端
npm test
npm run lint
npm run typecheck
npm run build
openspec validate add-task-priority

第二层：OpenSpec Verify

启用 expanded workflow 后，可以运行：

AI 对话 / OpenSpec Verify skill
/opsx:verify add-task-priority
COMPLETENESS

完整性

所有 tasks、requirements 和 scenarios 是否有实现或测试证据。

CORRECTNESS

正确性

代码是否符合规格意图、边界、错误路径和兼容要求。

COHERENCE

一致性

design 的关键决策是否真实反映到代码结构和实现方式。

HUMAN ACCEPTANCE

人工验收

真实用户路径、迁移、回滚、性能和运营观察是否满足上线标准。

Verify 不会阻止归档

官方工作流会报告 CRITICAL、WARNING 和 SUGGESTION，但 warning 不一定自动阻断 archive。团队应自行规定：CRITICAL 必须清零；WARNING 必须修复或记录明确豁免和责任人。

16 · Archive

第 7 步：同步当前事实并归档

大多数小型 Change：直接 archive

AI 对话 / OpenSpec Archive skill
/opsx:archive add-task-priority

归档会检查 artifact 和 task 完成情况，并在 delta 尚未同步时询问是否同步。确认后通常会：

  • 将 delta 合并到 openspec/specs/tasks/spec.md。
  • 把 Change 移入 openspec/changes/archive/YYYY-MM-DD-add-task-priority/。
  • 保留 proposal、design、tasks 和 delta，形成审计历史。

什么时候先单独 sync

AI 对话 / OpenSpec Sync skill
/opsx:sync add-task-priority
  • Change 周期很长，希望提前审查主规格合并结果。
  • 其他并行 Change 需要新的主规格作为基线。
  • 团队希望把“合并 specs”和“归档”拆成两次审查。
归档的真正含义

不是“文档处理完了”，而是声明：这次变化已经实现，主 specs 现在诚实描述系统当前行为。如果代码、数据或上线状态尚未到位，就不应为了清空列表而归档。

17 · Brownfield

已有 PRD 和旧项目怎么接入

官方对已有项目的核心建议很明确：不需要先记录整个代码库，只为现在准备修改的部分写规格。

  1. 把 PRD、架构文档和历史决策当作背景材料。
  2. 针对当前 Change，只引用相关章节。
  3. 用 explore 对照真实代码确认“现在怎样工作”。
  4. 只把本次改变写成可测试 delta。
  5. 实现并归档后，main specs 才增长为新的真实行为。
对照已有 PRD 的 Explore 提示
请读取 docs/PRD.md 的“任务优先级”章节，
并对照当前任务模型、API、列表查询和测试。

只分析本次准备实现的差异，
不要转换整份 PRD，不要改代码。

发现 PRD 与代码冲突时：
1. 先列出冲突；
2. 标明各自证据；
3. 等我确认哪一边代表当前事实。
PRD 不自动等于当前事实

旧 PRD 可能描述愿望、旧版本或已经变更的规则。main specs 也不能在未实现时提前写入愿望。产品事实冲突必须先报告，再由负责人确认。

18 · Parallel changes

单仓库里的并行 Change

每个 Change 有独立目录，很适合并行工作。但目录隔离不等于行为隔离。开始前至少检查：

  • 是否修改同一个 domain spec。
  • 是否修改同一数据表、API 契约或状态机。
  • 一个 Change 是否依赖另一个尚未归档的行为。
  • 归档顺序是否会让后一个 delta 覆盖前一个结果。
关系建议
完全独立可以并行，各自验证和归档。
修改同一 requirement明确先后顺序，后一个基于已合并的新事实重写 delta。
存在强依赖不要假装并行；先完成基础 Change，或把它们合并成一个单一目标。
多个 Change 都已完成Expanded profile 可考虑 bulk-archive，但仍要人工审查冲突解决结果。
19 · Failure modes

常见失败与处理

问题 1：把 AI 命令输进 PowerShell
/opsx:* 或相应 skill 在 AI 助手中运行；openspec * 在终端运行。Codex 还应优先查看生成的 .codex/skills/openspec-*。
问题 2：先为整个旧系统补全 specs
停止大规模回填。只为当前准备修改的切片创建 delta，让 main specs 随真实 Change 逐步生长。
问题 3：MODIFIED 只写一句差异
重写成修改后的完整 requirement 和 scenarios。它必须能在归档后替换原要求并独立成立。
问题 4：代码已经改了，artifact 没同步
判断哪一边代表已经批准的正确决定。如果代码正确，回写 delta/design/tasks；如果规格正确，继续修代码。归档前必须一致。
问题 5：同一个 Change 不断膨胀
同一目标的细化用 update；范围缩小则拆出后续 Change；问题本身改变则停止当前 Change 并重新 propose。
问题 6：tasks 全勾选就直接 archive
运行项目测试、构建、validate、关键人工验收；复杂或高风险 Change 再运行 verify。复选框不是完成证据。
问题 7：升级 CLI 后命令仍是旧版
在项目目录运行 openspec update，审查生成差异后提交，并重启或刷新 AI 工具的 skills/commands。
问题 8：Change 找不到或 artifact 被阻塞
先运行 openspec list 和 openspec status --change <name>，确认项目目录、Change 名称、schema 和依赖 artifact。

21 · Advanced appendix

Beta 进阶附录：跨仓库能力

BETA · 非新手主线

Stores 用独立规划仓库存放 OpenSpec 的 specs 和 changes，适合一个产品变更跨 API、Web 和共享库，或由平台团队统一拥有 requirements 的情况。

Coordination Workspace 是机器本地的多仓库视图，用于把多个 repo/folder 关联到一个工作区。官方 CLI 明确把这部分描述为仍在演进的 Beta。

什么时候再考虑它们

  • 一个产品目标必须同时落到三个以上仓库。
  • 需求由一个团队维护，却被多个代码仓库只读消费。
  • 规划需要早于代码仓库实施，且必须共享一个事实源。

什么时候不要升级复杂度

  • 第一个 Change 还没有完整跑通。
  • 当前功能全部在一个单体仓库内。
  • 团队尚未约定跨仓库 ownership、归档和冲突处理。
Beta 使用原则

命令、状态文件和 JSON 输出可能继续变化。不要把实验行为写死进长期自动化；使用前重新核对当前官方 Stores User Guide 和 CLI 文档。
