Production workflow · Not a prompt collection

把“让 AI 写代码”变成可验证的工程流程

Agent Skill 是给编码智能体执行的工作手册：它规定何时启动、按什么步骤推进、哪些借口不能接受，以及用什么证据才能宣布完成。

Mental model

先分清三层：何时、如何、由谁

很多混乱来自把 Command、Skill 和 Agent Persona 混为一谈。三层各司其职，组合起来才是一套可运行的系统。

L1 · WHEN

Command

用户入口，表达“现在要做哪类事”。它负责组合和激活所需技能。

例：/review
→
L2 · HOW

Skill

可执行工作流，包含步骤、质量门、反偷步规则和退出证据。

例：code-review-and-quality
→
L3 · WHO

Agent Persona

专家视角和报告格式，决定用谁的专业判断审视结果。

例：code-reviewer
Skill 不是参考文档。
它不是“读完就算”，而是智能体必须逐步执行、在 Gate 停下、拿出证据后才能退出的过程。
Skill 也不是越多越好。
一次塞入全部技能会浪费上下文。正确做法是按当前任务信号渐进加载。

Quick start

安装、发现、按需调用

最快方式是用开放的 skills CLI。也可以按具体智能体采用原生插件方式。安装命令需要网络，但本教程页面自身不需要。

terminal

任意智能体

Markdown 方式

把所需 SKILL.md 放入智能体支持的 skills、rules 或系统指令目录；在对话中明确要求遵循该工作流。

通用 · 无供应商锁定

Lifecycle

六阶段不是瀑布，是质量护栏

点击阶段查看输入、核心动作和退出证据。阶段可以往返，但不能用“先做了再说”跳过必要 Gate。

Entry points

8 个命令是入口，不是全部能力

命令替你组合 Skill。你只要表达当前意图，系统负责加载“怎么做”的工作流。

/spec

定义要构建什么，生成规格和成功标准。

原则：Spec before code
/plan

把规格拆成小型、可验证、按依赖排序的任务。

原则：Small, atomic tasks
/build

按垂直薄切片实施；与 TDD 组合，每步验证。

原则：One slice at a time
/build auto

一次批准计划后自动完成全部任务；失败或风险动作仍暂停。

自动化不等于取消验证
/test

用测试和运行时数据证明行为，不接受“看起来没问题”。

原则：Tests are proof
/review

合并前执行多维代码质量审查。

原则：Improve code health
/webperf

调用 Web 性能专家 Persona，测量 Core Web Vitals 等指标。

原则：Measure first
/code-simplify

保持行为不变，移除不必要复杂度。

原则：Clarity over cleverness
/ship

串起上线检查、风险评估、发布和回滚准备。

原则：Faster is safer

Skill anatomy

好的 Skill 会阻止智能体“合理化偷步”

真正有效的 Skill 同时告诉智能体：何时触发、如何执行、什么行为违规、拿出什么证据才算结束。

skills/example-skill/SKILL.md
---
name: example-skill
description: 做什么；何时使用
---
# Overview
说明结果和价值
## When to Use
正向触发 + 不适用情况
## Core Process
可执行步骤与 Gate
## Common Rationalizations
常见借口 + 事实反驳
## Red Flags
可观察的违规信号
## Verification
必须提交的证据
01

Process, not prose

写具体动作，不写“确保高质量”这类无法执行的口号。

02

Specific

触发条件、命令、产物和停点明确，智能体无需自行猜流程。

03

Anti-rationalization

提前列出“这个改动很小，不用测试”等借口，并给出事实反驳。

04

Evidence required

退出条件必须可观察：测试输出、构建结果、截图或运行时数据。

05

Progressive disclosure

SKILL.md 是入口；大型参考材料只在相关步骤需要时加载。

泛泛提示词

“请保证代码质量并做好测试。”

  • 没有测试范围
  • 没有失败时的处理
  • 没有完成证据
  • 智能体可以轻易宣布完成

可执行 Skill

“先写失败测试，再实现最小代码……”

  • 给出 Red → Green → Refactor 顺序
  • 失败即停线并定位根因
  • 输出具体测试命令和结果
  • 验收项逐条映射到证据

Adoption

落地顺序：先堵最大缺口，再扩展全链路

新项目可以从第一天采用完整生命周期；既有项目更适合验证优先的渐进引入。

路径 A · 新项目

从规格到发布全链路

  1. Define：规格和边界先于代码
  2. Plan：任务小型化并按依赖排序
  3. Build：薄切片 + TDD
  4. Review：质量、安全、性能 Gate
  5. Ship：灰度、监控、回滚

路径 B · 既有项目

验证优先，渐进采用

  1. 先接入 code-review-and-quality
  2. 补上 test-driven-development
  3. 新需求开始使用 spec-driven-development
  4. 稳定后扩展安全、性能和发布技能

六个常见偷步信号

“改动很小，不用规格”

小改动可以用两行验收标准，但不能没有完成定义。

“测试以后再补”

以后通常不会发生；没有失败测试，也无法证明测试能抓住问题。

“测试绿了，肯定没问题”

测试只证明覆盖到的内容；还需浏览器、边界和人工验收证据。

“先重构，顺便做功能”

混合意图扩大审查面；先保护行为，再拆分独立变更。

“直接加载全部 Skill”

会稀释注意力、浪费上下文；使用元技能按任务动态路由。

“能上线就算完成”

没有观测、灰度和回滚，上线只是把风险转移给用户。
