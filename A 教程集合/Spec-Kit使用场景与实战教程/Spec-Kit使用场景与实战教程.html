Spec-driven development field guide

先把“做什么”说清，再让 AI 写代码

一份面向产品负责人、技术负责人和开发者的 Spec Kit 使用场景与完整实战教程。从适用性判断开始，走完 specification、plan、tasks、implementation 与 convergence，并覆盖已上线项目的规格演进。

00

先做判断：这个需求要不要用 Spec Kit

规格流程不是免费午餐。先比较歧义成本与流程成本。

Spec Kit 最有价值的地方不是多生成几份 Markdown，而是在编码前把产品行为、技术方案、任务顺序和验证证据连接起来。需求越复杂、参与者越多、错误越难回滚，它越值得用。

场景建议为什么推荐路径
0→1 新产品或边界清晰的新模块强烈推荐把模糊产品意图变成可评审、可测试的行为契约完整流程
多角色、权限、状态、迁移、兼容性强烈推荐错误假设一旦进入代码，返工和线上风险都很高完整流程 + 人工 Gate
成熟系统里的中型增量功能推荐需要保护旧行为，并明确规格如何长期维护Brownfield + persistence model
单点、低风险、行为完全明确的修改按需完整流程可能重于修改本身短流程或团队轻量模板
线上事故正在止血不要先跑全流程恢复服务优先；稳定后再补规格和根因修复事故流程 → 事后规格化
团队不会评审产物，只想把它当长提示词不建议会制造“文档很全”的错觉，却没有真实约束先建立评审责任
适合

歧义成本高

默认值、边界、权限、异常路径、非功能目标尚未形成可验证表达。

适合

需要多人或多 Agent 交接

规格和任务成为共享事实源，减少口头上下文在交接时丢失。

不适合

没有验证环境

如果代码无法构建、测试或验收，规格也无法证明实现正确。

快速判断法

如果一个错误实现会影响数据、权限、兼容性、发布节奏，或者要让另一个人接手，就值得先规格化。如果修改十分钟内可完成、容易回滚、行为无歧义，用团队认可的轻量路径即可。

01

正确理解 Spec Kit

它是一套 SDD 工具包，不是替你做产品判断的“万能 skill”。

Spec Kit 把规格置于开发流程中心。核心链条是：产品意图形成 spec.md，技术选择形成 plan.md，工作拆分形成 tasks.md，实现和验证再回到这些承诺上收敛。

SPEC做什么、为什么、为谁
PLAN技术上怎么实现
TASKS依赖顺序与工作单元
IMPLEMENT按任务实现与验证
CONVERGE查找承诺与代码的缺口

核心产物与责任边界

产物回答的问题不应该包含什么主要评审者
constitution.md项目有哪些不可轻易突破的原则无法判定通过/失败的口号技术负责人、团队
spec.md用户要获得什么行为与结果框架、表名、类名等实现决定产品、业务、测试
plan.md现有系统如何实现这些行为没有代码证据的虚构架构工程、架构、安全
tasks.md按什么依赖顺序完成工作无来源任务、跨大范围的一条任务开发、测试、交付负责人
代码与测试实际实现是否兑现承诺未经批准的范围扩张开发、评审、产品验收

短流程与生产流程

小型功能

短流程

specify └─ plan └─ tasks └─ implement └─ converge

适合边界清楚、风险较低、团队已有成熟约束的小功能。短流程不等于跳过真实测试。

生产功能

完整流程

constitution └─ specify → clarify └─ plan → checklist └─ tasks → analyze └─ implement ⇄ converge

把澄清、需求质量检查和跨产物一致性分析作为编码前 Gate。

2026 年版本要点

Spec Kit 当前通过 .specify/feature.json 记录 active feature。核心流程不再依赖 Git 分支；Git 工作流由可选的 git extension 提供。切换 Git 分支本身不会切换 active feature。

02

安装与 Codex 初始化

本节使用 Windows PowerShell，固定到核对过的稳定版本。

官方支持从 GitHub release tag 或 PyPI 安装。团队环境优先固定版本，避免每个人在同一项目里使用不同模板和命令行为。

2.1 前置条件

  • Python 3.11+。
  • uv（推荐）或 pipx。
  • 受支持的 AI 编码 Agent；本教程使用 Codex。
  • 从 GitHub 源安装或启用 Git extension 时需要 Git；PyPI 核心使用路径可以不依赖 Git。
  • 目标项目本身可安装、构建和测试。

2.2 固定版本安装

uv tool install specify-cli --from git+https://github.com/github/spec-kit.git@v0.14.1
specify version
specify self check

specify version 验证当前命令和版本；specify self check 是只读更新检查。不要把“CLI 已升级”和“项目内模板已刷新”混为一件事。

2.3 初始化新项目

specify init task-manager --integration codex --script ps
Set-Location task-manager

Codex 当前是原生 skills 集成：技能安装到 .agents/skills，在对话中以 $speckit-<command> 形式调用。无需把 --integration-options="--skills" 当成 Codex 必填参数。

2.4 初始化现有项目

Set-Location E:\path\to\existing-project
specify init --here --integration codex --script ps

如果目录非空且 CLI 要求强制合并，先确保有可恢复的提交或备份，再执行：

specify init --here --force --integration codex --script ps
--force 是覆盖风险点

它可能刷新 Spec Kit 管理的命令、模板、脚本和共享 memory 文件。先保护 .specify/memory/constitution.md、.specify/templates/、.specify/scripts/ 的项目定制，再逐文件审查差异。specs/ 不属于模板包，但共享项目文件可能被覆盖。

2.5 你应该看到的结构

project/ ├─ .agents/ │ └─ skills/ │ ├─ speckit-specify/ │ ├─ speckit-plan/ │ ├─ speckit-tasks/ │ └─ ... ├─ .specify/ │ ├─ feature.json │ ├─ integration.json │ ├─ memory/ │ │ └─ constitution.md │ ├─ scripts/ │ │ └─ powershell/ │ └─ templates/ └─ specs/ # 执行 specify 后产生 feature 目录

2.6 终端命令与 Agent skill 不要混用

在哪里输入示例作用
PowerShellspecify init、specify version安装、初始化、管理工具和生态组件
Codex 对话框$speckit-specify、$speckit-plan驱动规格、计划、任务与实现工作流
其他 Agent 对话框/speckit.specify 等调用形式取决于集成；流程语义相同
03

完整工作流：每一步到底在控制什么

命令只是入口，评审 Gate 才是流程成立的条件。

顺序Codex skill核心结果人工 Gate
1$speckit-constitution项目治理原则原则是否可判定、可执行
2$speckit-specify用户故事、需求、成功标准WHAT/WHY 是否准确
3$speckit-clarify关键歧义被回答并回写产品决定是否明确
4$speckit-plan技术方案与设计产物是否基于真实代码与约束
5$speckit-checklist需求文本质量检查表是否明确、完整、一致、可测
6$speckit-tasks依赖有序的任务清单粒度、依赖、测试、回滚是否充分
7$speckit-analyze跨产物只读分析报告高优先级冲突是否归零
8$speckit-implement代码、测试和任务状态分批评审、阻止越界修改
9$speckit-converge把真实缺口追加为任务反复实现直至 converged
Checklist 不是测试执行表

checklist 检查的是需求与设计文本质量，类似“自然语言需求的单元测试”。真正的代码测试、构建、人工验收仍由项目工具执行。

三个不可替代的人类判断

产品判断

默认值、边界、失败状态、权限和范围取舍不能由 Agent 静默决定。

工程判断

迁移、兼容性、性能、架构和回滚必须基于真实代码与运行证据。

上线判断

Converged 不等于可发布。CI、验收、监控、发布和回滚准备仍要单独确认。

04

完整实战：给已上线任务系统增加优先级

一个功能走到底，包含产品边界、迁移、兼容、实现和验收。

案例范围

任务支持 P0、P1、P2、P3；默认按优先级和截止时间排序；旧任务迁移为 P2；管理员可关闭功能。此次不做自定义等级、跨项目模板和自动推断优先级。

0

建立可恢复的工作区

先知道项目在改动前是否健康。

git status --short
npm ci
npm test
npm run build

当前版本的核心 Spec Kit 不自动创建 Git 分支。如果团队需要分支工作流，先安装和配置 Git extension；否则按团队现有 Git 规范建立分支。

specify extension add git
# 或继续使用团队已有分支规范
git switch -c feat/task-priority
Gate：工作树状态已知；基线测试与构建结果已记录；失败项没有被误算成本次改动造成。
1

建立或复核 Constitution

把团队原则写成后续步骤必须遵守的约束。

$speckit-constitution
为本项目建立以下工程原则：
1. 数据库变化必须提供前向迁移、回滚和旧数据处理策略；
2. 对外 API 默认向后兼容，破坏性变化必须显式批准；
3. 每个用户故事必须有自动化测试，或说明不能自动化的原因；
4. 不允许顺手重构无关模块；
5. 上线前必须通过单元、集成、构建和关键路径验收；
6. 产品行为以已批准 spec.md 为准，技术发现改变行为时必须先回写规格。
Gate：每条原则都能回答“通过还是不通过”，而不是“保持高质量”一类口号。
2

创建 Feature Specification

只定义 WHAT/WHY 和可验证结果。

$speckit-specify
为已上线任务管理系统增加任务优先级。

目标用户：普通成员和项目管理员。
用户价值：成员能识别紧急任务，列表能稳定呈现执行顺序。

范围：
- 任务支持 P0、P1、P2、P3；
- 创建和编辑时可选择，默认 P2；
- 默认排序：优先级升序、截止时间升序、无截止时间最后；
- 管理员可按项目关闭；关闭后隐藏入口但保留历史数据；
- 旧任务迁移为 P2。

不做：自定义等级、跨项目模板、自动推断优先级。

成功标准：
- 新旧任务符合上述规则；
- 原有权限、分页、筛选和性能不退化；
- 数据迁移可回滚。

请只定义 WHAT/WHY 和可验证行为，不提前决定技术栈。

执行后检查 .specify/feature.json 指向的 feature 目录，而不是只看当前 Git 分支。目录通常类似：

specs/ └─ 00N-task-priority/ └─ spec.md
Gate：所有需求能转成测试；范围外内容没有混入；不存在未解决的 [NEEDS CLARIFICATION]。
3

澄清产品歧义

让 Agent 提问，不让它代替产品做决定。

$speckit-clarify
重点检查：
- P0 是否比 P1 更优先；
- 没有截止时间时如何排序；
- 关闭功能后 API 是否仍返回 priority；
- 恢复功能时历史值如何处理；
- 并列任务的稳定排序规则；
- 迁移失败时如何回滚。
不要自行猜测，请逐项提出需要产品决定的问题。

本案例决策：P0 最高、P3 最低；同优先级先按截止时间升序，无截止时间最后；截止时间相同按创建时间升序，再按任务 ID 稳定排序。关闭后 API 保留字段，前端隐藏；恢复后沿用历史值。

Gate：答案已回写 spec.md，不是只留在聊天记录里。
4

生成基于真实代码的技术计划

先读取现状，再决定怎么改。

$speckit-plan
沿用当前项目技术栈和既有架构，不新增框架。
先读取源码、迁移规范、任务 API、列表查询、权限、测试和项目功能开关。

计划必须包含：
- 实际受影响模块与依赖；
- 字段、默认值、索引、前向迁移、回滚和旧数据处理；
- API 兼容策略；
- 稳定排序实现；
- 功能开关的前后端行为；
- 单元、集成、端到端测试；
- 性能风险、观测指标、发布与回滚；
- 明确列出不修改的模块。

无法从代码确认的内容标记为未知，不得猜测文件路径或架构。
specs/00N-task-priority/ ├─ spec.md ├─ plan.md ├─ research.md ├─ data-model.md ├─ quickstart.md └─ contracts/
Gate：计划引用的文件和当前行为真实存在；迁移、兼容、性能和回滚路径经工程评审。
5

检查需求文本质量

发现“没说清楚”，不是证明代码已经正确。

$speckit-checklist
为任务优先级生成需求质量检查表，覆盖：
权限、稳定排序、空值、旧数据迁移、功能开关、
API 兼容、性能和回滚。
检查需求与设计文本质量，不是代码测试结果。
Gate：每个未通过项回到其事实源修正；不要在 checklist 里另造产品规则。
6

生成依赖有序的 Tasks

任务要小到一个 Agent 能可靠完成和验证。

$speckit-tasks
1. 契约与失败测试 T001 API 契约与兼容性测试 T002 默认值、排序和开关失败测试 2. 数据层 T003 priority 字段、约束与索引 T004 前向迁移和回滚迁移 T005 旧任务迁移为 P2 的验证 3. 服务端 T006 创建/更新校验 T007 稳定排序 T008 项目功能开关 4. 前端与发布验证 T009 选择器和列表标识 T010 关闭/恢复行为 T011 回归、性能、构建和迁移预演
Gate：没有前向依赖；实现、测试、迁移、回滚、发布验证都有任务；不存在“实现后端”这种过大任务。
7

实现前做跨产物分析

Analyze 是只读检查，问题要回到源文件修。

$speckit-analyze
  • Spec 有验收行为，Plan 却没有实现路径。
  • Plan 引入了 Spec 未批准的新 API 或行为。
  • Tasks 漏掉测试、迁移、回滚或发布验证。
  • Constitution 要求兼容，Plan 却设计了破坏性变更。
  • 同一个默认值在多个产物中不一致。
Gate：高优先级冲突归零后才能开始实现。
8

分批实现，而不是一次跑到底

大功能按检查点控制变更半径。

$speckit-implement
按 tasks.md 实现，但分四个检查点暂停：
1. 测试与契约；
2. 数据迁移；
3. 后端行为；
4. 前端与回归。

每个检查点完成后列出：
- 修改文件；
- 完成的 Task ID；
- 测试命令与结果；
- 尚未解决的问题。
等待确认后再继续，不得修改任务范围外代码。
npm test
npm run lint
npm run typecheck
npm run build
Gate：每批有可复现验证证据；失败没有被隐藏；越界改动被停止或单独立项。
9

Converge：让承诺与实现收敛

它会发现缺口并把剩余工作追加进 tasks。

$speckit-converge
对照当前 feature 的 spec.md、plan.md、tasks.md 与实际代码，
检查功能、测试、迁移、回滚、兼容性和非功能要求。
只把真实缺口追加为任务，不扩大范围。
$speckit-implement
$speckit-converge
# 重复，直到明确报告 converged
Gate：Converged 只表示规格与实现没有已识别缺口；仍需完成 CI、人工验收和发布准备。
10

人工验收与发布准备

用真实用户行为和运行证据结束流程。

  1. 新建任务默认 P2。
  2. P0–P3 展示、编辑和权限正确。
  3. 排序在分页、筛选和相同时间下保持稳定。
  4. 关闭功能后入口消失但数据保留；API 契约不被破坏。
  5. 恢复功能后历史值恢复显示。
  6. 旧任务迁移正确；失败可回滚。
  7. 旧客户端或既有 API 调用不受破坏。
  8. 监控指标、告警阈值、发布步骤和回滚步骤已准备。
05

已上线项目：规格如何长期演进

工具升级与 feature 规格演进是两条不同的维护环。

工具维护

刷新 Spec Kit 项目文件

涉及命令、脚本、模板和 shared memory。应在独立变更中执行，保护项目定制，并审查差异。

产品演进

维护 specs/ 产物

涉及项目真实行为、计划、任务和代码。只有产品意图或实现事实变化时才演进。

三种 Persistence Model

模型怎么做适合主要风险
Flow-forward每次重要变化创建新 feature 目录，旧目录保留上线系统、重审计与历史解释关联信息分散，需要交叉链接
Living spec先更新现有 spec，再同步 plan/tasks 并 analyze把规格视作长期产品契约重生成时可能丢失技术理由
Flow-back发现可落在 spec/plan/tasks/code 任一层，再统一对齐小团队、高探索性开发容易留下静默漂移
这不是 CLI 开关

三种模型是团队治理选择，应写入 Constitution 或 CONTRIBUTING.md。如果不规定，团队成员会在“新建 spec 还是改旧 spec”上产生不可追溯分歧。

Active feature 的新认知

  • Spec Kit 从 .specify/feature.json 识别当前 feature。
  • 可用 SPECIFY_FEATURE_DIRECTORY 环境变量覆盖。
  • 核心流程不要求 Git；Git extension 可以增加 feature branch 等能力。
  • git checkout 只切换代码分支，不保证切换 Spec Kit active feature。
# 只在当前 PowerShell 会话指定 feature
$env:SPECIFY_FEATURE_DIRECTORY = 'specs/012-task-priority'

# 用完后移除，避免误操作其他 feature
Remove-Item Env:SPECIFY_FEATURE_DIRECTORY
最危险的 Brownfield 错误

没有读取当前代码就让 Agent 生成 plan；或者技术发现改变了产品行为，却只改代码不回写 spec。前者会虚构架构，后者会让规格失去可信度。

06

Extensions、Presets、Bundles 与 Workflows

核心流程之外，Spec Kit 已经成为可组合的 SDD 工具生态。

组件解决什么问题典型使用边界
Extension增加新的命令、Hook 或集成能力Git、Bugfix、质量 Gate、外部工具增加能力，不是只换模板措辞
Preset覆盖核心或扩展模板合规格式、组织规范、术语本地化改变流程表达和约束，不引入新运行能力
Bundle把多个组件组成可安装角色栈开发者、产品经理、安全研究员套件是分发与组合层，不新增运行机制
Workflow把步骤、命令、Gate 编排成流程组织级 SDD 流程、并行或审批链要明确状态、失败和重试行为

先查看，再安装

# Extensions
specify extension search
specify extension info <name>
specify extension add <name>
specify extension list

# Presets
specify preset search
specify preset add <name>

# Bundles：info 展示的完整组件集合应与 install 一致
specify bundle search
specify bundle info <bundle-id>
specify bundle install <bundle-id>
specify bundle list
社区组件的信任边界

社区扩展、预设和 Bundle 由各自作者维护。安装前检查来源、版本、会写哪些文件、是否运行 Hook、是否访问外部系统；优先使用已验证来源，但“verified”也不替代组织自身审查。

覆盖优先级

高优先级 1. 项目本地 overrides .specify/templates/overrides/ 2. Presets .specify/presets/templates/ 3. Extensions .specify/extensions/templates/ 4. Spec Kit Core .specify/templates/ 低优先级

同名模板按优先级取第一个匹配项。删除高优先级组件后，下一层会重新生效。因此，遇到输出格式异常时，不要只看 core 模板，还要检查 override、preset 和 extension。

可选的 Task → Issue 交接

$speckit-taskstoissues 可以把生成的任务转成 GitHub Issues。执行前先审查任务粒度、标题、依赖和权限；创建外部 Issue 是对外写操作，不能把未批准的草稿直接发布。

07

常见失败模式与恢复办法

问题通常不在命令本身，而在事实源、依赖顺序和验证证据。

症状根因恢复动作
spec.md 出现框架、表名和文件路径WHAT/WHY 与 HOW 混在一起把实现决定移到 plan，保留可验证产品行为
Agent 根据一句需求直接改代码跳过规格链停止实现，补齐 specify → clarify → plan → tasks → analyze
Plan 引用不存在的模块未先读取代码列出真实入口、模型、API、权限、测试；未知项明确标记未知
Tasks 全勾选但功能仍缺失清单本身不完整运行 converge，同时执行真实测试与人工验收
切换 Git 分支后改错 feature误以为分支决定 active feature检查 .specify/feature.json 或环境变量
强制初始化后定制丢失未保护 shared files从版本控制恢复，独立执行 refresh，逐文件审查
重跑 plan/tasks 丢失人工理由把生成文件当临时产物先提交；把长期理由沉淀进 ADR、Constitution 或明确决策区
Converge 报告完成但上线仍失败把一致性检查当发布批准补 CI、迁移预演、人工验收、监控和回滚演练

三个高频控制提示词

在生成技术计划前，先定位本需求涉及的入口、数据模型、
API、权限、测试和配置。列出实际文件路径与当前行为；
无法从代码确认的内容标记为未知，不得猜测。
把发现的问题分为：
1. 本需求阻塞项；
2. 相关但可后置项；
3. 无关项。
只有阻塞项进入本次 plan/tasks，其余记录但不实施。
逐条建立 Requirement → Plan section → Task ID → Test → Code file 映射。
找出无任务的需求、无需求来源的任务、无测试的行为变化。

完成的定义

不是 tasks 全部勾选，也不是 Agent 说“已完成”。完成意味着：产品承诺、技术方案、任务、测试、代码和发布证据在同一个可审查链条里一致。
