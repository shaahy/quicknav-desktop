02

本质差异：三种方式在管什么

公平比较的前提是承认：直接对话是一种交互方式；Superpowers 是工程方法与技能集；OpenSpec 是规格驱动的变更生命周期。

事实边界：三者可以叠加，并非天然互斥；本页先按单独采用时的默认能力比较。
维度 直接对话 Superpowers OpenSpec
核心问题“我现在怎么让模型把这件事做完？”“怎样用可验证的工程纪律把它做对？”“这次到底改变什么，怎样形成可持续的事实？”
约束载体当前对话、Prompt、临时检查清单。技能规则、设计文档、实施计划、测试、审查与验证记录。Proposal、Delta Spec、Design、Tasks、Verify、主规格与 Archive。
默认工作单元一轮或一串对话。设计批准后的工程任务或 Bug 调试闭环。一个可独立提议、实施、验证、同步、归档的 Change。
主要事实源人脑 + 当前聊天上下文 + 仓库现状。批准的设计/计划 + 代码与测试证据。openspec/specs/ 当前事实 + openspec/changes/ 拟议变化。
对 Bug 的核心机制取决于你是否明确要求复现、根因、失败测试和回归。systematic-debugging 四阶段 + TDD + 完成前验证。用 Change 固化预期行为、影响范围和修复任务；根因方法需另补。
对功能的核心机制对话澄清后直接实现，或边实现边校正。Brainstorming → 隔离 → Plan → TDD → 双阶段审查 → 完成分支。Explore → Propose → Review → Apply → Verify → Sync/Archive。
长期记忆弱除非主动沉淀到仓库。中设计、计划、Git 与测试可保留实现上下文。强主规格和归档 Change 形成演进记录。
它不是什么不是自动存在的工程流程。不是产品规格数据库，也不是部署平台。不是测试框架、调试器、代码审查器或生产发布系统。
03

Bug 修复完整流程对比

以“用户保存后偶发丢失数据”为例。高质量 Bug 修复必须证明：症状被复现、根因被确认、修复能让失败测试变绿、旧行为未被破坏。

Bug 路线按工程阶段逐步比较。直接对话列展示“合格 Prompt 下的最佳实践”，不是默认自动行为。
阶段 / Gate 直接对话 Superpowers OpenSpec
0. 基线与止血 必须主动要求先看 Git 状态、测试基线、发布版本和回滚点；否则模型可能直接改。 先验证隔离环境与绿色基线。线上 P0 仍应先走事故止血，技能流程不能延误恢复。 严重事故先止血。较大永久修复再建立紧凑 Change，记录既有红灯与风险。
1. 稳定复现 提供错误文本、输入、频率、环境；要求只读调查并输出最小复现。 Phase 1：完整读取错误、稳定复现、检查近期变更与组件边界证据。 /opsx:explore 调查真实代码与行为；无承诺，不急于生成 Change。
2. 根因追踪 必须规定“没有根因证据，不准提出修复”；否则容易症状修补。 Phase 1–3：坏值逆向追踪 → 比较工作模式 → 单一可证伪假设。 Design 可记录根因与方案，但 OpenSpec 本身不强制采用特定根因方法。
3. 预期行为 在对话中写清 Given / When / Then 与不改变的旧行为。 将已确认预期变成失败测试和计划约束。 用 MODIFIED/ADDED Requirement + Scenario 固化外部可观察行为。
4. 失败测试 主动要求先写、运行、看到正确失败，再允许改生产代码。 强制 RED：测试必须因缺失行为失败，不是因环境、拼写或测试自身错误。 Tasks 可要求失败测试，但是否严格 RED–GREEN 取决于团队规则或组合 Superpowers。
5. 最小修复 限定一次只改一个假设；避免顺手重构和多个补丁混在一起。 GREEN：只修根因，让当前测试通过；之后才重构。 /opsx:apply 按 Tasks 实施；新事实出现时先更新 Change。
6. 回归与兼容 必须显式列出新测试、相关模块、全量测试和真实运行验证命令。 verification-before-completion 要求在当前状态重新运行证据命令并读取退出码。 项目测试 + 兼容/迁移验证 + /opsx:verify + 人工产品验收。
7. 审查 需要主动开独立审查上下文，避免实现者自审代替评审。 规格符合度审查后，再做代码质量审查；严重问题阻断。 审查代码、测试、Change 和 Delta 是否一致；规格审查不替代代码审查。
8. 闭环 人工记录原因、修改、验证、残余风险和回滚方式。 选择合并/PR/保留/丢弃分支；分支完成仍不是生产上线批准。 验证后 Sync/Archive，将已证实变化合并进当前规格并保留归档。
Bug 路线结论 小而清楚时快；质量高度依赖操作者纪律。 默认首选：对“找对根因并证明修复”约束最强。 适合行为契约变化或需审计的 Bug；复杂根因应补调试方法。
04

功能增量完整流程对比

以“给已完成的任务管理 MVP 增加标签”为例。真正风险不是把按钮写出来，而是范围、兼容、数据迁移、验收和长期事实是否一致。

功能路线从问题澄清到事实归档。生产发布所需灰度、监控和回滚是三种方式都要另行完成的外层闭环。
阶段 / Gate 直接对话 Superpowers OpenSpec
1. 澄清问题 通过多轮问答确认用户、痛点、成功标准、范围外与约束。 brainstorming 一次问一个问题，先理解现状，再给 2–3 个方案。 /opsx:explore 调查问题和代码，不建立实施承诺。
2. 设计方案 方案可能只存在对话里；需主动要求保存设计与决策理由。 分段展示设计并获得批准，形成设计文档；YAGNI 控制未证实范围。 Proposal 说明 Why/What/Impact，Design 说明实现方向、迁移、风险和回滚。
3. 行为规格 手工编写验收标准，容易漏掉修改和移除的既有行为。 设计和计划可以写行为，但不维护独立的主规格/Delta 生命周期。 ADDED / MODIFIED / REMOVED Delta 精确表达与当前规格的差异。
4. 人工批准 完全取决于 Prompt 是否设置“未经批准不写代码”。 设计批准后才写实施计划；计划批准后才执行。 四类产物互相一致、未知项解决、成功标准可验证后才 Apply。
5. 任务拆分 临时 Todo，颗粒度与证据要求依操作者能力。 writing-plans 拆成短任务，包含文件、代码方向与验证命令。 Tasks 绑定规格、实施顺序与完成证据；可在实现中持续更新。
6. 实现纪律 可要求 TDD，但模型容易在长对话中弱化约束。 RED–GREEN–REFACTOR；可按任务使用新上下文并做两阶段审查。 Apply 约束按计划实施，但 TDD、独立审查强度由工程制度决定。
7. 处理新事实 在聊天里改方向，若未同步文档，容易出现对话、代码、验收不一致。 重大偏差回到设计/计划 Gate；小偏差按计划更新。 先更新 Proposal/Spec/Design/Tasks，再继续 Apply，保留同一 Change 的一致性。
8. 验证与验收 需要主动建立规格映射表与全量验证清单。 任务测试、全量测试、代码审查和新鲜验证；外层补真实用户验收。 项目质量命令、兼容/迁移、规格一致性、人工产品验收四层证据。
9. 长期收口 人工更新 README、PRD、ADR 或 Issue，否则事实散落。 Git、设计、计划和测试留下实现历史，但产品事实需额外维护。 Sync 将 Delta 合入主规格，Archive 保留完整 Change 历史。
功能路线结论 只适合边界已明确的小功能；否则最容易边做边变。 工程质量强，适合设计已明确且需要可靠实现的增量。 行为变化、多人评审与长期演进的默认首选。

30 项全面对比矩阵

“强”表示该能力被原生流程显式要求；“可补”表示可以通过 Prompt、团队规则或组合方法实现，但不是默认保证。

能力矩阵不评价模型本身的编码水平，只评价流程是否系统性降低遗漏、漂移和伪完成。
对比维度 直接对话 Superpowers OpenSpec
01 启动速度5/5 几乎零准备。3/5 需加载技能、核查环境。3/5 需初始化并建立 Change。
02 学习门槛5/5 会描述问题即可开始。3/5 需理解技能触发与 Gate。3/5 需理解 Spec/Change/Delta/Archive。
03 流程灵活性5/5 随时改方向。4/5 可选 Bug/功能路线，但纪律严格。4/5 产物可迭代，但变化必须同步。
04 需求澄清可补 取决于提问质量。强 Brainstorming 显式要求。强 Explore/Proposal/Review。
05 范围边界弱 容易在长对话中漂移。强 批准设计、计划与 YAGNI。最强 Change 与 Delta 明确差异。
06 根因调查可补 需明确禁止猜修。最强 四阶段系统化调试。中 可记录，不强制方法。
07 TDD 强制力可补 容易先实现后补测。最强 必须看到正确 RED。可补 Tasks 可要求，但非核心机制。
08 回归保护中弱 依赖人工列全范围。强 测试与完成前验证。强 规格场景与 Verify 可映射回归。
09 代码审查可补 需另开独立审查。强 规格符合度 + 代码质量。可补 Change 审查不等于代码审查。
10 验证纪律中弱 易接受模型口头结论。最强 新鲜命令、退出码、失败数量。强 多层 Verify，但项目证据需配置。
11 行为规格弱 多为聊天文本。中 设计/计划承载。最强 Requirement + Scenario + Delta。
12 需求到代码追溯弱 需人工建表。强 计划任务 → 提交 → 审查。强 Change → Tasks → Verify → Archive。
13 长期产品事实弱 对话易失效。中 实现事实强，产品规格需另管。最强 主规格持续更新。
14 上下文恢复弱 依赖聊天历史与人工摘要。强 计划、Git、测试及进度记录。强 Change 目录即工作上下文。
15 多人协作弱 难共享隐含决策。中强 任务和审查清晰。最强 共享计划先于代码。
16 多 Agent 协作中弱 易上下文碎片化。强 任务隔离与阶段审查。中强 共享规格强，执行编排需宿主能力。
17 并行安全性低 接口和范围易冲突。中强 依赖拆分正确时可并行。中强 Change 边界清楚，但并行 Change 仍需冲突治理。
18 方案决策留痕弱 除非主动沉淀。强 设计文档包含方案与理由。强 Proposal/Design/Archive 保留。
19 变更中途校正快但易漂 改口即可。强 回到设计或计划 Gate。最强 先更新产物再继续 Apply。
20 文档维护成本5/5 最低，但债务后移。3/5 设计与计划有成本。2/5 产物最多，需持续维护。
21 小改吞吐5/5 快。3/5 有固定纪律。3/5 紧凑 Change 仍有启动成本。
22 中高风险返工控制2/5 易晚发现误解。4/5 设计、测试和审查前移。5/5 先对齐变化，再实现。
23 数据迁移表达可补 全靠 Prompt。强 可纳入设计与任务验证。强 Design/Tasks/Scenario 可系统表达。
24 接口兼容表达易漏中强 需加入设计附录。最强 修改行为与兼容场景可直接规格化。
25 审计与合规弱中 Git/测试/审查有证据。强 提议、批准、变更、归档链清晰。
26 紧急热修适配强 但要最小护栏。强 系统调试可压缩，不应省略根因。中 不应阻塞止血，事后补齐事实。
27 生产发布能力无内置无内置 分支完成不是上线批准。无内置 Archive 不是生产发布。
28 监控与灰度需另补需生产附录可写入 Design/Tasks，但需外部系统执行
29 回滚可逆性可补工程分支可控 生产回滚另管。变更与影响清晰 生产回滚另管。
30 最依赖的人类能力技术负责人持续掌控范围、测试和证据。批准设计/计划，并判断审查结论与生产风险。写对可观察行为、控制 Change 粒度并维护当前规格。

产物、仓库与维护成本

工件不是越多越好。关键是每份工件是否减少了误解、返工或交接成本。

“默认”指遵循各自标准流程时通常会产生；项目可按需要调整路径与模板。

任务计划临时 Todo。细粒度实施计划。tasks.md。

07

常见失败模式与修正动作

选型不是看宣传语，而是看团队最可能犯什么错，以及流程能否在错误发生前拦住它。

每种方式列出高频失败、用户后果和最低修正动作。
方式 典型失败 真实后果 最低修正动作
直接对话
  • 一看到错误就改代码
  • 多个修复一起试
  • 测试写在实现之后
  • 只跑新增测试
  • 相信模型“已完成”
 根因未修、复发、旧功能被破坏、问题无法解释、下次从头调查。 固定五步护栏：只读复现 → 根因证据 → 失败测试 → 单一最小修复 → 新鲜全量验证。
Superpowers
  • 小改跳过设计或调试
  • 机械执行过重计划
  • Reviewer 只看最后提交
  • 把分支完成当上线
  • 产品事实未同步
 流程看似完整，但规格边界或生产风险仍失控；长期文档与代码分离。 按风险压缩篇幅，不删除 Gate；审查完整 Diff；明确开发 Gate 与生产 Gate；必要时补 OpenSpec。
OpenSpec
  • Proposal 代替真实调查
  • Change 过大
  • 规格写得清楚但实现无 TDD
  • 代码变化后不更新 Delta
  • 未验证就 Archive
 产生“文档正确、代码错误”或“文档与现实双轨”的伪确定性。 未知先 Explore；一 Change 一闭环；Tasks 强绑定证据；高风险实现叠加系统调试、TDD 与独立审查。
08

按风险与场景选型

推荐不是二元开关。方式可以分层：OpenSpec 管“改什么”，Superpowers 管“怎样可靠实现”，直接对话只作为受控快车道。

默认推荐基于“已完成 MVP、需要保护既有行为”的前提。团队制度更成熟时，可调整权重。
场景 风险特征 首选方式 为什么 必须补充
文案、样式、明显拼写错误无数据/接口/权限影响；人工易验证。直接对话流程成本低，回退容易。Diff 检查 + 相关测试/构建。
单模块、稳定复现的 Bug影响有限，但需要防复发。Superpowers失败测试与最小根因修复更可靠。产品验收与回归范围。
偶发、跨组件、根因不清猜修概率高，复现成本高。Superpowers四阶段系统调试优先解决证据链。若行为契约变化，再补 OpenSpec Change。
线上 P0 故障恢复时间优先，错误成本极高。事故止血 → 系统调试先恢复服务，再完成永久根因闭环。回滚、监控、事故记录；较大永久修复补紧凑 Change。
纯局部小功能边界清晰，不改外部行为契约。Superpowers设计可短，但 TDD 与验证能保护基线。明确范围外与旧行为回归。
用户可见行为变化验收、帮助文档或流程发生变化。OpenSpecDelta 能精确说明增加、修改与移除。实现阶段补 TDD 与代码审查。
接口、数据、权限变化兼容、迁移、回滚和审计风险高。OpenSpec + Superpowers同时需要契约治理和可靠实现。Expand/contract、功能开关、灰度、监控。
多人或多 Agent 并行共享理解与集成冲突是主要风险。OpenSpec + 任务级审查先共享 Change 边界，再隔离执行。依赖图、接口冻结、跨任务集成测试。
一次性内部原型允许丢弃，不承诺长期维护。直接对话治理收益可能低于启动成本。明确“原型非生产”、合成数据和销毁边界。
五问决策规则：任一高风险答案为“是”，就向更强约束升级。
决策问题如果“否”如果“是”
根因是否不清楚？可继续评估直接对话。至少使用 Superpowers 系统化调试。
是否改变用户可观察行为？可能是纯内部修复。建立 OpenSpec Change 或等价行为契约。
是否涉及接口、数据、权限、迁移？保持当前等级。OpenSpec + Superpowers，并增加回滚设计。
是否需要多人、多 Agent 或跨版本协作？单一上下文可能足够。使用可共享、可评审、可归档的规格。
修错后果是否难以恢复？可采用轻流程。完整根因、TDD、独立审查、真实环境验证和发布 Gate。

专业建议：把“直接对话”限定为低风险快车道；把 Superpowers 设为 Bug 与实现质量的默认主线；当行为契约、数据、接口、权限或团队协作发生变化时，再引入 OpenSpec。高风险变化不是二选一，而是 OpenSpec 与 Superpowers 分层组合。

成本模型：别只看“开始写代码有多快”

总成本由启动、执行、返工、交接和长期维护共同组成。直接对话常把成本从前期治理转移到后期返工。

定性成本比较。具体时间取决于仓库规模、测试基础、变更风险和团队熟练度。
成本项 直接对话 Superpowers OpenSpec
首次接入极低：直接聊天。中：安装技能、理解工作流、测试与 Git 规范。中：安装初始化、建立配置、理解产物生命周期。
单次小改最低。中；短设计与验证仍有固定成本。中高；即使紧凑 Change 也需评审与归档。
中风险变更表面低，误解或回归会抬高总成本。中，测试和审查前置换取较少返工。中高，规格前置换取更低范围漂移。
高风险变更不可预测；返工和事故成本可能最高。可控，但需补行为契约与生产闭环。规格成本高，但与 Superpowers 组合后总体风险最低。
交接成本高：接手人需还原聊天和隐含判断。中低：计划、提交、测试与审查可读。低：当前事实和每次 Change 均可追溯。
长期治理前期低，文档债务随版本累积。中，工程事实持续积累。持续投入最高，但最适合多版本演进。
总成本公式
总成本=启动+实施+返工概率 × 返工损失+交接+长期维护

根因已确认

11

统一完成门槛

无论选哪种方式，都不能跳过这些结果条件。方法可以轻，证据不能虚。

Definition of Done：满足开发完成的最低证据；是否上线还需独立生产 Gate。
完成项 必须回答的问题 合格证据 禁止结论
Bug 根因为什么发生，而不只是哪里报错？稳定复现、数据流/调用链证据、被验证的单一假设。“看起来像”“可能是”之后直接改代码。
范围改什么、不改什么、影响谁？批准的范围、受影响组件和旧行为清单。边做边扩大且未重新批准。
测试测试是否能捕获缺失行为？正确 RED、修复后 GREEN、相关回归与全量测试。测试补写后直接通过就声称已覆盖。
代码审查实现是否符合意图，代码本身是否可靠？完整 Diff、规格符合度和代码质量两类结论。实现者一句“自查无误”。
新鲜验证当前最终状态真的通过吗？最终状态上的命令、退出码、通过/失败数量和时间。引用修改前或中间状态的旧绿灯。
兼容与迁移旧数据、旧客户端、旧配置会怎样？兼容矩阵、真实旧数据验证、迁移前后检查。只在空库和新用户路径测试。
人工验收用户目标是否达成，异常状态是否可恢复？按场景执行的产品验收记录。自动化测试通过即代表产品正确。
文档与规格当前事实是否与代码一致？需要时更新规格、帮助、运行手册、ADR 或 Change。留下旧文档让下次 Agent 读取错误事实。
回滚失败时如何恢复，数据是否可逆？明确回滚步骤、功能开关、迁移策略和恢复验证。“Git 可以回退”但数据库或外部副作用不可逆。
生产发布上线风险是否被独立批准？灰度计划、监控指标、阈值、告警、回滚演练与负责人。“测试绿了”“PR 合并了”“Change 归档了”所以可以上线。
