01

先把概念讲明白

Monorepo 描述的是仓库组织方式，不限定语言、框架或部署方式。

普通多仓库（Polyrepo）：网站、后台、组件库分别拥有自己的 Git 仓库，各自提交、发版和管理权限。

单体仓库（Monorepo）：这些项目放在同一个 Git 仓库中，但仍保留独立目录、依赖和发布方式。

多仓库三间分散的工作室，各有钥匙和规章。
↔
Monorepo一座共享园区，各团队有独立办公室，共用门禁和基础设施。
不要混淆：Monorepo ≠ MonolithMonorepo 是代码如何存放；Monolith 是系统如何运行和部署。仓库放在一起，服务仍然可以独立部署。
02

什么时候适合使用？

关键不是项目数量，而是项目之间是否需要频繁同步、共享代码和统一变更。

GOOD FIT

推荐使用

  • 前端、后台和共享组件经常联动修改
  • 多个应用复用同一套工具、类型或业务规则
  • 希望一次提交完成跨项目变更
  • 需要统一代码规范、测试与自动化流程
  • 同一团队维护一组关联产品
POOR FIT

谨慎使用

  • 项目完全独立，几乎没有共享代码
  • 不同团队必须严格隔离仓库权限
  • 仓库中有大量二进制素材或超大历史
  • 每个项目的合规边界完全不同
  • 只是为了“看起来更统一”而合并
判断问题如果回答“是”倾向
跨项目改动经常需要同时合并吗？Monorepo 能让一次提交保持原子性适合
多个应用共享内部包吗？本地依赖和版本同步会更简单适合
必须按仓库做严格访问隔离吗？单仓库授权通常不够细不适合
项目间完全没有关联吗？合并只会增加仓库复杂度不适合
03

一眼看懂目录结构

常见做法是把可运行项目放进 apps，把可复用模块放进 packages。

my-monorepo/ ├─ apps/ # 可独立运行或部署的应用 │ ├─ web/ # 网站 │ └─ admin/ # 管理后台 ├─ packages/ # 被应用复用的内部包 │ ├─ ui/ # 公共组件 │ └─ utils/ # 公共工具函数 ├─ package.json # 工作区入口与统一脚本 ├─ package-lock.json # 统一依赖锁定 ├─ .gitignore └─ README.md

三个核心规则

  1. 只有根目录存在一个 .git，子项目不再各自初始化 Git。
  2. 每个项目保留自己的 package.json，明确自己的依赖和命令。
  3. 共享包通过工作区名称引用，开发时直接连接本地代码，不必先发布到 npm。
04

标准工作流程

先建立边界，再连接依赖，最后统一验证。不要一开始就堆工具。

01

规划项目边界

列出哪些是独立应用，哪些是共享能力。应用进 apps/，共享模块进 packages/。

02

建立根工作区

根 package.json 声明 workspaces，并设置只在根目录执行的统一脚本。

03

连接内部依赖

应用通过包名依赖共享模块，让包管理器自动建立本地链接。

04

局部开发

只启动当前应用；修改共享包时，消费它的应用可以同步验证。

05

统一质量检查

在根目录运行测试、格式化和构建，避免某个子项目被遗漏。

06

一次提交完整变更

共享包和使用方放在同一提交中，评审者能看到完整影响链。

05

从零搭建一个 Monorepo

示例只使用 Node.js、Git 与原生 npm workspaces，不依赖 Turborepo、Nx 等额外工具。

实验目标：一句问候，两个项目协作

共享包 @demo/utils 提供问候函数，应用 @demo/web 调用它。

约 15 MIN
01

创建目录并初始化 Git

PowerShell
mkdir my-monorepo
cd my-monorepo
git init
mkdir apps, packages
mkdir apps/web, packages/utils

此时只在 my-monorepo 根目录初始化一次 Git。

02

声明根工作区

在根目录创建 package.json：

my-monorepo/package.json
{
  "name": "my-monorepo",
  "private": true,
  "workspaces": [
    "apps/*",
    "packages/*"
  ],
  "scripts": {
    "start": "npm run start --workspace=@demo/web",
    "check": "npm run check --workspaces --if-present"
  }
}
private: true 很重要它可以防止误把整个仓库发布到 npm。真正需要发布的内部包可在自己的配置中单独管理。
03

创建共享工具包

packages/utils/package.json
{
  "name": "@demo/utils",
  "version": "1.0.0",
  "type": "module",
  "exports": "./index.js",
  "scripts": {
    "check": "node --check index.js"
  }
}
packages/utils/index.js
export function greet(name) {
  return `你好，${name}！欢迎进入 Monorepo。`;
}
04

创建使用方应用

apps/web/package.json
{
  "name": "@demo/web",
  "version": "1.0.0",
  "type": "module",
  "scripts": {
    "start": "node index.js",
    "check": "node --check index.js"
  },
  "dependencies": {
    "@demo/utils": "1.0.0"
  }
}
apps/web/index.js
import { greet } from '@demo/utils';

console.log(greet('怡哥'));
05

安装并运行

PowerShell · 根目录执行
npm install
npm start

你好，怡哥！欢迎进入 Monorepo。

npm install 会识别两个 workspace，并让 @demo/web 连接本地的 @demo/utils。

06

统一检查并提交

PowerShell · 根目录执行
npm run check
git add .
git commit -m "feat: initialize npm workspaces monorepo"
完成标志：根目录有一个 Git 仓库；两个 workspace 能被识别；应用能直接调用本地共享包；统一检查通过。
06

日常开发怎么做？

Monorepo 的价值体现在跨项目改动仍然保持完整、可验证。

示例：给共享函数新增参数

  1. 从主分支创建功能分支：git switch -c feat/custom-greeting。
  2. 修改 packages/utils 的函数和检查。
  3. 同步修改 apps/web 的调用方式。
  4. 在根目录执行 npm run check，验证所有相关 workspace。
  5. 把共享包和应用改动放进同一个提交与评审。
提交边界比目录边界更重要一次业务变更涉及多个项目时，应在同一提交或同一合并请求中完整呈现，避免共享包先改、应用暂时坏掉。

常用的 workspace 定向命令

目的命令
只运行某个应用npm run start --workspace=@demo/web
给某个应用安装依赖npm install axios --workspace=@demo/web
所有工作区运行脚本npm run check --workspaces --if-present
查看工作区依赖npm ls --workspaces
07

已有项目如何迁移？

迁移重点不是“复制文件”，而是保留历史、消除嵌套仓库并验证路径变化。

假设你有教程文件夹 A（没有 Git）和工具项目 B（已有 Git 历史），目标是统一到仓库 C。

迁移前
A/  教程文件
B/  工具代码
└─ .git/  已有历史
→
迁移后
C/
├─ .git/       唯一仓库
├─ tutorials/  来自 A
└─ tool/       来自 B

推荐迁移思路

  1. 先备份并检查 A、B 的状态、敏感文件、大文件和硬编码路径。
  2. 以 B 的 Git 仓库作为 C 的历史基础。
  3. 把 B 的普通内容移动到 tool/，但根 .git 留在 C。
  4. 把 A 的内容复制到 tutorials/。
  5. 修正相对路径、脚本和 .gitignore，再进行运行验证。
  6. 检查 git status 的确切变更后再提交。
高风险操作必须先停下来确认移动、删除旧目录或推送远端都可能影响现有工作。先列出准确路径、改动范围、备份与回滚办法，再执行。
08

最常见的六个坑

多数问题不是工具造成的，而是边界、依赖和 Git 规则没有先说清。

×

把子项目的 .git 一起复制进来

会形成嵌套仓库，外层仓库可能只记录一个特殊引用。正确做法是整个 Monorepo 只保留根目录的一个 .git。

×

所有依赖都装在根目录

每个 workspace 应声明自己真正使用的依赖；根目录只放全仓库共用的开发工具和统一脚本。

×

共享代码通过相对路径乱穿

不要写 ../../../packages/utils。给共享包正式命名，再通过 workspace 依赖引用。

×

每次改动都构建所有项目

小仓库可以先简单执行；规模变大后，再引入受影响项目检测和任务缓存，避免过早复杂化。

×

忽略权限与责任边界

单仓库并不自动解决代码所有权。团队项目应配置 CODEOWNERS、评审规则与敏感目录保护。

×

仓库里塞入大量生成物

构建产物、缓存、密钥和依赖目录应写入 .gitignore；大型二进制文件需单独评估 Git LFS。

09

动手检查清单

勾选状态会保存在当前浏览器中。全部完成，说明你已经掌握最小闭环。

我的第一次 Monorepo

一分钟自测

把一个已有 .git 的项目复制进 Monorepo 子目录，最可能出现什么问题？

最后，只记住这四句话

  1. Monorepo 是多个关联项目共享一个 Git 仓库。
  2. 应用放 apps，共享能力放 packages，根目录只有一个 .git。
  3. 一次跨项目变更，要一起修改、一起验证、一起评审。
  4. 先用原生 workspace 跑通，再按规模引入更复杂的工具。
