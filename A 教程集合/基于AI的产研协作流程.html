🎨 产品设计阶段

需求澄清理解问题与边界产品设计

先明确本次需要解决什么问题

  1. 读取全量 PRD、相关决策与涉及模块代码，补充本次目标。
  2. 可以纯对话，也可以使用 grill-with-docs、wayfinder 或其他产品设计技能。
  3. 明确范围、行为、约束和验收标准。Wayfinder 处理大型、复杂或模糊需求时产出的地图 Issue 使用 type::map。
发布 Issue将需求转为正式规格status::triage

执行 to-spec，将完整 Spec 发布到 GitLab

  1. 发布完整规格，应用 type::spec 与 status::triage。
  2. 关联必要研究与正式材料，核对 Issue 正文、标签与链接。
  3. 发布成功不代表评审通过，也不表示已经授权开发。
原型与人工评估人工评估必做，原型按需triage → backlog

评估通过后，由人工修改 Issue 状态

  1. 涉及界面或关键交互时结合原型；无界面需求可以评估 Spec 与相关材料。
  2. 未通过：修改原型与 Issue，结论回写 Spec，保持 triage，再次评估。
  3. 通过：人工手动改为 backlog，评审评论按需；不予实施则 canceled 并关闭。
原型仅供人工评审，不作为开发输入或验收依据；影响开发的结论必须写入 Spec。

⚙ 开发阶段

读取 ISSUE 拆分任务读取已评估的 Specbacklog → in-progress

人员选择 backlog Spec，明确范围并拆分 Task

  1. 人员决定启动时机、拆分方式与授权范围，可只拆分或拆分并开发。
  2. 核对 Spec、负责人、依赖、资源与验收条件，保留执行依据快照。
  3. Task 关联父 Spec，写明交付、验收和依赖。条件齐备用 ready，正常等待用 backlog。
  4. 实际开始工作后改为 in-progress；仅拆分完成时父 Spec 回到 backlog，等待开发授权。

读取 Spec #42，授权拆分任务并开发；合并和发布分别等待人工批准。

完成 Task 开发按授权范围推进status::in-progress

按依赖实现任务，提交可验证的交付物

  1. 执行实现、测试和自查，保留结果与候选代码版本。
  2. 可串行或并行；并行需依赖满足、工作空间隔离、接口与文件责任明确。
  3. 整合任务结果，针对整合后的代码执行必要回归。
  4. 范围内正常修复自动推进；需求歧义、越权或异常阻塞交回人工处理。
独立审查Code Review审查节点

由实现者之外的 Agent 或人工检查代码

  1. 检查代码质量、潜在缺陷与回归风险，实现者自查不能代替独立审查。
  2. 未通过：返回 Task 开发修复，完成后重新审查。
  3. 代码有修改时重新运行受影响验证，不沿用已失效的通过结果。
需求审核逐条对照 Spec需求检查节点

验证实现是否满足已确认的需求

  1. 按当前已确认且获授权的 Spec，逐条标记通过、未通过或未验证，并提供证据。
  2. 检查正常、异常、边界与回归；界面和运行要求检查实际行为。
  3. 实现有误：返回 Task 修复并重新经过代码审查与需求审核。
  4. 需求发生实质变化：返回产品评估，更新 Spec 并重新获得执行授权。
整体人工验收人工检查最终交付status::review

交付与证据齐备后，由人工整体验收

  1. 检查整体交付物、需求审核结果、验证证据及 PRD 修改。
  2. 实现未通过：返回 Task 开发修复，重新走独立审查、需求审核和人工验收。
  3. 若需改变需求：返回产品评估；不得自行改验收标准。
  4. 验收通过后批准当前候选的 MR 合并。批准合并不等于批准发布。

🚀 合并与发布

MR 代码合并维护者执行合并合并后完成 Spec 收尾

人工批准后，将代码与 PRD 同步合并

  1. MR 关联 Spec／Task／bug 和验证结果，Spec 汇总任务与 MR。
  2. 改变产品行为时在同一 MR 更新 PRD；纯技术任务或恢复既定行为的修复不机械改写 PRD。
  3. 由项目维护者合并已获人工批准的候选；维护者可以是开发人员或 Agent。
  4. 整体交付验收通过、MR 合并且 PRD 同步后，Spec 标为 done 并关闭。
Task 关闭不等于 Spec 完成；MR 自动关闭不能绕过整体完成条件。
CI/CD 发布单独批准，再执行发布结果单独跟踪

MR 合并后，另行获得发布批准

  1. 合并完成后提交发布批准，未获批准不启动发布。
  2. 获批后执行项目 CI/CD，跟踪构建、部署与发布结果。
  3. 发布失败按项目修复或回滚流程处理；回滚同步检查 PRD，保留关联 Issue 与证据。
  4. 使用更新后的主分支与全量 PRD 开始下一轮产品迭代。

项目准备与产品基线
一次安装 · 每仓库初始化

把工作约定放进仓库

  1. 全局安装 Matt 技能，包含 setup-matt-pocock-skills 与 to-spec。
  2. 拉取主仓库，在仓库内运行初始化技能。
  3. 配置 GitLab 访问工具、Issue 标签映射与领域文档位置；若技能无 GitLab 选项，通过项目配置适配。
  4. 验证认证、仓库识别和必要权限；由维护者入库配置，主分支通过 MR 更新。
仓库里通常保存哪些规则？

docs/agents/issue-tracker.md 管理 Issue 操作；triage-labels.md 管理技能角色映射；domain.md 指引术语和决策文档。具体结构遵循项目约定，凭据不入库。

每轮设计之前

以已实现产品为起点

  1. 同步主分支，了解当前代码与仓库结构。
  2. 读取全量 docs/PRD.md，理解已验收、已合并的产品行为。
  3. 读取相关决策与涉及模块代码，补充本次设计目标。不要求读取全仓库全部源码。
没有全量 PRD 怎么办？

新项目：目标与规划先放 map／Spec，首批交付合并时建立 PRD。
旧项目：依据代码、文档与实际运行整理草稿，标注不确定项，经人工确认后入库。

PRD 是现有产品基线。未来计划保存在 map／Spec，不写成已经具备的能力。
Issue 标签、技能映射与角色职责
type::spec

需求规格

定义行为、范围、约束与验收标准。

type::task

实施任务

开发、重构、原型、测试或验收。

type::bug

缺陷修复

实际行为偏离已确认要求。

type::research

调研验证

交付证据、实验结论与决策建议。

type::map

Wayfinder 地图 Issue

Wayfinder 技能处理大型、复杂或模糊需求时产出的 Issue 类型。

status::triage

待评估

新发布的 Spec 必须从这里开始。

status::backlog

待安排

已接受，等待人员安排或正常前置依赖。

status::ready

可开始

内容、依赖、资源和授权齐备，尚未开工。

status::in-progress

进行中

已经认领并实际开始工作。

status::review

待评审 / 验收

完整交付与证据齐备，等待检查。

status::blocked

异常阻塞

需要介入解决，记录原因、解除条件和推动者。

status::done

已完成 · 关闭

达到对应 Issue 的完成条件，必要评审通过。

status::canceled

不再执行 · 关闭

取消、重复或被替代，不等于满足前置依赖。

没有匹配的标签，请尝试其他关键词或切换到“全部”。

更新时显式移除旧状态，不依赖自动互斥。只有 done、canceled 关闭，其他保持打开；负责人和执行方式写在负责人字段或正文。
Matt 默认分诊角色如何映射？

needs-triage → triage；needs-info → blocked；ready-for-agent → ready / backlog，按依赖、资源和授权判断；ready-for-human 按实际阶段选状态；wontfix → canceled。新 Spec 必须 triage 的规则优先。不再叠加 spec、Task、wayfinder:* 等旧标签。

👥 产品与决策

产品人员拉取仓库、本地分析与制作原型、管理需求 Issue；多人协作时禁止推送任何分支。
执行授权人选择 backlog Spec，决定时机、拆分方式和授权范围。
人工批准人评估交付与证据，验收并批准合并。

开发人员 / AI在授权分支实现、测试、修复，准备 MR 与 PRD 修改。

角色可以兼任，职责需区分。产品人员通过 Issue 附件或链接交接正式材料，由开发人员或维护者入库。

WHEN THINGS CHANGE

🧭 情景速查

合并主分支，是缺陷处理的分界

🧭 情景速查

创建 MR 不等于合并。新需求也不能按“功能遗漏”直接补做。

AFK 停止条件

这些情况，暂停相关工作

  • 影响实现的歧义，或必须改变已确认需求。
  • 缺少权限、资源或关键依赖，无法继续。
  • 超出授权的删除、数据迁移等高风险操作。
  • 同一问题连续修复 3 轮仍未通过。
保留现场，记录原因、解除条件和推动者。异常执行任务用 blocked，实质变更的 Spec 回到 triage；不受影响且已获授权的任务可继续。

恢复前确认解除条件与授权；需求变更需重新评估、安排和授权，并更新快照及验证依据。

合并前简单缺陷：当前分支修复，在原 task／MR 留痕；合并后缺陷：先建 bug Issue。复杂缺陷：diagnosing-bugs 诊断，建立或关联 bug 后修复。实质变更：Spec 返回 triage；独立新增需求：另建 Spec。文字澄清不改变行为时可直接更新。回滚：关联 bug 并同步检查 PRD，历史 Spec 保留交付记录。
