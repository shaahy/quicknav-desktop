01

30 秒认识 Ponytail

它是 Codex 的“反过度工程”约束：先复用、再用原生能力，最后才写最小可行代码。

一句话定位 Ponytail 让 Agent 在写代码前先问：能不能不做、复用现有代码、使用标准库或平台原生能力？都不行时，才写能工作的最小实现。
  1. 先判断是否真的要做不为猜测中的未来需求增加配置、抽象或扩展点。
    YAGNI
  2. 再查现有代码、标准库和平台原生能力能复用就不重写，能原生完成就不新增依赖。
    优先复用
  3. 最后写最小可靠实现改在根因位置，保留必要校验、安全边界和最小验证。
    正确且小

懒在方案

  • 删除优先于新增。
  • 标准库优先于自定义。
  • 根因修复优先于入口补丁。
  • 一个最小检查优先于空口保证。

不能懒的地方

  • 理解需求与真实调用链。
  • 信任边界输入校验。
  • 防数据丢失的错误处理。
  • 安全、可访问性和硬件校准。
02

在 Codex 桌面端怎么用

前提：Ponytail 插件已经安装，并在安装后重新启动过 Codex 桌面端。本教程不负责联网安装。

1. 打开任务

在 Codex 桌面端打开目标项目，创建或进入一个编码任务。

2. 输入技能

在输入框键入 @ponytail full，发送后继续描述开发任务。

3. 核对结果

检查变更、运行验证，再用 @ponytail-review 查是否写多。

第一次使用：直接复制到 Codex 输入框
@ponytail full

读取当前项目后完成这个任务：
[写明必须实现的功能]

约束：不新增依赖；优先复用现有代码；保留错误处理和验证。
完成后说明：修改了什么、运行了什么验证、哪些内容有意没有增加。

模式怎么选

模式行为适用阶段风险
LITE先按要求做，再提示更轻方案。刚开始试用、强约束任务。约束较弱。
FULL完整执行最小实现纪律，默认推荐。日常功能、修 Bug、重构。需求必须先明确。
ULTRA主动删减范围和抽象。一次性脚本、允许砍范围的原型。可能挑战既有方案。
OFF退出 Ponytail 持续模式。非编码或架构探索。不再自动约束过度工程。

04

六项技能速查

每张卡只回答四件事：给什么、得到什么、什么时候用、在 Codex 桌面端输入什么。

ponytail

持续模式：让当前编码任务采用最小可靠实现。

实现前 → 实现中
输入

明确需求、相关代码、调用链、现有依赖、不可删约束；可选参数 lite | full | ultra。

输出

代码优先；最多三行说明跳过了什么、什么条件下再增加。复杂逻辑附一个最小可运行检查。

适用阶段

需求已经明确后的实现前与实现中；日常功能、Bug 修复和小型重构优先使用 Full。

Codex 桌面端示例

@ponytail full
“读取现有导出逻辑，增加 CSV 导出；不要新增依赖，保留字段转义和现有测试。”

ponytail-review

一次性报告：只审当前 Diff 中的过度工程。

实现后 → 提交前
输入

当前未提交 Diff 或明确的变更范围；最好同时提供任务验收标准，避免把必需代码误判为多余。

输出

逐行发现：delete、stdlib、native、yagni、shrink，结尾给出可能减少的行数。

适用阶段

实现与验证完成后、提交前；也适合检查一段 AI 生成的当前 Diff。

Codex 桌面端示例

@ponytail-review
“只审当前 Diff 是否过度工程；只报告，不修改，也不要审正确性、安全或性能。”

ponytail-audit

一次性报告：扫描整个仓库的过度工程。

专项治理 / 迭代间隙
输入

完整代码树、依赖清单和项目边界；应排除构建产物、第三方目录和生成代码。

输出

按可削减量排序的清单：删什么、用什么替代、路径在哪里；结尾估算可减少行数和依赖数。

适用阶段

迭代间隙、重构立项前或旧仓库治理时；不适合在紧急修复中扩大范围。

Codex 桌面端示例

@ponytail-audit
“扫描仓库的单实现接口、代理包装层、死配置和重复标准库能力；只报告，不修改。”

ponytail-debt

一次性报告：收集有意识的简化与升级触发条件。

迭代末 / 发布前
输入

代码库中的 # ponytail: 或 // ponytail: 注释。约定内容应写明能力上限和升级触发条件。

输出

按文件分组的债务台账：位置、简化内容、上限、升级条件；缺少触发条件的项标记 no-trigger。

适用阶段

迭代末、发布前或技术债盘点时；前提是代码中已经存在带触发条件的 ponytail: 注释。

Codex 桌面端示例

@ponytail-debt
“汇总项目中的 ponytail 注释；标出没有升级触发条件的项，不要写文件。”

ponytail-gain

一次性卡片：展示项目发布的基准数据。

评估 / 分享
输入

无需仓库输入；直接调用。它不会分析当前项目。

输出

ASCII 记分牌，展示代码、成本和速度的发布基准；不改变模式、不写文件。

适用阶段

团队介绍、工具评估或演示时；不参与当前项目的实现与审查。

Codex 桌面端示例

@ponytail-gain
直接发送即可。它展示发布基准，不会测量当前仓库的真实收益。

ponytail-help

一次性卡片：查询模式、技能、配置和停用方法。

任何阶段
输入

无需上下文；直接调用或询问“Ponytail 有哪些命令”。

输出

模式表、六项技能列表、停用方式和默认模式配置位置。

适用阶段

任何阶段；忘记模式、技能名称、配置位置或退出方式时使用。

Codex 桌面端示例

@ponytail-help
直接发送即可。它只显示帮助；退出持续模式可输入 stop ponytail。

统一边界review 与 audit 只审“是否写多”，不审正确性、安全和性能；所有只读技能都不会自动修改代码。安全校验、防数据丢失处理和用户明确要求不能为了少代码而删除。
05

Codex 桌面端完整实战

示例任务：在现有本地 Todo 项目中增加 CSV 导出。重点不是抄代码，而是走完一次可复用的 Codex 操作链。

先写清验收导出的 CSV 包含任务名和到期日；逗号、双引号与换行不会破坏列结构；不新增依赖；保留现有校验和测试。
01

开启 Full 模式并提交任务

粘贴到 Codex 输入框
@ponytail full

读取当前 Todo 项目，实现 CSV 导出：
1. 导出任务名和到期日；
2. 正确处理逗号、双引号和换行；
3. 不新增依赖，优先复用现有逻辑；
4. 保留现有校验，并运行相关测试。

完成后告诉我：改了什么、验证结果、哪些未来能力有意没做。

你应该看到：Codex 先检查现有实现和依赖，再做局部修改，而不是先安装 CSV 库或建立新架构。

02

检查改动证据

在 Codex 的变更视图中确认：修改集中在真实导出位置；没有无关文件、额外依赖或为未来需求准备的接口；CSV 边界处理没有被省略。

证据不足时继续输入
先不要继续扩展。请列出本次实际修改的文件、运行过的验证命令及结果，并说明为什么没有新增依赖。

进入下一步的条件：能看到具体文件和真实验证结果，而不是只有“应该可以”。

03

用 Ponytail Review 查“是否写多了”

粘贴到 Codex 输入框
@ponytail-review

只审查当前 Diff 是否过度工程。
只列问题，不要修改；不要审正确性、安全或性能。
验收要求中的 CSV 转义、现有校验和测试不能当作多余代码删除。

你应该看到：逐项精简建议，或 Lean already. Ship.。这不是质量验收结论。

04

单独做正常代码审查

新的 Codex 提示词
现在进行正常代码审查，只报告，不修改。
检查：验收标准、CSV 转义正确性、错误处理、安全、回归风险和测试覆盖。
不要因为 Ponytail Review 判定精简就省略这些检查。

你应该看到：基于正确性和风险的独立发现。它与“是否写多了”是两份不同报告。

05

记录明确接受的能力上限

假设当前只支持少量本地任务，服务端大数据导出不在本次范围。让 Codex 添加带升级触发条件的注释：

债务标记示例
请只在真实限制附近添加一条注释：
// ponytail: 当前仅导出已加载任务；需要导出全部服务端数据时升级为分页流式导出

不要创建债务文件，也不要实现未来方案。

好的债务说明同时包含“当前上限”和“何时升级”，而不是模糊的 TODO。

06

生成债务台账并人工验收

最后一次调用
@ponytail-debt

汇总当前项目的 ponytail 注释；标记缺少升级触发条件的项。只报告，不写文件。

最后由人按验收条件实际导出边界数据。测试变绿、Review 显示 Lean，都不能替代人工验收。

06

边界与常见误区

Ponytail 的目标是减少没有当前价值的维护面，不是机械追求最少行数。

不要用它决定需求

已确认的 SPEC、兼容性和合规约束不能被“更少代码”推翻。

不要把 Review 当完整审查

review 和 audit 不负责正确性、安全、性能与发布审批。

不要为了短而删验证

边界处理、信任边界校验、防数据丢失和最小测试不是样板代码。

不要默认使用 Ultra

日常任务选 Full；只有明确允许主动砍范围时才使用 Ultra。

关于 gain@ponytail-gain 展示的是项目发布基准，不会测量当前仓库。没有自己的对照实验，不要宣称实际节省了多少代码或成本。
