Decision-first field guide

先决定谁掌舵，
再安装技能。

这不是 README 的中文翻译，而是一份采用决策手册：解释安装范围，找出 Matt Pocock Skills 与现有 gstack、Superpowers 的真实冲突，再给出可执行的最小试用路线。

一句话结论 技能本体可以用户级安装后跨项目复用，但 setup-matt-pocock-skills 是每仓库配置；当前环境不建议一次启用整套，尤其不要让两套同阶段编排器同时自动触发。

01 / INSTALL

是不是每个项目都要安装一次？

把“下载技能”“让 Codex 看见技能”“为当前仓库配置技能”拆开，答案就清楚了。

L1

技能本体

通过 skills.sh 复制到项目时，项目各有一份；若安装器选择 Codex 用户级目录，则可以跨项目共用。

不一定每项目重复下载
L2

Agent 可见范围

项目级安装便于定制与版本固定；用户级安装便于统一更新，但会让更多项目看到模型调用型技能。

作用域是关键选择
L3

仓库配置

/setup-matt-pocock-skills 会配置 Tracker、Triage 标签和领域文档布局，官方要求首次使用工程流前按仓库运行。

每仓库一次
当前建议：先不安装。若试用，优先在一个隔离项目中只选 3–4 个独有价值技能；不要先把 9 个模型调用型技能全部放进用户级作用域。
02 / POSITION

三套体系解决的不是同一个问题

重叠来自“都能完成开发”，区别来自它们如何组织决策、执行和交付。

mattpocock/skills

可组合的工程纪律

  • 以 grilling、领域语言和深模块设计为底层词汇。
  • 围绕 Tracker 组织 Spec、Tickets、实现与审查。
  • 用户编排器与模型纪律拆分清晰。

最强项：领域建模、纵向切片、双轴审查。

gstack

端到端工程与交付工具箱

  • 覆盖规划、设计、QA、审查、发布、部署与监控。
  • 带浏览器、设计、报告和发布能力。
  • 更像完整工作台而非一条开发方法。

最强项：从计划到发布的完整闭环。

superpowers

强制过程门禁

  • 创作前 brainstorming、编码前计划、实现时 TDD。
  • 强调工作树隔离、验证证据和阶段确认。
  • 通过硬门禁降低代理跳步概率。

最强项：用强规则保证过程纪律。

03 / CONFLICTS

冲突不是报错，而是流程失去唯一指挥

大多数技能不会发生文件名级覆盖。真正的风险是同一阶段出现两个“必须先做 X”的编排器。

冲突类型典型组合用户看到的后果风险解决规则
自动触发竞争tdd vs Superpowers TDD重复确认 seam、重复执行红绿循环，代理不知道谁的完成标准优先。高同一阶段只保留一个模型可调用技能。
硬门禁叠加grilling vs brainstorming一轮需求可能经历两次访谈、两份设计说明和多次确认。高需求澄清入口三选一。
编排嵌套implement + executing-plans + gstack ship实现、测试、审查与提交被重复编排，链路变长且难以恢复。高一个任务只允许一个实现编排器。
产物双轨CONTEXT.md、ADR、Spec、gstack artifacts同一决策写进多个位置，之后互相矛盾，代理无法判断谁是事实源。中预先指定唯一主 PRD、词汇表和决策记录位置。
审查重复code-review vs gstack review vs requesting-code-review相同 diff 被多次审查，基线和严重度口径可能不同。高固定一个审查器，并写清 fixed point 与 Spec 来源。
Git 收尾冲突implement、worktree、ship重复 Commit、不同分支策略或在未确认时完成 merge/rebase。中只有一个技能拥有提交与交付权限。
上下文膨胀多个模型调用型长 Skill每轮任务携带更多触发说明，注意力被流程规则分散。中用户级作用域只放高频且不冲突的模型技能。

05 / FIELD LAB

同一个需求，三套体系怎么走

案例不是让三套全跑一遍，而是用同一问题看清每一阶段谁应该拥有控制权。

Scenario

给现有 SaaS 增加“团队邀请”功能

管理员通过邮件邀请成员；邀请有有效期、可撤销、不可重复接受；需要邮件、权限、状态和审计记录。

推荐混合原则

允许不同阶段选不同体系，但每个阶段只选一个主技能。上一阶段的产物成为下一阶段唯一输入，不嵌套另一个同类编排器。

07 / OPERATING RULES

让三套体系和平共存的 6 条规则

关键不是记住所有 Skill，而是为每个控制层指定唯一责任人。

每阶段唯一主流程

澄清、规格、实现、测试、审查、交付，每一阶段只能有一个编排器拥有“下一步怎么走”的决定权。

事实源只有一份

主 PRD、领域词汇表、ADR 和交付计划分别指定唯一位置；其他页面只引用，不复制改写。

显式调用优先

试用期先安装用户调用型技能。模型调用型技能只有在没有同类触发器时才放进用户级作用域。

编排器不调用编排器

不要用 Matt implement 再套 Superpowers executing-plans，也不要让两者最后都调用审查和提交。

写权限只给一个收尾器

Issue 状态、Commit、Merge、Deploy 都属于外部状态变化；每次任务明确谁能写，其他技能只报告。

先做一个试验仓库

记录触发次数、重复步骤、产物位置和真实收益，再决定是否扩展到用户级安装。
