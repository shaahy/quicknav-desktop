四种组合开发流程对比矩阵

核心变量：BMAD交付PRD时，下游先拆出全量Task，可批量并行；BMAD交付正式Story时，按“出一个、开发一个”推进，跨Story整体串行。

并行 / 高吞吐 串行 / 高聚焦 较高风险
精简为10项。并行效率与质量风险采用怡哥的项目实战观察；具体结果仍受Task依赖、Agent能力、测试策略和集成Gate影响。
对比项 组合 1 BMAD PRD → Spec Kit → Superpowers 产品事实 → 全量规格/Task → 并行TDD 组合 2 BMAD完整流程 产品 → 架构 → Epic → Story → 开发 组合 3 BMAD Story → Superpowers 完整规划 → 逐Story → Story内TDD 组合 4 BMAD PRD → Superpowers 产品事实 → 全量Task → 并行TDD
1. 正式流程链路 三段式专业分层最细BMAD定产品，Spec Kit形成完整Feature规格与Task，Superpowers负责TDD实现。 单框架BMAD全生命周期PRD、UX、架构、Epic、Sprint、Story、开发与评审在同一体系内推进。 双框架BMAD规划，SP执行BMAD一直负责到正式Story；每个Story再交给Superpowers实施与验证。 双框架产品后直接工程化BMAD完成产品和UX，Superpowers一次性规划全量工程任务并实施。
2. BMAD交付边界 PRD级交付产品事实主要交付PRD、DESIGN、EXPERIENCE；Feature规格和任务拆分由Spec Kit补齐。 Story级交付聚焦实施上下文BMAD完成架构、Epic/Sprint，并逐个创建可开发Story。 Story级交付正式StoryStory携带AC、依赖和必要架构/UX上下文，是Superpowers的范围事实源。 PRD级交付产品事实主要交付PRD、DESIGN、EXPERIENCE；工程设计与任务拆分全部交给Superpowers。
3. 架构与实施规划 Spec Kit主导Feature计划较完整constitution、clarify、plan、tasks可以形成完整Feature包；系统级架构仍需明确补充。 BMAD主导全局规划最完整Architecture、Epics、Readiness、Sprint和Story共同保证依赖顺序与技术一致性。 BMAD主导全局计划完整BMAD控制架构与Story边界；Superpowers只把当前Story细化为工程步骤。 Superpowers主导工程计划强、全局产品规划薄可生成清晰实施计划，但缺少正式Epic、Readiness和Sprint依赖视图。
4. 全量Task可见性 全量可见先拆完整Task集合Spec Kit从PRD/Feature规格生成全量Task，便于提前识别可并行项和依赖项。 Story逐步展开列表可见，细节逐Story生成Epic中可看到Story规划，但正式开发上下文按“创建一个Story、完成一个Story”展开。 Story逐步展开当前只工程化一个Story全局Story队列存在，但Superpowers拿到的是当前正式Story，不是全量Story的完整Task集合。 全量可见PRD一次拆成完整计划Superpowers先生成全量工程Task，再按依赖关系选择串行或并行执行。
5. Subagent并行模式 跨Task批量并行并行能力强全量Task形成后，可把互不依赖的任务分派给多个Subagent并行开发。并行前必须先锁定共享接口、数据模型和集成顺序。 跨Story串行整体偏串行BMAD按逐Story创建、开发、评审推进；在该实战方式下不做跨Story批量并行。换来更稳定的上下文与逐Story验收。 跨Story串行仅Story内部可并行上游Story仍是“出一个、开发一个”；Superpowers只能并行当前Story内部互不依赖的工程任务。Subagent能力不能突破上游Story供给节奏。 跨Task批量并行并行能力最直接PRD被拆成全量Task后，可直接用Subagent同时开发多个独立模块或能力。并行宽度最大，也最依赖强集成治理。
6. 开发效率 高吞吐前置规格较慢，实施并行较快Spec Kit增加一次规格与Task准备，但完成后可批量并行，适合任务量较大的项目。 低吞吐流程最稳但最慢逐Story创建、开发、评审带来较多等待与会话切换，整体交付周期较长。 中低吞吐Story间串行，Story内可加速Superpowers能提高单Story开发速度，但无法消除BMAD逐Story供给造成的串行瓶颈。 最高吞吐链路最短、并行最直接跳过Spec Kit和BMAD Story层，完成全量计划后即可批量启动Subagent。
7. Bug与功能遗漏风险 中高风险规格减少需求遗漏，并行增加集成BugSpec Kit能强化Feature完整性；但多个Subagent并行仍容易出现接口偏差、重复实现和集成缺陷。 低风险逐Story聚焦，质量稳定每次上下文小、AC明确，并在进入下一Story前完成开发与评审，功能遗漏和联动偏差较少。 最低风险Story聚焦 + Superpowers TDDBMAD保证Story上下文和验收完整，Superpowers保证测试优先与双阶段评审；代价是速度较低。 最高风险并行快，但上下文容易碎片化缺少Spec Kit完整规格和BMAD Story Gate时，Subagent更容易各自理解PRD，造成功能遗漏、接口不一致和返工。
8. TDD与质量控制 强规格场景 + Superpowers TDD可把Spec Kit场景映射为失败测试；还需增加跨Task集成测试和全局回归。 中强Story开发与Code Review完整BMAD有测试和评审流程，但严格RED–GREEN–REFACTOR需要额外写入项目规则和Gate。 最强聚焦Story的严格TDDAC可直接映射失败测试，之后执行最小实现、重构、规格符合性和代码质量双评审。 局部强单Task TDD强，全局覆盖需补每个Task可以严格TDD，但测试通过不代表PRD全部功能和跨模块场景都已覆盖。
9. 交接、追溯与变更成本 成本最高两次交接、三层工件PRD→spec/tasks→SP plan需要维护双向追溯；变更时可能同步三套事实。 最统一单框架状态链跨框架漂移最低，Correct Course可处理重大变化；代价是流程操作较多。 边界最清楚Story定WHAT，SP Plan定HOW每个Story交接一次，发现范围问题退回BMAD；完成证据应回写Story与Sprint状态。 交接最少链路短，但追溯较弱PRD直接到工程Task，变更同步快；缺少Story层后，Task与产品验收的映射更依赖人工维护。
10. 最适用场景 规格治理型需要全量Feature契约且任务可并行适合Spec Kit是组织标准、多人/多Agent并行、愿意承担较高规格与集成治理成本的项目。选择理由：独立规格资产 + 高并行。 统一治理型复杂、合规、质量优先适合更看重全生命周期一致性、审计和稳定质量，可以接受较低开发吞吐的项目。选择理由：单一体系 + 低遗漏。 质量优先型中大型产品的高质量Story交付适合Bug和功能遗漏代价高、需要BMAD完整规划与Superpowers严格TDD，但不追求跨Story批量并行的项目。选择理由：质量最高，效率较低。 速度优先型边界清晰、可模块化并行适合强技术负责人在场、模块接口能提前冻结、需要最大化Subagent吞吐并能承受更高返工风险的项目。选择理由：效率最高，风险也最高。

注：这里的“串行”指怡哥当前采用的BMAD逐Story实战方式；不代表框架在所有版本、自动化模式或人工编排下绝对不能并行。
