使用 BMAD 从 0 到 1 开发一个新产品

这不是“让 AI 一次写完整个应用”的教程，而是一套逐层建立事实、逐层审批、按 Story 交付、用证据上线的产品工程方法。

先看结论

完整 0→1 默认走 BMad Method，不走 Quick Dev

新产品包含大量未决的用户、业务、体验和技术问题。正确路线是逐层建立上下文：Analysis → Planning → Solutioning → Implementation。每一层产物都是下一层的输入，最终由 Story 文件把已确认事实带进实现。

默认主链：bmad-help → 可选分析与研究 → bmad-product-brief → bmad-prd → 有界面则 bmad-ux → bmad-architecture → bmad-create-epics-and-stories → bmad-check-implementation-readiness → bmad-sprint-planning → Story 开发循环 → 发布 → Epic 复盘。
不是大 Prompt

分阶段新对话

每个主要 workflow 使用独立对话，减少上下文污染；通过正式产物完成交接。

不是 spec.md 主导

Story 是实现契约

完整流程依靠 PRD、UX、Architecture、Epics 与 Story 逐层收敛；spec-*.md 主要属于 Quick Flow。

不是自动等于正确

Gate 决定能否前进

规划、技术方案、实现、发布都要用可检查证据通过门禁。

上下文工程

质量的基础：每个 Agent 只依据已批准事实工作

业务事实

由最终 Product Brief / PRD 控制，不从代码猜业务意图。

体验事实

由 DESIGN.md 与 EXPERIENCE.md 控制，不用临时 Mock 反向定义体验。

技术事实

由 Architecture 与 Project Context 控制，跨 Story 保持一致。

实现事实

由当前 Story、代码、测试和 Review 证据控制。

推荐的对话纪律

  1. 每个主要 workflow 新开对话。
  2. 开始时明确 Create / Update / Validate 意图。
  3. 只加载最新 final 上游产物与必要项目配置。
  4. 发现上游冲突先报告，不在下游偷偷改需求。
  5. 每个阶段结束记录状态、未决项、批准人和下一步。
最常见失败：在同一长对话里混做 PRD、UX、Architecture 和编码，Agent 会把讨论中的临时想法当成最终事实。分阶段的意义就是让上下文边界可控。
Phase 1 · 可选

Analysis：先证明值得做，再定义怎么做

Analysis 是可选阶段，但“可选”不代表“没有证据也可以跳过”。当用户问题、市场、技术可行性或商业模式不确定时，先探索比写 PRD 更便宜。

Workflow适用情形主要产物退出条件
bmad-brainstorming方向模糊，需要扩展与收敛想法创意记录与意图出现可进一步验证的候选方向
bmad-forge-idea要用反方压力测试概念Forge 报告、成熟想法想法被证实、调整或便宜地放弃
Market / Domain / Technical Research市场、行业规则或技术假设不确定研究发现与证据关键假设有证据和置信度
bmad-prfaq希望从客户价值反推产品PRFAQ价值主张和客户结果经得起质疑
Gate A0：明确目标用户、核心问题、现有替代方案、为什么现在做、最危险假设、成功信号和明确不做什么。若核心问题仍是猜测，不进入 PRD。
Phase 1 · 推荐

Product Brief：把证据压缩成战略起点

输入

  • 创意、访谈、市场/领域/技术研究。
  • 商业目标、资源与时间约束。
  • 现有替代方案与竞争差异。

输出

  • 产品愿景与目标用户。
  • 问题、价值主张和成功指标。
  • MVP 边界、风险与假设。
bmad-product-brief

请基于以下最终研究输入创建 Product Brief：
- 产品想法：[填写]
- 目标用户与场景：[填写]
- 已验证证据：[填写]
- 商业目标与约束：[填写]

请显式区分事实、假设和待验证问题；定义 MVP、Non-goals、成功指标和最大风险。
发现材料冲突时先列出冲突，不要自行选择。
Gate A1：Brief 必须回答“为谁、解决什么、为什么值得、MVP 做什么、不做什么、如何知道成功”。没有可衡量结果的愿景不能直接成为 PRD 范围。
Phase 2 · 必需

PRD：把产品意图变成可验证要求

bmad-prd 具有 Create、Update、Validate 三种意图。0→1 首次创建使用 Create；定稿前单独运行 Validate，不能把“写完”当成“通过”。

Create

从 Brief 和研究提取上下文，通过引导式发现形成用户、范围、功能需求、非功能需求、状态、权限、数据和验收。

产品负责人逐项审阅

确认 MVP 与未来范围、业务规则、角色权限、异常状态、成功指标和约束。争议必须决策，不能留给开发猜。

Validate

在新对话中对 final 候选稿做覆盖、矛盾、可测试性和范围检查，修复 Critical / High 问题。

bmad-prd

意图：Create。
请完整读取最终 Product Brief、研究和项目配置，创建新产品 PRD。
要求：
1. 明确 Personas、Journey、MVP、Non-goals；
2. FR / NFR 可追踪、可测试；
3. 覆盖角色、权限、状态、异常、数据与集成边界；
4. 冲突和缺失决策先报告，不得自行补成产品事实；
5. 完成后给出 Validate 所需输入和质量清单。
Gate P1：PRD 范围冻结；关键角色、规则、状态、权限、数据、FR/NFR 与验收可测试；Critical 和 High 验证问题清零或有明确批准的处置。
Phase 2 · 有界面则执行

UX：分别定义“看起来怎样”和“如何工作”

有用户界面的产品应在 PRD 后运行 bmad-ux。核心不是做漂亮页面，而是建立视觉事实和行为事实，让后续 Architecture、Story 与实现不再猜体验。

DESIGN.md

视觉方向、设计原则、Tokens、组件、布局、响应式、可访问性与关键屏幕。

EXPERIENCE.md

信息架构、用户流程、状态转换、反馈、错误、空态、加载、权限与恢复路径。

bmad-ux

请基于 final PRD 创建本产品 UX。
先审计 PRD 的角色、Journey、状态、权限、关键任务和 NFR，再建立 DESIGN.md 与 EXPERIENCE.md。
每条关键用户流程必须覆盖：入口、主路径、空态、加载、错误、权限不足、取消、恢复和完成反馈。
视觉事实与行为事实分开维护；原型不得擅自改变 PRD 业务规则。
Gate P2：关键 Journey 可完整演示；每个核心页面/状态有入口；异常与恢复可描述；响应式和可访问性有标准；UX 与 PRD 不冲突。
Phase 3

Architecture：在多个 Agent 写代码前统一技术决定

系统边界

模块、服务、客户端、第三方、信任边界和部署单元。

一致性决定

技术栈、API、数据、身份权限、状态、事件、错误、观测和测试。

质量属性

安全、性能、可用性、扩展性、可维护性和成本的实现策略。

bmad-architecture

请读取 final PRD、DESIGN.md、EXPERIENCE.md 和已有项目约束，创建 Architecture。
所有关键技术决定必须关联对应 FR/NFR 或 UX 需要，写明选择、理由、权衡和一致性规则。
覆盖：系统边界、数据模型、API、身份权限、状态/事件、错误处理、安全、性能、观测、测试、部署与迁移。
发现产品或 UX 未决项时停止并列出，不得用技术假设替代产品决定。
Architecture 不负责新增需求：如果技术设计需要改变用户可见规则，应回到 PRD/UX Update，而不是在 Architecture 中悄悄重写产品。
Gate S1：所有跨 Epic 的关键技术决定明确；没有互相矛盾的技术模式；风险与 Spike 有处置；Architecture 能约束不同 Story 的实现保持一致。
Phase 3

Epics & Stories：在架构之后拆分，才能真正可实现

BMAD V6 将 Epics/Stories 放在 Architecture 之后。这样 Story 能继承数据、API、权限和技术模式，而不是只有业务标题。

层级应包含质量判断
Epic独立用户/业务价值、范围、依赖和完成标准完成后能交付可观察结果，不只是技术分层
Story用户目标、上下文、AC、异常、技术约束、测试要求、依赖一个 Agent 在合理上下文内可完成并验证
TraceabilityFR/NFR、UX、Architecture 决定映射每个 active 要求有落点，每个 Story 有来源
bmad-create-epics-and-stories

请基于 final PRD、UX 与 Architecture 创建 Epics 和 Stories。
按可交付用户价值拆 Epic，不按前端/后端/数据库分层。
每个 Story 必须包含：
- 关联 FR/NFR、UX 流程与 Architecture 决定；
- 明确 AC、错误/权限/边界状态；
- 依赖、风险、测试和可观测性要求；
- 可在单个实现循环内完成的范围。
最后输出覆盖矩阵、依赖顺序和无法落位的要求。
Gate S2：所有 active FR/NFR 和关键 UX 状态都有实现落点；Story 无循环依赖、无巨大模糊范围；顺序支持逐步形成可运行产品。
实施前总门禁

Implementation Readiness：不是形式检查，而是允许开发的闸门

bmad-check-implementation-readiness

请对 final PRD、UX、Architecture、Epics/Stories 做实施就绪检查。
重点验证：
- 要求覆盖与双向追踪；
- 业务、UX、技术决定是否互相一致；
- Story 是否可独立实现和测试；
- 权限、安全、数据、状态、异常、NFR 是否有落点；
- 依赖、风险、迁移和未决项是否阻塞。
请给出 PASS / CONCERNS / FAIL，并逐项给出证据和修复归属。
PASS关键规划材料一致、完整、可实现；可进入 Sprint Planning。允许开发
CONCERNS存在风险但不一定阻塞；必须有责任人、影响、处置和接受记录。条件通过
FAIL存在阻塞性缺口或冲突；回到对应上游 workflow 修复并重新检查。禁止开发
禁止做法：Readiness 为 FAIL 时仍让 Dev Agent 开始“边做边补”。这会把产品未决项和架构冲突扩散到代码、测试和数据。
Phase 4

Sprint Planning：只初始化一次，再按优先级推进 Story

bmad-sprint-planning 创建 sprint-status.yaml，把 Epics 和 Stories 转为可跟踪的开发序列。它不是重新定义需求。

排序原则

  1. 基础骨架与高风险技术验证。
  2. 最短可运行用户路径。
  3. 核心业务价值和关键状态。
  4. 异常、运营、优化和扩展能力。

进入条件

  • Readiness 已 PASS 或条件通过。
  • 开发/测试环境可用。
  • 代码规范和 Project Context 明确。
  • 发布策略与最小验收环境可用。
bmad-sprint-planning

请读取已批准的 Epics/Stories 与 Readiness 结论，初始化本项目 sprint-status.yaml。
按依赖、用户价值、风险降低和可演示增量排序。
不得新增未批准需求；阻塞项必须标记责任人与解除条件。

bmad-code-review

请对当前 Story 的最终实现做代码审查。
对照 Story AC、Architecture、Project Context、实际 Diff 与测试结果，检查：
1. 每条 AC 是否有实现和证据；
2. 权限、数据、状态、错误、并发、重试和边界；
3. 是否违反共享架构模式或引入兼容问题；
4. 测试是否能抓住真实失败，而非只覆盖表面；
5. Story 文件清单与实际改动是否一致。
区分当前必须修复项与无关历史问题。
质量体系

测试不是 Phase 4 最后的一个步骤，而是每个 Story 的完成条件

层级证明什么常见责任点
静态检查类型、格式、基础代码规则每次实现与合入
单元测试局部业务规则和边界Story 实现者
集成/契约测试模块、API、数据库、事件和第三方协作跨边界 Story
用户路径 / E2E真实入口到结果的关键 Journey核心价值路径
状态与权限不变量直接调用、并发、重放不能绕过规则安全与数据边界
NFR 验证性能、安全、可靠性、可访问性和观测Release Gate 前
可选补充：项目缺少 API/E2E 覆盖时可使用 bmad-qa-generate-e2e-tests 生成测试。但测试生成不能替代 bmad-code-review，也不能替代产品验收。
Definition of Done：AC 有证据、自动化测试通过、关键用户路径可运行、状态/权限不变量不被绕过、Review 有效问题关闭、文档和 Sprint 状态同步。
上线闭环

BMAD 负责构建上下文；上线仍需要项目自己的 Release Gate

部署方式取决于你的技术栈。不要把“代码 Review 通过”直接等同于“可以上线”。发布必须证明制品、配置、迁移、监控和回退都可执行。

候选版本冻结

确认纳入的 Stories、版本号、制品、配置、数据库迁移和已知限制。

发布前验收

运行全量回归、关键 Journey、NFR、权限/数据检查，并由产品负责人完成 UAT。

发布准备

确定灰度范围、功能开关、监控指标、告警阈值、回退触发条件和负责人。

上线与观察

按计划发布，观察错误、性能、核心业务指标和数据一致性；达到观察窗口才关闭发布。

不可逆动作：生产数据库删除、批量数据修复、财务处理、权限迁移和安全策略变更必须单独确认，先验证备份/恢复，不能由 Agent 自主执行。
变更管理

计划变化时，用 Correct Course；Epic 完成后做 Retrospective

bmad-correct-course

适用于开发中出现重大范围、依赖、技术或优先级变化。先评估影响，再更新 PRD/UX/Architecture/Epics/Sprint 中真正受影响的层。

不要：直接修改当前 Story 来承载一个跨 Epic 的新方向。

bmad-retrospective

每个 Epic 完成后复盘估算、上下文质量、缺陷、Review、测试、流程摩擦和用户结果，把可复用经验带到下一个 Epic。

输出：事实、原因、行动项、责任人、验证时间。

变更分层：用户价值/业务规则变了 → PRD Update；体验变了 → UX Update；跨模块技术决定变了 → Architecture Update；只是实现细节 → 当前 Story 内处理。
贯穿案例

案例：从 0 到 1 开发“团队 AI 任务台”

阶段 1：从想法到 Product Brief

原始想法：让小团队把需求、执行和验收放在同一个 AI 协作工作台。

研究发现：目标用户不是缺少任务工具，而是 AI 产出与正式决策脱节，交接时丢失上下文。

MVP：创建项目、建立任务、绑定事实文档、执行检查清单、形成交付证据。

Non-goals：首版不做企业 SSO、计费、多地区部署和开放插件市场。

阶段 2：PRD 与 UX

角色：Owner、Contributor、Reviewer。

关键 Journey：Owner 创建项目 → Contributor 接收任务并交付 → Reviewer 按证据批准或退回。

关键状态：Draft、Ready、In Progress、Review、Changes Requested、Done、Blocked。

UX Gate：每个状态都有入口、允许动作、反馈、异常、权限和恢复路径。

阶段 3：Architecture 与 Story 拆分

Architecture：统一身份边界、项目/任务/审查数据模型、状态机、审计事件、文件引用和通知策略。

Epic 1：项目与成员；Epic 2：任务生命周期；Epic 3：Review 与证据；Epic 4：运营与可靠性。

Story 示例：“作为 Owner，我要邀请 Contributor，使其只能访问指定项目。”AC 覆盖邀请、过期、重复、撤销、越权和审计。

阶段 4：第一个可运行增量

顺序：项目骨架 → 身份与项目 → 任务创建 → 状态流转 → Review → 通知 → 运营。

每个 Story：Create Story 明确契约，Dev Story 实现与测试，Code Review 独立验证。

首个 Release：邀请制灰度，观察任务完成率、Review 退回原因、错误率和权限异常。

FAQ

常见问题

新产品能否直接用 bmad-quick-dev？

只适合范围非常小、业务和技术都已明确的工作。真正的 0→1 产品通常存在大量未决问题，应走 BMad Method；否则 Agent 会用实现假设替代产品和架构决定。

Product Brief 是必需的吗？

官方流程允许直接从 PRD 开始，但 0→1 默认建议先做 Brief。它能把研究、愿景、MVP 和风险压缩成稳定输入，减少 PRD 反复解释。

UX 必须在 Architecture 前吗？

有界面且用户体验影响系统状态、数据、权限或接口时，建议先完成 UX。Architecture 才能依据真实流程设计边界。纯后台或无显著 UX 的产品可按实际跳过。

为什么 Epics/Stories 要在 Architecture 后？

因为数据、API、权限和技术模式会影响 Story 的边界、依赖和验收。先有架构再拆 Story，能减少实现时反复改写。

是否有统一 spec.md？

完整主流程没有强制统一 spec.md。PRD、UX、Architecture 和 Epic/Story 共同构成规格链；当前 Story 是实现时最直接的工作契约。spec-*.md 主要来自 Quick Dev。

如何保证不同 Agent 写出的代码一致？

用 Architecture 和 Project Context 固化跨 Story 规则；每个 Story 明确引用它们；Code Review 再检查实际 Diff 是否违反这些决定。

Readiness 是 FAIL 怎么办？

按问题归属回到 PRD、UX、Architecture 或 Epics/Stories 修复，再重新运行检查。不要让开发在代码里自行消化阻塞。

上线是否属于 BMAD workflow？

BMAD 主链负责从规划到实现与质量验证；实际构建、部署、灰度、监控和回退取决于项目技术栈。教程因此提供 Release Gate，但不假装存在一个适用于所有项目的统一部署命令。

这个 HTML 为什么不需要本地服务器？

全部样式和脚本都内嵌在一个文件中，没有模块加载、接口请求或在线资源。直接双击 index.html 即可打开。

最终记忆句：BMAD 0→1 的核心不是多写文档，而是让“为什么做、做什么、体验怎样、如何构建、如何验收”在进入代码前逐层变成可检查事实。
