BMAD → Spec Kit 双路径教程 · 2026-07-29

两种 BMAD 产品设计交付方式

这份教程只回答一个问题：BMAD 应该做到什么程度，再把哪些文件交给 Spec Kit。答案有两种，区别在于产品级架构、Feature 拆分和 Readiness 风险由谁提前收敛。

单文件离线教程 两条交付路线 文件级责任说明 Gate 驱动
ROUTE A / RECOMMENDED

Phase 3 完整交付

完成 PRD、UX、Architecture、Epics/Stories，并通过 Implementation Readiness 后交接。适合中大型和长期产品。

ROUTE B / LEAN

UX & Design 后交付

交付 prd.md、DESIGN.md、EXPERIENCE.md，由 Spec Kit 补 Feature roadmap 和技术规划。适合小型 MVP。

SHARED RULE

只保留一个拆分真相

Feature 拆分只能由 BMAD Epics/Stories 或 Spec Kit roadmap 中的一方负责，不能长期并行维护两套范围。

默认推荐路线 A：先在 BMAD 中完成 Phase 3 Solutioning，并通过 Implementation Readiness Check，再按一个 Epic 或 Feature 交给 Spec Kit。只有范围小、架构简单、速度优先的 MVP，才建议采用路线 B。
本教程对前述讨论的正式修正 “Feature 包”和独立的 traceability.md 都不是 BMAD 当前标准工作流的固定原生产物。它们只能被标记为自定义适配层，不能冒充 BMAD 官方输出。

Route Decision

先选交接深度，再选 Feature 拆分负责人

两条路线都能成立。区别不是“正确与错误”，而是有多少产品级风险在 BMAD 中提前收敛，以及有多少责任被转移给 Spec Kit。

A

Phase 3 完整治理路线

适合中大型产品、多个 Feature、长期演进、多成员/多智能体协作，以及有复杂权限、集成、安全或部署要求的项目。

  • 产品级架构先冻结
  • Epics/Stories 在 BMAD 中形成
  • Readiness 作为正式交接 Gate
B

UX & Design 轻量路线

适合小型 MVP、单体应用、技术边界简单、迭代速度优先，以及允许 Spec Kit 承担更多分解和规划责任的项目。

  • 只交付 PRD 与两个 UX Spine
  • Spec Kit 负责 Feature roadmap
  • 技术一致性需额外补偿
先做一个不可重复的决定 Feature 拆分只指定一个负责人：要么使用 BMAD 的 Epics/Stories，要么使用 Spec Kit 的 Spec-of-Specs roadmap。不要让两边各自产出一套并长期并行维护。

Route A · Recommended

BMAD 完成 Solutioning 和 Readiness 后交付

这条路线把产品级不确定性留在 BMAD 中解决。Spec Kit 接手时，不再重新发明产品目标、体验和整体架构，而是把一个已批准的交付切片编译成可执行规格。

PHASE 1 Analysis 研究、Product Brief，按需执行
PHASE 2 PRD + UX 产品需求、设计系统与体验行为
PHASE 3 Architecture + Epics 整体技术决策和产品交付切片
GATE Implementation Readiness 只有 PASS/READY 才正式交接
HANDOFF Spec Kit per Feature Specify → Plan → Tasks → Analyze
BMAD 的停止点 Readiness 通过后停止 BMAD 实施循环。不再运行 BMAD 的 Sprint Planning、Create Story、Dev Story 作为主开发链，否则会与 Spec Kit 形成重复任务系统。

Route A · Handoff Gate

不是“把一堆文件扔进去”，而是带着范围和权威关系交接

交接前检查

  • PRD 的 FR/NFR 有稳定且连续的 ID，没有未处理的关键开放问题。
  • DESIGN 与 EXPERIENCE 已批准，职责边界清楚，关键流程包含失败与恢复路径。
  • Architecture 已冻结产品级技术决定，并说明 Feature 允许自行决定的空间。
  • Epics/Stories 覆盖 MVP，依赖清楚；Story 是产品切片，不是重复的代码任务。
  • Implementation Readiness 为 PASS/READY；所有 CONCERNS 均有明确处置。
  • 本次只选择一个 Epic 或垂直切片，不把整个产品放入一次 Feature Spec。

推荐交接提示词

你正在为本项目创建一个 Spec Kit Feature Specification。

请读取并尊重以下权威源：
- prd.md：业务范围、业务规则、FR/NFR、成功指标
- DESIGN.md：视觉 Token、组件与表达规则
- EXPERIENCE.md：用户流程、行为、状态、错误恢复与无障碍
- ARCHITECTURE-SPINE.md：产品级技术决策和不可违反的约束
- epics/epic-01.md：本次 Feature 的范围与验收意图
- implementation-readiness.md：交接 Gate、剩余风险和豁免

本次只规格化 Epic 01，不得引入其他 Epic 范围。
保留所有上游需求 ID，并在 spec.md 中增加 Source References。
如上游文件发生冲突，停止并报告冲突，不自行选择或改写源文件。
先执行 /speckit.specify，再执行 /speckit.clarify；未经确认不要进入 plan。
不要进入 BMAD Phase 4 主循环 一旦选择 Spec Kit 负责 Feature 规格与任务，BMAD 的 sprint-status.yaml、Create Story 和 Dev Story 不应再成为另一套实施真相。项目管理工具可以追踪状态，但不能复制任务内容。

Route B · Lean Handoff

PRD、DESIGN、EXPERIENCE 也能启动 Spec Kit

这条路线可以使用，但它只完成了产品需求和体验层。Architecture、Feature 切片及跨 Feature 一致性尚未由 BMAD 收敛，因此必须明确转交给 Spec Kit 或人工治理。

BMAD PRD 产品事实与验收目标
BMAD UX Design + Experience 视觉与行为体验基线
SPEC KIT PROJECT Constitution + Roadmap 补充原则与 Feature 分解
PER FEATURE Specify → Analyze 逐 Feature 规格、计划和任务
这不是“少三个文件”这么简单 没有 Architecture 和 Readiness，意味着第一个 Feature Plan 可能无意中替整个产品做出架构决定；后续 Feature 又可能采用另一套模型。小型 MVP 可以接受这种速度优先策略，中大型产品必须补偿。

BMAD 实际交付给 Spec Kit 的三个文件

文件产生技能/阶段已有作用尚未解决的问题重点注意
prd.mdbmad-prd / Phase 2产品目标、范围、业务规则、FR/NFR、成功指标。未形成 Feature 路线图和技术方案。保留需求 ID；Spec Kit 不得把技术偏好反写成产品需求。

Route B · Risk Control

三文件方式可行，但要主动偿还四类缺口

缺口

路线 B 的适用边界

可以直接采用

  • 小型或验证型 MVP
  • 单体应用，外部集成很少
  • 技术栈已有明确团队惯例
  • 功能数量少，可逐个 Feature 校正
  • 接受速度优先及后续架构补强
VS

建议回 BMAD 补 Architecture

  • 多个端、服务或仓库
  • 复杂权限、支付、合规或安全
  • 跨 Feature 共享核心数据模型
  • 多人或多智能体并行开发
  • 需要长期维护、迁移和发布治理

Single Decomposition Owner

Feature 包不是必需品，清晰的拆分责任才是

BMAD 没有名为“生成 Feature 包”的标准工作流。解决方式不是强造一个文件，而是选择下列一种拆分机制。

BMAD 负责拆分

bmad-create-epics-and-stories 使用 PRD 和 Architecture 产生技术知情的 Epics/Stories。

  • 一个 Epic 或垂直 Story 集合成为 Spec Kit 输入
  • 不再额外生产 Feature 包
  • Spec Kit 的 spec.md 就是最终 Feature 合同
OR

Spec Kit 负责拆分

使用 Spec-of-Specs roadmap，把产品拆成多个可独立规格化和验收的子 Feature。

  • roadmap 保存稳定 ID、范围和依赖
  • 每个 Feature 单独走 Spec → Plan → Tasks
  • 不再生成 BMAD Epics/Stories 与它竞争
禁止双重拆分真相 如果 BMAD Epic、Spec Kit roadmap 和自定义 Feature 包同时存在，范围、编号、状态和依赖迟早漂移。选择一个主拆分源，其他形式只做引用，不复制内容。

最小 roadmap 示例

| ID    | Feature      | 范围     | 上游来源                  | 依赖  | 状态    | Sub-spec |
|-------|--------------|----------|---------------------------|-------|---------|----------|
| F-001 | 账号登录     | MVP      | PRD-FR-001, EXP-FLOW-01   | —     | planned | —        |
| F-002 | 内容创建     | MVP      | PRD-FR-002, EXP-FLOW-02   | F-001 | planned | —        |
| F-003 | 内容分享     | Deferred | PRD-FR-003, EXP-FLOW-03   | F-002 | planned | —        |

Traceability

traceability.md 不是默认答案

BMAD 的 Readiness 会检查规划文件的内聚性，但没有一个通用标准步骤保证输出名为 traceability.md 的独立矩阵。多数项目使用“稳定 ID + 引用链”即可。

SOURCEPRD-FR-001产品需求稳定 ID
SLICEEpic 01 / F-001产品或 roadmap 切片
CONTRACTspec.md / FR-001Feature 行为合同
DELIVERYtasks + tests实现与验证证据

推荐的 Source References

## Source References

- Product requirements: PRD-FR-001, PRD-FR-003, PRD-NFR-002
- User journeys: EXP-FLOW-002, EXP-STATE-004
- Design rules: DESIGN-COMP-004, DESIGN-TOKEN-007
- Architecture constraints: ARCH-AUTH-001, ARCH-DATA-003
- Delivery slice: EPIC-01 / STORY-01-02
什么时候才单独维护 traceability.md？ 强监管、跨团队、多供应商、审计或合同性交付项目，需要集中查看需求覆盖时再建立。普通产品中，它往往是高维护成本的重复索引。

Failure Modes

最容易让三套方法互相打架的做法

  • 一次把整个产品交给 /speckit.specify
    纠偏：选择一个 Epic/Feature，或者先做 Spec-of-Specs roadmap。
  • 把 PRD 直接改名为 spec.md
    纠偏：PRD 是产品级事实，Spec 是一个 Feature 的行为合同，粒度不同。
  • 同时维护 BMAD Stories、Feature 包、Spec Kit roadmap 三套切片
    纠偏：只保留一个 Feature 拆分真相，其他文件只引用稳定 ID。
  • 把 traceability.md 当成 BMAD 官方必需产物
    纠偏：默认使用稳定需求 ID、roadmap/Epic 和 Source References。
  • 让 Feature Plan 默默推翻 Architecture
    纠偏：产品级决策改变必须先回写并批准上游 Architecture。
  • 把内部 Gate PASS 描述成发布批准
    纠偏：规划就绪、实现验证、公开测试和正式发布是不同 Gate。
  • 只验证 Happy Path
    纠偏：Experience、Spec、测试和 Converge 都必须覆盖异常、恢复、并发和生命周期。

Reference & Closure

最终建议

默认采用路线 A：BMAD 完成 Phase 3 Solutioning 并通过 Readiness，再把一个获批 Epic/Feature 交给 Spec Kit。路线 B 可以加速小型 MVP，但必须显式补偿 Architecture、Feature roadmap、追踪和一致性 Gate。
