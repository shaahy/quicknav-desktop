# Spec-Kit 与 OpenSpec 软件开发实战教程 PRD

## 1. 问题是什么

需要形成一套面向真实软件开发的中文教程，回答三类问题：

1. GitHub Spec Kit 在软件开发各阶段适合解决什么问题，如何从需求走到实现。
2. Fission-AI OpenSpec 在软件开发各阶段适合解决什么问题，如何完成一次变更闭环。
3. 一个已经用 Spec Kit 完成 MVP 并上线的现有项目，如何继续安全地增加小需求、调整既有需求，并保持需求、规格、计划、任务与代码一致。

重点不是重复 README，而是给出可复制的命令、目录、输入示例、产物示例、审核点和常见错误。

## 2. 成功标准

- 读者能判断何时选 Spec Kit、何时选 OpenSpec，以及二者是否需要共存。
- 两套教程都包含安装/初始化、需求澄清、规格、设计或计划、任务拆分、实现、验证、归档或演进的完整闭环。
- 现有项目教程分别覆盖“新增小需求”和“修改已上线需求”。
- 明确说明旧 `spec.md` / `plan.md` / `tasks.md` 应保留、修改还是新建，避免覆盖历史和规格漂移。
- 所有命令以 2026-07-14 的官方仓库主线文档为依据，并标注工具版本变化风险。
- 最终提供一份可直接照着整理和提交项目资料的清单。

## 3. 输出范围

计划输出 4 份独立 Markdown 文档：

1. `01-Spec-Kit使用场景与实战教程.md`
2. `02-OpenSpec使用场景与实战教程.md`
3. `03-已上线Spec-Kit项目的增量迭代教程.md`
4. `04-项目资料整理与交付清单.md`

每套框架教程包含：

- 核心思想与适用场景
- 不适用场景和真实代价
- 在需求、设计、开发、测试、发布、维护各阶段的用法
- 一个贯穿始终的小型示例
- 命令级操作步骤与预期产物
- 质量门槛、分支策略、人工审核点和故障排查
- 与另一套框架的对照和选型建议

现有项目教程包含：

- 场景 A：新增独立小功能
- 场景 B：调整既有功能行为
- 场景 C：实现中发现原需求或技术方案需要反向修订
- Spec Kit 的 flow-forward、living spec、flow-back 三种演进方式及选择规则
- 是否迁移到 OpenSpec 的判断，不默认建议迁移

## 4. 暂不包含

- 未拿到真实项目资料前，不对你的项目架构和具体文件做推测。
- 本轮不直接改项目源码、不执行升级、不覆盖现有 Spec Kit 产物。
- 不把两套框架宣传文案当作客观结论；对比会区分官方事实与我的判断。
- 不展开企业级合规、跨仓库 Store 等高级能力的完整实施，只说明适用入口。

## 5. 约束条件

- 你的项目已经上线，任何增量流程都应支持回滚、评审和历史追溯。
- Spec Kit 与 OpenSpec 的命令和目录近年仍在演进，教程必须注明版本或检查方式。
- 真实项目定制必须以源码和现有产物为证据，不能只凭原始需求文档推导当前系统状态。
- 项目可能含密钥、用户数据、生产配置；交付资料前必须脱敏。

## 6. 初步方案

### 6.1 教程结构

采用“解释 + 场景判断 + 动手教程 + 参考清单”四层结构：

- 解释：建立两套框架的心智模型。
- 场景判断：按项目阶段、变更大小、团队协作和追溯要求选择。
- 动手教程：用同一个示例分别走完 Spec Kit 和 OpenSpec，便于比较。
- 参考清单：列出命令、目录、产物和审核门槛。

### 6.2 对你当前项目的初步判断

不建议因为 OpenSpec 更强调 brownfield 就立即迁移。你当前已经有 Spec Kit 产物，优先考虑沿用 Spec Kit 的增量演进流程，成本最低、历史最完整。只有在后续变更多、希望每个 change 独立提案/归档，或 Spec Kit 的阶段与 Markdown 负担明显影响效率时，再评估 OpenSpec。

### 6.3 需要你后续提供的资料

最好把以下内容放在一个文件夹中，保持原目录层级：

**必需：**

1. 当前项目源码，建议完整 Git 仓库或可运行副本；至少包含本次变更涉及的模块、测试、配置样例和依赖清单。
2. 当前要新增或调整的需求，写清背景、目标用户、现状、期望行为、验收标准、优先级及明确不做什么。
3. Spec Kit 已生成的完整目录，不只单独拷贝 `spec.md`：建议保留 `.specify/`、`specs/` 及其中的 `spec.md`、`plan.md`、`tasks.md`、`research.md`、`data-model.md`、`contracts/`、`quickstart.md`、`checklists/` 等实际存在内容。

**强烈建议：**

4. 最初需求文档和后续变更记录，用来判断“原始意图、已上线行为、现在的新意图”三者差异。
5. README、架构说明、数据库结构或迁移脚本、API 文档、测试说明、部署说明。
6. 当前线上版本对应的 Git commit / tag、默认分支，以及本次迭代准备使用的分支。
7. 已知技术债、线上问题、不能改变的兼容约束、数据迁移和回滚要求。

**不需要提供或必须脱敏：**

- `.env`、生产密钥、Token、真实用户数据、数据库备份、第三方私钥。
- `node_modules`、构建产物、缓存目录和大型二进制文件，除非问题只在这些产物中出现。

推荐整理结构：

```text
项目增量开发资料/
├─ 00-说明.md
├─ 01-新需求与调整需求/
├─ 02-原始需求与历史变更/
├─ 03-spec-kit产物/
├─ 04-项目源码/
├─ 05-测试与验收资料/
└─ 06-架构部署与约束/
```

其中 `00-说明.md` 建议写：项目如何启动、当前线上 tag/commit、本次要改什么、哪些目录禁止修改、测试命令、脱敏情况。

## 7. 待确认的问题

1. 正式教程默认以哪个 AI 编码工具演示：Codex、Claude Code、GitHub Copilot，还是三者都给命令差异？
2. 教程示例是否采用一个通用 Web 应用小需求，例如“已上线任务管理系统新增任务优先级并调整到期提醒规则”？
3. 你希望教程偏“产品负责人能直接驱动 AI 开发”，还是同时覆盖开发者级 Git、测试、代码评审和发布细节？我建议后者，但产品决策点会单独标出。
4. 现有项目定制教程是在你上传资料后再做第二版，还是本轮先写通用版、上传后再补项目专属版？我建议先通用版，再基于真实资料做专属版。

## 8. 官方依据（PRD 阶段）

- Spec Kit 官方仓库与 `Evolving Specs in Existing Projects` 指南。
- OpenSpec 官方仓库、`Using OpenSpec in an Existing Project` 与变更编辑指南。

正式教程会在关键命令和方法判断旁提供可点击的官方来源链接。
