# 项目资料整理与交付清单

> 目标：让我能够基于证据为你的已上线项目制定增量开发方案，同时避免泄露密钥、用户数据和生产配置。

## 1. 最终结论

请同时提供：

- 当前源码。
- Spec Kit 完整产物。
- 本次新需求/调整需求。
- 原始需求和历史变更。
- 测试、架构、部署与约束资料。

其中前三项是最低必需集。最好保持项目原目录结构，不要把所有 Markdown 平铺到一个文件夹，否则文件之间的引用关系和 feature 边界会丢失。

## 2. 推荐目录结构

```text
项目增量开发资料/
├─ 00-说明.md
├─ 01-新需求与调整需求/
│  ├─ 本次需求.md
│  ├─ 验收标准.md
│  └─ 参考截图或原型/
├─ 02-原始需求与历史变更/
│  ├─ 原始PRD.md
│  ├─ 历史变更记录.md
│  └─ 已知线上差异.md
├─ 03-spec-kit产物/
│  ├─ .specify/
│  └─ specs/
├─ 04-项目源码/
│  └─ [保持原项目目录结构]
├─ 05-测试与验收资料/
│  ├─ 测试说明.md
│  ├─ 测试报告/
│  └─ 验收记录/
└─ 06-架构部署与约束/
   ├─ 架构说明.md
   ├─ API或数据库说明/
   ├─ 部署与回滚.md
   └─ 技术约束.md
```

如果源码本身已经包含 `.specify/`、`specs/`、docs 和测试，不必重复复制。可以直接提供完整脱敏项目仓库，并在 `00-说明.md` 标出这些目录的位置。

## 4. 必需资料

### 4.1 当前源码

优先提供完整 Git 仓库的脱敏副本，至少应包含：

- 依赖清单和锁文件，如 `package.json`、`package-lock.json`、`pyproject.toml`。
- 主要源代码。
- 配置样例，如 `.env.example`，只能放占位符。
- 数据库 schema 和 migrations。
- API 定义或 contracts。
- 单元、集成、端到端测试。
- README、启动和构建说明。
- CI 配置。

如果源码太大，最低限度提供本次需求涉及模块及其直接依赖、调用方、测试和配置。但需要在 `00-说明.md` 明确哪些代码没有提供；否则影响面分析可能不完整。

### 4.2 Spec Kit 完整产物

保留实际存在的目录，不要求为了清单人工补造文件：

```text
.specify/
├─ memory/
│  └─ constitution.md
├─ templates/
├─ scripts/
└─ [其他实际文件]

specs/
└─ <feature>/
   ├─ spec.md
   ├─ plan.md
   ├─ tasks.md
   ├─ research.md
   ├─ data-model.md
   ├─ quickstart.md
   ├─ contracts/
   └─ checklists/
```

为什么不能只给 `spec.md`：

- `constitution.md` 决定不可违反的工程原则。
- `plan.md` 记录技术路线和影响范围。
- `tasks.md` 记录实际实施边界和完成状态。
- `research.md`、`data-model.md`、`contracts/` 可能保存关键取舍和兼容约束。
- `checklists/` 能说明需求当时如何验收。

### 4.3 本次需求

至少写清：

- 背景和问题。
- 目标用户。
- 当前行为。
- 目标行为。
- 验收标准。
- 范围和非范围。
- 默认值、权限、状态和异常路径。
- 存量数据处理。
- API/客户端兼容。
- 发布、灰度和回滚要求。

没有答案的事项直接标注“待决定”，不要为了填表猜一个答案。

## 5. 强烈建议提供

### 5.1 原始需求与历史变化

- MVP 原始 PRD。
- 上线前后的需求调整。
- 产品验收记录。
- 已知“文档与线上不一致”的地方。
- 用户反馈、数据结论或事故记录中与本次需求有关的部分。

这能区分：原始意图、规格承诺、实际实现和新意图。

### 5.2 版本与分支信息

```powershell
git rev-parse HEAD
git branch --show-current
git remote -v
git tag --points-at HEAD
git status --short
```

如果仓库地址敏感，可以删除 remote URL，只保留分支、commit 和 tag 信息。

### 5.3 测试与质量命令

请提供真实命令及当前结果：

- 安装依赖。
- 启动开发环境。
- 单元测试。
- 集成测试。
- 端到端测试。
- Lint 和格式化检查。
- 类型检查。
- 构建。

不要只写“运行测试”，要写可执行命令和所需依赖。

### 5.4 数据和部署约束

- 数据库类型和版本。
- 表规模量级，不提供真实数据。
- migration 工具与规范。
- 是否允许停机、锁表或后台回填。
- 预发布环境是否可用。
- 部署方式、灰度能力、监控和回滚流程。

### 5.5 参考界面

如需求影响 UI，可提供：

- 脱敏截图。
- Figma/原型导出图。
- 关键用户路径说明。
- 不同权限和空/错/加载状态。

## 6. 绝对不要提供

- `.env`、`.env.production` 等真实环境文件。
- API Key、访问 Token、Cookie、SSH Key、证书私钥。
- 云服务、数据库、支付、邮件和短信真实凭据。
- 真实用户姓名、手机号、邮箱、身份证、地址、对话记录。
- 生产数据库备份或未脱敏 SQL dump。
- 内网地址、生产主机清单和不应公开的安全拓扑。
- 第三方受版权或合同限制、无权分享的源码和数据。

可用占位符：

```dotenv
DATABASE_URL=postgresql://USER:PASSWORD@HOST:5432/DB_NAME
API_KEY=REDACTED
JWT_SECRET=REDACTED
```

不要使用看起来像真实密钥格式的“示例值”。

## 7. 通常不需要提供

- `node_modules/`、`.venv/`、vendor 缓存。
- `dist/`、`build/`、`.next/` 等可重新生成的构建产物。
- IDE 缓存和系统临时文件。
- 大型日志、视频和数据库文件，除非它们与问题直接相关并已脱敏。
- 与本次需求无关的设计素材和业务资料。

例外情况要在 `00-说明.md` 解释原因。

## 8. 建议排除目录

按项目技术栈调整：

```text
node_modules/
.venv/
venv/
dist/
build/
.next/
coverage/
.cache/
tmp/
logs/
*.log
.env
.env.*
```

注意：不要排除 `.env.example`，但必须确认其中只有占位符。

## 9. 交付前自检

### 完整性

- [ ] 有 `00-说明.md`。
- [ ] 有当前源码或明确的最小源码范围。
- [ ] 有 `.specify/` 和 `specs/` 的完整相关产物。
- [ ] 有本次需求、非范围和验收标准。
- [ ] 有当前线上 commit/tag。
- [ ] 有项目安装、测试和构建命令。
- [ ] 有数据迁移、兼容和回滚约束。
- [ ] 已指出无法提供的资料及影响。

### 安全

- [ ] 没有真实 `.env`。
- [ ] 没有密钥、Token、Cookie、私钥和证书。
- [ ] 没有真实用户数据。
- [ ] 截图和日志已经脱敏。
- [ ] Git 历史中也没有准备一并交付的秘密。
- [ ] 第三方代码和资料有权分享。

### 可执行性

- [ ] README 中的启动方式仍有效。
- [ ] 依赖锁文件存在。
- [ ] 测试命令能执行，已知失败已记录。
- [ ] 本次需求涉及的测试、migration 和调用方没有漏掉。

## 10. 我收到资料后的处理步骤

我会先只读，不直接改代码：

1. 读取 `00-说明.md` 和新需求。
2. 识别当前线上基线与项目技术栈。
3. 盘点 `.specify/`、相关历史 specs 和源码入口。
4. 对照原需求、旧 spec、当前代码、新需求，形成三态/四态差异表。
5. 输出影响范围、风险、未知项和需要你决定的问题。
6. 建议 flow-forward、living spec 或 flow-back，并说明理由。
7. 写真实项目专属的简要 PRD/执行计划，等你确认。
8. 得到确认后才创建或修改 Spec Kit artifact 和源码。

## 11. 最小可先发版本

如果暂时不方便整理全部资料，可以先提供：

```text
第一批/
├─ 00-说明.md
├─ 本次需求.md
├─ specs/中相关feature的完整目录/
├─ .specify/memory/constitution.md
└─ 本需求涉及的源码与测试/
```

我可以先做“是否足够开始”的只读审查，并指出第二批还缺什么；但在依赖、调用方、迁移或测试不完整时，不会把影响范围判断成确定结论。
