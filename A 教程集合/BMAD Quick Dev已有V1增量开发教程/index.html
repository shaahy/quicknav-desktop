ONE INTENT · ONE SPEC · ONE REVIEWABLE CHANGE

用 BMAD Quick Dev 为已有 V1 做小功能增量

从一个清晰目标出发，经过意图压缩、Spec 审批、实现、自检、对抗式 Review 和问题分流，交付一组可审查、可测试、可回退的代码变更。

1一次只做一个目标
3三个高价值人工检查点
6+内部执行阶段
0无需启动本地网页端口
先看结论

Quick Dev 不是“跳过规划”，而是把规划压缩到一次执行里

它适合已有 V1 中边界清楚、风险可控的小改动。完整过程仍包含：理解目标、读取现有项目、决定直接实现还是先写短 Spec、获得批准、实现与测试、自检、对抗式 Review、修复或延期无关问题、交付结果。

推荐用法：如果 V1.1 有 2–3 个独立小功能，执行 2–3 次 Quick Dev。每次一个功能、一个 spec-{slug}.md、一组代码变更和一次 Review。全部完成后再做一次版本级组合回归。
输入

单一意图

一个用户可理解的目标、清晰边界、可验证结果，以及 V1 中不能破坏的行为。

过程

长执行，少打断

人工集中在意图澄清、Spec 批准和最终验收，而不是每改一个文件就确认。

输出

可审查变更

Spec、代码、测试、Review Trail、延期事项，以及是否可交付的明确结论。

边界

什么适合 Quick Dev，什么不适合

适合

小、清楚、局部

  • 已有页面的小功能或体验增强
  • 明确原因的 Bug 修复
  • 少量文件内的重构
  • 配置、校验、提示、筛选和排序调整
  • 复用现有模式的 API 或字段扩展
  • 一个已有 BMAD Story 的快速实现
VS
不适合

模糊、高风险、跨边界

  • 多个彼此独立的目标混在一起
  • 核心权限、计费、安全或状态机变化
  • 跨多个系统的协调式改造
  • 新的平台级架构或数据迁移策略
  • 需求还不能写出可判定验收
  • 需要团队长期维护的新架构决定
数量不是唯一标准：“只加一个按钮”也可能触发权限、审计和隐私风险；“修改十个相似文案”反而可能是一个低风险目标。判断依据是扩散面和决策风险，不是文件数。

步骤 1

为已有 V1 准备可用上下文

Quick Dev 会扫描现有项目，但它不可能从混乱或过时的代码库中自动得到正确产品事实。开始前先确保 V1 的真实边界可定位。

确认当前生产基线

至少知道 V1 对应的代码分支/提交、当前数据库结构、关键接口、权限、测试入口、已知缺陷和发布回退方式。

确认 Project Context

推荐存在并保持最新的 _bmad-output/project-context.md。它应记录技术栈、目录、命名、测试和不可违反的实现约束。

bmad-generate-project-context

上面是 AI IDE 中调用的 BMAD 工作流名，不是本教程网页的启动命令。

提供最相关的事实源

不要把全部历史文档无差别塞给 Agent。优先给：当前功能相关的最终 PRD/UX/Architecture、现有代码、相关测试和一个明确的 V1 不变清单。

停止条件：文档和生产代码严重不一致、现有测试不能运行、关键权限/数据行为未知。此时先运行项目文档梳理或正式影响分析，不应直接 Quick Dev。
步骤 2

把一个功能写成“单一意图包”

好的输入不需要很长，但必须让 Agent 知道用户结果、边界、验收、回归和可用事实源。

# Quick Dev Intent

## 目标
让 [用户角色] 能够 [完成一个结果]，从而 [获得价值]。

## 当前 V1 行为
- 现在用户怎样操作
- 相关页面 / API / 数据 / 权限是什么

## 本次改变
- 只列一个主要目标

## 明确不做
- 不做的重构、平台化、历史缺陷和扩展能力

## 验收
- 正常路径的可观察结果
- 错误、空数据、重复操作、无权限等边界结果

## V1 回归边界
- 哪些既有行为必须保持不变

## 相关输入
- 最终 PRD/UX/Architecture 章节
- 相关代码与测试路径

## 停止并询问
- 哪些产品、数据或架构决策不允许 Agent 自行推测

合格示例

“让运营人员再次进入订单列表时恢复其上次有效筛选；只针对当前用户和当前租户；清除无效条件；不增加跨设备同步；不得改变默认权限和查询结果。”

不合格示例

“优化订单列表体验，顺便把筛选、导出、权限、性能和老代码都改好。”这里至少包含五个目标，且验收不可判定。

步骤 3

在新对话中启动 Quick Dev

每个功能使用一个新对话，避免上一个功能的假设、Review 结论或延期事项污染下一个功能。

最稳妥的启动提示

bmad-quick-dev

这是一个已经上线的 V1 项目。本次只处理一个增量目标：
[粘贴单一意图包]

执行要求：
1. 先读取 project-context.md、相关最终规划产物、现有实现和测试。
2. 以 V1 当前生产行为为兼容基线，发现文档与代码冲突先报告。
3. 只处理本目标，不顺手重构或修复无关历史问题。
4. 先给出理解和影响范围；需要 Spec 时必须等我批准后再实现。
5. 同步实现测试，运行验证，并执行对抗式 Review。
6. 当前变更导致的问题必须修复；无关问题写入 deferred-work.md。
7. 最终给出改动文件、测试证据、Review Trail、剩余风险和回退建议。

Quick Dev 可接受的其他输入

输入适用情况补充要求
自然语言范围清楚的小功能或 Bug仍要写 Non-goals 和验收
本地意图文件内容较长或需要团队先审阅提供明确文件路径和优先级
Issue / 工单团队已有单一需求入口确认 Agent 能访问，并核对工单是否过时
既有 BMAD Story想用 Quick Dev 快速实现某一 StoryQuick Dev 会读取内容，但不要假设它自动维护全部 Sprint 语义
步骤 4

认真审批短 Spec，这是最重要的前置门禁

当前版本 Quick Dev 通常直接生成带状态的 spec-{slug}.md，支持多个并行会话使用不同文件。不要只看标题，要逐项检查执行边界。

Problem解决的是真实用户问题，而不是直接描述某个实现方案。确认
Scope只有一个目标；修改范围和明确不做均可判定。确认
Context引用了正确的 V1 事实、代码模式和 Project Context。确认
Acceptance正常、异常、边界、权限和回归结果都可观察。确认
Implementation文件、数据、API 和测试范围合理，没有暗含新架构。确认
Risk迁移、兼容、监控和回退与真实风险匹配。确认
不要批准“看起来差不多”的 Spec：批准后 Agent 会更长时间自主执行。一个模糊词可能扩散成错误数据结构、错误权限或大量无关改动。

批准时可直接回复

我确认当前 Spec 的目标、范围、Non-goals、验收和 V1 回归边界。
请按该 Spec 实现。任何超出边界的新产品决策、架构决定、不可逆数据变化或权限变化必须停止并询问，不得自行扩大范围。
步骤 5

让 Quick Dev 实现，但要求它提供真实验证

实现阶段应当读取实际代码、复用现有模式、修改最小必要范围并同步测试。不要把“代码生成完成”等同于“功能完成”。

代码约束

  • 复用 V1 现有模式
  • 避免顺手大重构
  • 兼容既有数据/API
  • 记录所有实际修改文件

测试约束

  • 覆盖每条验收标准
  • 补边界与错误路径
  • 运行相关 V1 回归
  • 报告命令和真实结果

停止条件

  • 需要新产品决定
  • 需要改变核心架构
  • 发现不可逆迁移风险
  • 现有事实发生冲突
验证证据至少包含：执行了哪些测试、通过/失败数量、未运行的测试及原因、构建/类型/Lint 结果、受影响 V1 路径的回归结果。仅写“测试通过”信息不足。
步骤 6

理解 Review 的三类结果，修在正确的层

发现类型例子处理方式
当前实现问题空值崩溃、权限绕过、AC 未实现、测试错误在本次 Quick Dev 中修复并重新验证
意图或 Spec 问题Agent 实现正确，但需求理解本身错了回到意图/Spec，重新批准后再实现，不用补丁掩盖
无关历史问题Review 发现相邻模块旧 Bug，但非当前变更导致记录到 deferred-work.md，另开 Quick Dev

Quick Dev 的 Review 重点不是找得越多越好，而是对发现进行分流，保持当前变更聚焦。Review Trail 应追加到 Spec 或相应实施产物中，让你看到发现、决定和修复结果。

不能延期的发现：当前改动引入的回归、未实现的验收、数据破坏、权限绕过、安全漏洞、虚假的任务完成声明。把这些写进 deferred work 等于带病交付。
步骤 7

最终验收：看 Diff、证据和用户结果

核对用户可见结果

按 Spec 的验收标准实际走一遍功能，不只看单元测试。确认成功、失败、空态、刷新、重复操作和权限差异。

核对变更范围

查看实际 Diff 和文件清单。任何未在 Spec 范围内的修改都需要解释，无法解释就撤出本次变更。

核对测试与 Review Trail

确认测试真实运行，所有当前变更相关的高风险问题已关闭，延期项确实与本功能无关。

决定交付或继续修复

只有证据满足 Definition of Done 才合入或发布。若已生成本地提交，也应先由人确认后再推送或创建 PR。

范围实际变更等于批准的 Spec，无偷偷加料。通过
行为所有验收和关键 V1 回归均有证据。通过
质量构建、类型、Lint、测试和 Review 达标。通过
运营需要时具备日志、监控、数据校验和回退方案。通过
多功能策略

2–3 个小功能：串行跑 2–3 次 Quick Dev

Quick Dev 的基本单位是一个连贯目标，不是一个版本。V1.1 可以包含多个 Quick Dev 结果，但每次运行必须独立。

A
功能 A：新对话 → Quick Dev → 验收 → 独立变更

完成后记录受影响模块、测试和延期事项。

Run 1
↓
B
功能 B：基于合入后的最新代码重新扫描

不要复用 A 的长对话；若依赖 A，在意图中显式写明。

Run 2
↓
C
功能 C：独立 Spec、实现和 Review

如果 C 暴露共享架构风险，停止并升级流程。

Run 3
↓
R
V1.1 版本级组合回归

验证 A+B+C 的交互、共享数据、权限、性能和 V1 关键路径。

Release

为什么不一次输入三个功能

  • 无法清楚判断每个功能是否完成。
  • Review 很难区分问题属于哪个变更。
  • 一个功能失败时难以独立回退。
  • 上下文扩张会增加 Agent 漂移和顺手重构。
  • deferred work 容易与另一个功能的正式范围混淆。
允许合并的例外：多个动作共同构成一个不可分割的用户结果，例如“增加筛选开关并显示对应结果计数”。若每个动作单独交付没有用户价值，可以作为一个 Quick Dev 目标。
版本门禁

Quick Dev 完成后仍要做 V1.1 组合回归

层级验证内容通过标准
单功能每次 Quick Dev 的 Spec、验收、测试和 Review各自独立通过
功能组合2–3 个功能是否共享状态、数据、权限或组件并产生冲突组合路径通过
V1 回归登录、权限、主交易/主流程、数据写入、关键查询无新增回归
非功能性能、安全、可访问性、日志、告警、兼容满足原 V1 或本次明确阈值
发布运营迁移、灰度、监控、数据校验、回退或前向修复有真实证据和责任人
Quick Dev 不负责替代发布治理：它交付的是一个小目标的实现闭环。多个闭环组成版本时，仍需要版本级测试、发布审批和上线观察。
退出条件

出现这些信号，停止 Quick Dev 并升级流程

需求与产品信号

  • 无法收敛成一个目标
  • 验收存在多种产品解释
  • 需要改变正式业务规则或 NFR
  • 涉及多个角色和复杂流程重设计

技术与风险信号

  • 需要新架构、重大 ADR 或跨系统协调
  • 权限、安全、计费、租户边界变化
  • 不可逆迁移或大规模数据修复
  • 回归面无法在局部上下文内判断

升级后的推荐路径

停止当前 Quick Dev，不继续实现。

1. 将已澄清意图沉淀为正式 SPEC 或 PRD 增量。
2. 按影响更新 UX / Architecture / Project Context。
3. 创建增量 Epic 与 Stories。
4. 执行 Implementation Readiness。
5. 进入 Create Story → Dev Story → Code Review 的完整循环。
完整示例

示例：订单列表记住上次有效筛选

这是一个适合 Quick Dev 的 V1 增量：单一用户结果、复用现有页面和筛选逻辑、不改变权限、不增加跨设备同步。

输入意图

bmad-quick-dev

目标：让运营人员再次进入订单列表时，恢复该用户上次提交成功的有效筛选条件，减少重复设置。

V1 当前行为：
- 每次进入列表都使用默认筛选。
- 已有筛选组件、URL 参数解析和“清除筛选”功能。

本次范围：
- 在当前浏览器保存当前用户最后一次有效筛选。
- 再次进入列表时恢复；无效或已下线的筛选项自动丢弃。
- 点击“清除筛选”同时清除保存值并恢复 V1 默认值。

Non-goals：
- 不做跨设备同步。
- 不新增数据库字段或后端 API。
- 不改变默认权限、查询逻辑、排序和结果字段。
- 不重构整个列表状态管理。

验收：
1. 用户提交有效筛选后离开并返回，筛选与结果一致恢复。
2. 保存值损坏、版本过旧或包含无效选项时安全回到默认值。
3. 不同用户不读取对方筛选。
4. 清除后刷新仍保持默认值。
5. 原有 URL 筛选优先级按现有规则执行，不产生循环覆盖。

相关输入：project-context.md、订单列表页面、筛选状态模块和现有 E2E 测试。
任何涉及后端存储、跨设备同步或权限变化的方案必须停止并询问。

预期 Spec 要点

边界

浏览器本地、当前用户、现有筛选 Schema；不触碰服务器数据。

实现

复用已有序列化/校验模式；读失败安全回退；清除动作原子更新 UI 与存储。

测试

恢复、清除、损坏值、用户隔离、无效选项、URL 优先级与 V1 默认行为。

Review 中应重点攻击

  • 是否把敏感筛选条件以不安全方式持久化。
  • 用户切换后是否误读上一个用户的值。
  • 保存值损坏是否导致白屏。
  • URL、默认值和本地值是否形成覆盖循环。
  • 筛选项下线后是否仍发出无效查询。
  • “清除筛选”是否只清 UI 而未清存储。

不要只报告“测试通过”。请列出实际执行的构建、类型、Lint、单元、集成、E2E 和回归验证；给出通过/失败数量、未运行项及原因，并逐条映射 Spec 验收标准。
模板 5：最终验收
请按最终验收格式交付：
1. 用户可见变化；2. 实际修改文件；3. 每条验收的证据；4. 测试结果；5. Review Trail；6. 已修复问题；7. deferred work；8. 剩余风险；9. 回退建议；10. 是否建议交付及理由。

FAQ

常见问题

Quick Dev 会不会完全不生成 Spec？

它会根据扩散面选择最小安全路径。极小的一次性改动可能直接实现；其他改动会先形成短 Spec 并要求批准。当前版本通常使用带状态的 spec-{slug}.md，不是固定单例文件。

能否把三个小功能一起交给 Quick Dev？

如果是三个独立用户结果，不建议。分别运行三次，最后做版本级组合回归。只有多个动作共同构成一个不可分割目标时才合并。

Quick Dev 会读取原 PRD、UX 和 Architecture 吗？

当前工作流具备规划产物感知能力，会选择性加载相关内容。你仍应在输入中指出权威文件和冲突处理规则，避免它读取旧稿或错误分片。

Quick Dev 的自我 Review 是否足够？

不够。它能提高发现率，但不能替代人工 Diff Review、CI、真实环境验证、安全/性能检查和发布治理。高风险项目可再使用独立代码审查或 TEA 测试门禁。

发现旧代码问题，要不要顺手修？

只有该问题由当前变更引入或阻断当前验收时才在本次修复。其他问题写入 deferred work，另开一次 Quick Dev，避免范围失控。

什么时候应该放弃 Quick Dev？

当需求不清、扩散面跨多个系统、需要新架构决定、改变权限/计费/核心状态、包含不可逆迁移，或团队需要正式长期文档时，升级到增量 Full Method。

HTML 为什么双击就能用？

本文件把样式和交互脚本全部内嵌，没有在线字体、图片、CSS、JavaScript 或接口请求。浏览器直接打开本地文件即可。

最终记忆句：Quick Dev 的速度来自“一个目标、一个冻结边界、一次长执行”，不是来自跳过质量。对已有 V1，先保护基线，再让 Agent 快。
