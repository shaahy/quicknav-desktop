00

先把五个对象放在同一层理解

它们本来并不完全同类。若不先校准，比较会产生“拿执行方法和文档策略比速度”的错觉。

重要校正 Spec Kit 的 Flow-Forward 是规格持久化模型，不是单独的 CLI 工作流。本文所称“Spec Kit Flow-Forward”，指使用 Spec Kit 的 Specify → Plan → Tasks → Implement 主链路，并约定已完成 feature 目录不再修改；需求变化时新建 feature 目录。[S4][S5]
表 0-1｜五种方式的类型与公平比较口径
方式本质类型本文如何操作化主要解决的问题不天然解决的问题
直接与大模型对话 无固定流程的基准方式 在同一或连续对话中描述需求，让模型直接读代码、修改、测试 以最低启动成本快速得到代码改动 长期规格、变更留痕、稳定 Gate、跨会话一致性
Superpowers 技能驱动的软件开发方法 Brainstorming → worktree → plan → TDD 实现 → 双阶段审查 → 收尾 把工程纪律强制嵌入 Agent 行为，减少“说完成但没验证” 产品级长期主规格的持续合并与治理
OpenSpec 面向增量变化的规格协议层 Explore/Propose → delta specs/design/tasks → Apply → Verify（expanded profile）→ Archive 区分“当前事实”与“拟议变化”，完成后把增量合回真相源 默认并不等于严格 TDD、独立代码审查或分支治理
BMAD Quick Dev 低人工中断的一体化快速开发流 压缩意图 → 判断一击直达或完整路径 → 冻结 spec → 实现 → 分层审查 在安全边界足够清楚后，让模型长时间自主执行 跨大量增量变更的长期规范合并，不是其核心定位
Spec Kit Flow-Forward SDD 主链路 + 不可变历史约定 每次变化建立新 feature 目录；旧 spec/plan/tasks 保留为历史记录 获得清晰时间线、审核证据和“当时为何这样做”的可追溯性 跨 feature 的统一当前视图，需要额外索引、链接或汇总习惯

02

工作链路：从一句需求到可合并代码

比较的不只是步骤数量，而是每一步是否产生稳定边界、谁负责确认、失败时回退到哪里。

表 2-1｜端到端链路对照
阶段直接对话SuperpowersOpenSpecBMAD Quick DevSpec Kit Flow-Forward
0. 入口 “帮我增加收藏功能” 识别为创造性工作 → 自动触发 brainstorming /opsx:explore（可选）或 /opsx:propose 输入意图、Issue、计划文本或 Story 内容 为本次变化新建 feature 目录
1. 需求收敛 取决于提示词；模型可能边问边改，也可能直接假设 逐项澄清、给出备选方案、分段展示设计并要求批准 Explore 先读代码和讨论选择；Proposal 固化 why/what 把杂乱请求压成单一、无矛盾、可执行目标 在新 spec.md 中描述此次变化，不改旧 feature
2. 规格/设计 通常存在于对话；除非主动要求写文件 保存设计文档，再生成细粒度实现计划 proposal → delta specs → design → tasks，各产物可回访 小且零爆炸半径可直达；其余生成并批准冻结 spec spec.md → plan.md，并保留历史目录
3. 隔离/准备 不固定；可能直接改当前分支 创建 Git worktree/分支、执行项目设置、验证干净基线 工具本身以规格目录为中心；分支/worktree 需项目约定补充 依赖具体宿主和配置；重点是安全边界而非固定 Git 策略 feature 目录天然分隔文档；代码分支仍需另行约定
4. 任务拆解 可临时列 Todo，也可能整块生成 任务细到约 2–5 分钟，包含文件、代码、命令和预期结果 tasks.md 作为变更内清单，Apply 时逐项勾选 完整路径才规划；一击直达路径省略不必要拆解 生成 tasks.md，作为该 feature 的永久历史组成
5. 实现 模型直接编辑、运行测试；行为高度依赖当前提示 子代理逐任务或批次执行；严格 RED → GREEN → REFACTOR Apply 按已批准工件实现并更新任务状态 在清晰边界内长时间自主执行，减少中途打断 Implement 按 tasks 执行，不回写旧 feature 产物
6. 审查 需显式要求；同一上下文可能出现自证偏差 先查规格符合性，再查代码质量；关键问题阻断 可用 expanded profile 的 Verify 对照实现与工件；它报告问题但不自动阻断 Archive [S6] 审查发现按意图层、规格层、局部实现层分流修正 内置工作流可设 spec/plan Gate；实现审查需配置或补充
7. 收尾 通常给出“完成”摘要；规格是否同步不确定 跑完整验证，选择合并/PR/保留/丢弃并清理 worktree Archive 把 delta 合入 openspec/specs/ 并归档 change 人最终验收；局部问题局部修，边界问题回退重生 关闭 feature 并保持目录不可变；下一次变化另起目录
为什么“失败回退层级”比多跑一次测试更重要？

意图错误代码越补越偏，测试只证明错误需求被稳定实现重新澄清目标和边界BMAD Quick Dev、Superpowers Brainstorming

人机控制：你的注意力花在哪里

“人工轮次少”不等于“失去控制”。关键是把人放在高杠杆决策点，而非频繁批准机械动作。

表 4-1｜确认点、自主性与偏差控制
控制问题直接对话SuperpowersOpenSpecBMAD Quick DevSpec Kit Flow-Forward

强制停点 没有天然停点 设计批准、计划疑问、审查 Critical、分支收尾选择 主要靠团队约定；工件是 enabler，不被设计成僵硬瀑布 Gate 目标矛盾、无法安全推断、最终验收、问题需回退上层 官方 workflow 可在 spec 与 plan 后配置审批 Gate

注意：这里是相对结构判断，不是实测工时承诺。真实成本取决于仓库规模、模型、测试速度、上下文窗口、团队纪律与变更风险。

选型规则：先问四个问题

选择不是从工具名开始，而是从变化的风险、寿命、协作和审计要求开始。

表 10-1｜四问决策法
顺序问题如果“是”如果“否”
Q1出错是否会影响数据、安全、资金、权限、迁移或多个模块？不要直接对话；进入 OpenSpec/Flow-Forward，并采用 Superpowers 质量执行继续 Q2
Q2本次需求是否小、明确、可逆，并有确定性回归验证？优先 BMAD Quick Dev；极小变化可直接对话继续 Q3
Q3未来是否会频繁修改同一能力，需要随时回答“当前行为是什么”？优先 OpenSpec，完成后必须 Verify + Archive继续 Q4
Q4是否必须保留每个阶段当时的批准内容，且不能被后来改写？采用 Spec Kit Flow-Forward，并维护 lineage 索引OpenSpec 或 BMAD Quick Dev 即可；按质量风险叠加 Superpowers
表 10-2｜三档流程路由，可直接写进团队约定
通道进入条件推荐流程最低 Gate禁止项
L1 微改通道 单文件/局部、可逆、无模型变化、回归命令确定 直接对话或 BMAD Quick Dev 一击直达 先读相关代码；展示 diff；运行定向测试和构建 不得涉及数据迁移、权限、安全、公开 API
L2 标准增量通道 新增用户行为、跨 2–3 模块、需要长期记住 OpenSpec change → Apply → Verify → Archive；关键逻辑使用 TDD Proposal/spec 批准；测试绿；主规格合并审查 不得跳过 Archive 后声称完整闭环
L3 高风险通道 安全、支付、迁移、并发、一致性、不可逆操作、合规 OpenSpec 或 Flow-Forward + Superpowers 完整执行/独立审查 规格 Gate、设计 Gate、RED/GREEN、独立双审、回滚/恢复演练 不得自主推断关键产品/安全决策；不得以内部测试代替发布批准

总结建议：用 OpenSpec 管变化，用风险决定执行重量

这是针对“已完成 MVP V1.0，后续持续增量”的建议，不是绿地项目的通用答案。

表 11-1｜最终建议
建议层级选择理由落地规则
默认主干 OpenSpec 它最直接解决 MVP 后的核心矛盾：既要快速改变既有系统，又要让完成后的规格重新描述当前现实。delta specs 避免每次重写全量规格，Archive 关闭变化闭环。 每个非微小用户行为建立 change；完成定义必须包含 Verify、Archive 和主规格 diff 审查。
执行质量层 按风险引入 Superpowers OpenSpec 擅长管理“为什么改、改什么、最终事实”，Superpowers 擅长“怎样把这次代码做扎实”。二者职责互补，不必让每个文案改动都走完整 TDD 仪式。 L2 的关键逻辑使用 TDD/完成验证；L3 使用 worktree、细粒度计划、规格审查、代码质量审查和分支收尾。
快速通道 BMAD Quick Dev 边界明确的小中型功能，最适合先集中压缩意图，再减少人工中断。它比无流程直接对话更安全，又比完整 SDD 更轻。 只有目标无矛盾、影响范围可枚举、外部依赖已确认时才能进入长跑；行为变化仍要回写长期规格。
微改例外 直接对话 对确定性、低风险、可逆改动，流程成本可能超过实现价值。 限制在 L1；至少保留目标/非目标、diff、测试证据。跨模块或修改数据模型立即升级。
审计升级 Spec Kit Flow-Forward 当“不允许后来改写当时批准内容”比“随时看到统一当前规格”更重要时，不可变历史才值得其碎片化成本。 必须同时维护 capability index、supersedes 链与当前状态摘要，否则不要选。
一句话落地： 不建议在五种方式里只选一个并强制覆盖全部变化。建议建立三档路由：微改用直接对话/Quick Dev，标准功能以 OpenSpec 为主干，高风险功能在 OpenSpec 或 Flow-Forward 之上叠加 Superpowers 的 TDD、隔离与独立审查。
表 11-2｜如果你坚持只选一种
你的首要目标只选一种时你必须接受的代价
最快交付且自己能持续盯住BMAD Quick Dev需另建长期规格同步规则
长期持续迭代且当前事实可信OpenSpec需补强 TDD、Git 隔离和独立代码审查
工程质量和验证纪律优先Superpowers流程较重，产品级主规格仍需另外维护
合规审计和不可变历史优先Spec Kit Flow-Forward必须治理重复、索引和演进链
