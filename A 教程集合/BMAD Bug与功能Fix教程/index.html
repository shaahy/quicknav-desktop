先看结论

清晰的小缺陷用 Quick Dev；不清楚的缺陷先诊断，不要猜着改

BMAD 当前对 Bug Fix、局部功能调整和小范围重构的默认路径是 bmad-quick-dev。但“快速”不是直接改代码：必须建立复现、期望行为、根因证据、失败测试、修复范围、回归面和回退方式。

默认闭环：缺陷分级 → 收集证据 → 稳定复现 → 写失败测试 → Quick Dev 修复 → 测试与自检 → bmad-review 独立复核 → 人工验收 → 合入/Hotfix → 观察与关闭。
普通 Bug

行为偏离已确认事实

按 V1 既定需求恢复正确行为，不新增产品范围。

功能 Fix

功能已做但不完整

先判断是实现漏项，还是需求真的发生变化。

Change Request

本质是新需求

不能包装成 Bug 绕过产品、UX 或架构评审。

定义

先分清三件事，否则会在错误层修复

类型判断标准事实来源推荐动作
Bug实际行为偏离已经确认并仍有效的要求生产基线、最终 PRD/UX/Architecture、验收与测试恢复正确行为，补回归测试
功能 Fix功能已存在，但某条已确认能力、状态或边界未实现原 Story/Spec/AC、正式产品事实按漏项修复；若事实不清则先澄清
新需求用户现在希望系统表现得不同，但旧实现符合原要求新业务意图走增量 Spec/PRD/UX/Architecture，不伪装为 Bug
关键问题：“系统做错了，还是我们现在想法变了？”前者修代码，后者更新意图和事实源。不能用补丁把需求变化藏在实现里。
分级

严重度决定发布速度，风险决定流程强度

等级用户/业务影响处理方式最低证据
P0 / 紧急安全、资金、数据破坏、全站不可用、合规事故先止血与隔离；Hotfix 最小变更；并行准备回退和事后完整修复复现或生产证据、影响范围、审批、验证、监控、回退
P1 / 高核心路径大量失败，无可靠替代方案高优先 Quick Dev；独立 Review；针对性回归；灰度发布稳定复现、失败测试、根因、回归和观察
P2 / 中局部功能异常，有替代路径正常 Quick Dev 周期复现、测试、Review、人工验收
P3 / 低轻微文案、样式、低频边界批次排期，但每次仍保持单一目标验收与相关回归

严重度由用户影响决定，不由修复代码行数决定。一个单行权限 Bug 可能是 P0。

步骤 1

用缺陷事实包代替“这里好像有问题”

# Bug / Feature Fix Intake

## 标识与严重度
- Bug ID：BUG-___
- 环境/版本：
- P0 / P1 / P2 / P3：

## 实际行为
- 用户看到了什么
- 错误信息、状态码、日志或错误数据

## 期望行为
- 对应的最终 PRD / UX / Architecture / Story / Spec / AC

## 复现步骤
1. 前置数据与权限
2. 用户操作或 API 输入
3. 实际结果
4. 发生比例与时间条件

## 影响范围
- 用户 / 租户 / 数据 / 接口 / 浏览器 / 地区 / 版本

## 已知证据
- 日志、Trace、截图、请求、数据快照、相关提交

## 回归边界
- 修复后必须保持不变的 V1 行为

## Non-goals
- 本次不做的重构、新功能和历史问题
隐私要求：不要把真实密码、Token、Cookie、身份证号、支付数据或个人信息直接粘进缺陷包。使用脱敏数据和可控测试账号。
步骤 2

没有稳定复现时，先诊断，不要直接尝试修复

固定变量

记录代码版本、配置、环境、权限、测试数据、时间、网络和依赖版本。一次只改变一个变量。

建立最小触发

从完整用户路径缩小到最少输入；同时保留一个不会触发的对照组，避免把相关性当因果。

沿因果链找边界

UI 输入 → API 请求 → 业务服务 → 数据写入 → 异步任务 → 返回/展示。找到“最后一个正确状态”和“第一个错误状态”。

记录根因置信度

“怀疑”不是根因。根因至少应能解释复现、代码路径和为什么此前测试没抓住。

偶发生产 Bug：优先补观测性、采样、关联 ID、错误上下文和安全重放条件。不要为了“试试看”连续提交多个无证据补丁。
步骤 3

回归测试先行：先让测试因 Bug 失败

红

在未修代码前，新增测试稳定失败，并且失败原因就是报告中的缺陷。

绿

最小修复后测试通过；不是放宽断言、吞错误或改测试迎合实现。

防复发

运行邻接边界和 V1 回归，证明修复没有把问题转移到别处。

测试必须覆盖两个维度

用户路径

用户通过真实入口操作时，页面、API、错误提示、重试和最终结果正确。

状态不变量

即使绕开 UI、并发、刷新或重放，请求也不能破坏权限、余额、库存、状态机或审计约束。

示例：按钮禁用测试只能证明 UI 挡住用户，不能证明直接 API 调用也被拒绝。权限或状态 Bug 必须同时测入口和底层不变量。
步骤 4

在新对话中用 bmad-quick-dev 修复一个缺陷

bmad-quick-dev

这是一个已上线 V1 的缺陷修复。本次只修复 BUG-[编号]：
[粘贴缺陷事实包]

执行要求：
1. 读取 project-context.md、相关最终事实源、现有代码、测试和最近相关变更。
2. 先复现问题并建立修复前失败的回归测试；无法复现时停止在诊断阶段。
3. 区分已证实根因、候选原因和未知项，不得把猜测写成结论。
4. 形成最小修复 Spec，列出 Non-goals、风险、回归面和回退方式，等我批准。
5. 只修改最小必要因果链，不顺手重构或修复无关历史问题。
6. 修复后运行针对性测试、邻接边界测试和受影响 V1 回归。
7. 执行对抗式 Review；当前修复相关问题必须关闭，无关问题写入 deferred-work.md。
8. 最终提供实际 Diff、测试结果、Review Trail、剩余风险和发布建议。

以上内容输入 AI IDE 对话，不是网页启动命令。

已知根因可以直接进入 Quick Dev；未知根因仍可使用 Quick Dev，但必须明确“先调查、未复现不修改”。这样不会把临时猜测固化成代码。
步骤 5

审批修复 Spec：因果链必须闭合

复现输入、环境、步骤和实际错误可重复。有证据
根因解释了为什么发生、影响谁、为什么测试没抓住。可证伪
修复修改点直接切断根因，不是掩盖症状。最小化
测试修前失败、修后通过，含邻接和不变量。已设计
范围Non-goals 清楚，未混入新需求和大重构。已冻结
发布风险、监控、数据校验、灰度和回退可执行。已定义
拒绝以下 Spec：“可能是缓存问题，所以清缓存”；“加个 try/catch 避免报错”；“把测试改成符合当前返回”；“顺便重构整个模块”。这些没有证明根因或扩大了风险。
步骤 6

实现最小修复，不把 Hotfix 变成重构项目

修因不修表

切断错误因果链；不能只隐藏报错、吞异常或强制刷新。

保持兼容

不破坏既有 API、数据、权限、事件、缓存和用户路径。

保留观测

错误不再发生，同时留下足够日志和指标验证效果。

限制扩散

无关重构和旧问题进入 deferred work，另开任务。

修复期间必须停止并升级的情况

  • 发现实际期望行为没有被正式确认。
  • 需要新增架构、改变权限/计费/核心状态机。
  • 需要不可逆数据修复或跨多个系统协调。
  • 原根因无法解释新证据，修复方向已经失效。
步骤 7

Quick Dev 内部 Review 后，再用 bmad-review 做独立复核

Quick Dev 会自检并做对抗式 Review。高风险或生产缺陷建议在新对话中再对最终 Diff 运行多视角复核：

bmad-review

审查 BUG-[编号] 的最终 Diff、修复 Spec、失败测试和测试结果。
请启用适用的对抗、边界条件和验证缺口视角，重点检查：
- 根因是否真的被切断，而非掩盖症状；
- 并发、空值、超时、重试、重复提交、权限和数据边界；
- 改变的行为是否都有可靠测试；
- 修复是否引入新的兼容、性能、安全或观测问题；
- 文件清单、Spec 声明和实际 Diff 是否一致。
请区分当前修复必须解决的问题与无关历史问题。
人工过滤仍然必要：对抗式 Review 会主动找问题，可能产生误报。逐项核实证据；不能因为 Agent 找够了若干条问题，就假设剩余代码安全。
步骤 8

验证与关闭：Bug 消失不等于修复完成

验证层要证明什么证据
原始复现相同输入和环境不再出现缺陷复现脚本/步骤结果
回归测试修前失败、修后通过，未来能自动抓住测试名称与运行结果
邻接边界空值、最大值、并发、超时、重试、权限等没有新问题测试或可复核记录
用户路径真实入口、反馈、刷新、返回和重试正确人工/E2E 验收
状态不变量直接 API、并发和重放不能破坏数据与权限集成/契约测试
生产观察错误率下降，业务与系统指标无异常监控、日志、数据校验

若缺少端到端覆盖，可按项目条件使用 bmad-qa-generate-e2e-tests 补 API/E2E 测试；它只负责测试生成与执行，不能替代代码 Review。

回退

回退策略必须在发布前确定

代码可回退

通过版本控制创建反向变更或恢复上一制品；避免覆盖式回退丢失他人变更。

数据可恢复

数据库迁移要么可逆，要么有前向修复；先备份并验证恢复路径。

功能可隔离

使用已有功能开关、灰度或流量控制；不要临时创造未经验证的开关体系。

触发回退的条件

  • 原缺陷未下降或出现新 P0/P1。
  • 核心业务、权限、数据一致性或性能指标越线。
  • 迁移数据数量、约束或审计不符合预期。
  • 无法在既定观察窗口内证明安全。
实战示例

三类常见 Fix

示例 A：登录过期后页面白屏

复现：会话过期后从深链接进入，接口返回未认证，页面继续读取空用户对象。

失败测试：模拟过期会话，预期跳转登录页并保留安全返回地址，不渲染受保护内容。

最小修复：在统一会话边界处理未认证状态；不在每个页面散落空值判断。

回归：正常登录、权限不足、主动退出、刷新、多个标签页、返回地址白名单。

示例 B：重复点击导致重复扣减

严重度：涉及资金/权益/库存，通常至少 P1，可能 P0。

失败测试：同一幂等键并发提交两次，只允许一次状态变化和一条有效审计。

最小修复：在服务/数据原子边界实现幂等，不只禁用按钮。

回归：超时重试、网络重放、不同幂等键、失败重试、回滚与审计一致性。

示例 C：功能 Fix，导出文件缺少当前筛选

先判定：如果原 Spec/AC 已要求“导出当前筛选结果”，这是功能漏项；如果原来只导出全部数据，而现在新提出按筛选导出，这是新需求。

失败测试：给定筛选条件，导出内容必须与当前用户可见结果集合一致。

风险：权限字段、分页全集、排序、时区、大数据量、公式注入和敏感信息。

升级信号：若需要新异步任务、权限策略或大规模导出架构，应进入增量完整流程。

质量门禁

四个 Gate，一个都不能用“应该没问题”代替

G1 Evidence类型、严重度、实际/期望、影响和复现证据清楚。才可修
G2 Fix Spec根因可证伪，最小修复、Non-goals、测试和回退已批准。才可改
G3 Verification修前失败、修后通过；边界、用户路径和状态不变量通过。才可合
G4 Release独立 Review、灰度/发布、监控、数据校验和回退证据齐全。才可关

FAQ

常见问题

所有 Bug 都直接用 bmad-quick-dev 吗？

清晰、局部、风险可控的 Bug 最适合。无法复现的 Bug先诊断；涉及安全、资金、核心状态、不可逆数据或新架构时，升级正式流程和更强审批。

是否必须先写失败测试？

原则上应该。它证明测试能捕捉真实缺陷，并防止复发。若环境限制暂时不能自动化，至少保留确定性复现脚本/步骤，并创建明确的补测项；高风险缺陷不能以此长期豁免。

bmad-review 和 bmad-code-review 有什么区别？

bmad-review 是核心多视角审查工具，可直接审 Diff、文件或文档；bmad-code-review 是完整 Story 实现循环中的代码审查工作流。普通 Quick Fix 可优先用前者独立复核，Story 开发使用后者。

功能缺了一项，为什么可能不是 Bug？

如果这项能力从未在已确认需求或验收中出现，它就是新的期望，不是实现偏差。应先更新意图和事实源。

紧急 Hotfix 可以不 Review 吗？

不建议。可以缩短范围和使用针对性验证，但风险越高越需要独立审查。至少由不同上下文/不同人核对 Diff、测试、数据和回退。

为什么既要测 UI 路径，又要测状态不变量？

UI 可以阻止普通点击，但直接 API、并发、重放或内部写入仍可能绕过。只有两层都通过，才能证明权限和业务状态没有被旁路破坏。

HTML 是否需要本地服务器？

不需要。本文件内嵌全部样式和脚本，没有模块加载、在线资源或接口请求，双击即可打开。

最终记忆句：好的修复不是“改完不报错”，而是“复现被测试抓住、根因被最小改动切断、邻接边界没有新回归、生产指标证明问题消失”。
