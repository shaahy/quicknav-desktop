01 · START HERE

先记住一句话

Superpowers 管好“怎样可靠地开发”；线上产品还需要一层“怎样安全地发布”。两层都通过，才是可上线候选。

最重要的红线：“测试通过”“分支完成”“PR 已创建”都不等于生产上线获批。Superpowers 的 finishing-a-development-branch 终点是代码集成决策，不是灰度、监控和回滚完成。
SUPERPOWERS 原生

开发可信度

需求先设计、隔离工作、细粒度计划、测试先行、逐任务审查、用新鲜证据声明完成。

生产工程补充

发布可逆性

向后兼容、expand/contract 迁移、功能开关、灰度、指标阈值和回滚演练。

人工 GATE

风险所有权

合并、推送、部署、数据变更和删除必须由有权限的人做出明确决定，Agent 不代替业务负责人。

02 · OPERATING MODEL

正确模型：内层开发循环 + 外层生产闭环

内层 · Superpowers

把变更做对

  1. brainstorming：理解与批准设计
  2. using-git-worktrees：隔离 + 绿色基线
  3. writing-plans：可执行的小任务
  4. subagent-driven-development：逐任务实现与审查
  5. test-driven-development：RED → GREEN → REFACTOR
  6. verification-before-completion：证据后置声明
  7. finishing-a-development-branch：集成选择
→
外层 · 生产保护

让改变可安全落地

  1. 冻结 V1.0 事实与回归基线
  2. 声明兼容、迁移、观测和回滚合同
  3. 合并后在准生产环境重验
  4. 先迁移再开功能，按比例灰度
  5. 用指标阈值决定继续、暂停或回滚
  6. 确认稳定后再做 contract 清理
来源边界：左侧技能名与纪律来自 Superpowers 6.2.0；右侧是本教程针对已上线系统补充的通用生产工程做法。不要把右侧描述成官方 Superpowers 自带的部署系统。
03 · CODEX SETUP

先让技能真正可用

Superpowers 会自动匹配相关技能，但“自动”不代表可以忽略环境检查。以下安装动作本身需要联网；安装完成后，本教程可完全离线阅读。

CODEX APP

推荐主线

  1. 打开 Codex 侧边栏的 Plugins。
  2. 在 Coding 分类找到 Superpowers 并安装。
  3. 重启或新开任务，让技能清单刷新。
  4. 确认能看到 brainstorming、writing-plans 等技能。
CLAUDE CODE 对照

插件市场安装

/plugin install superpowers@claude-plugins-official

也可使用 Superpowers 自有 marketplace；团队应固定一种安装来源，避免不同机器技能版本漂移。

Codex 多智能体开关

subagent-driven-development 需要 Codex 的多智能体能力。在 ~/.codex/config.toml 中配置：

[features]
multi_agent = true

保存后重新启动 Codex。如果当前宿主没有提供子智能体工具，就改用 executing-plans；不要假装已经做了独立审查。

Codex App 特例：如果任务已经位于宿主管理的 worktree，Superpowers 应检测并复用它。如果是 detached HEAD，开发仍可进行，但结束时通常要使用 App 的 “Create branch” 或 “Hand off to local”；不要强行再套一层手工 worktree。

05 · RUNNING CASE

贯穿案例：给任务管理 MVP 增加标签

示例技术栈为 React + Node.js + PostgreSQL。你的项目可替换命令和文件名，但 Gate 的语义不变。

V1.0 已上线事实
  • 任务具有标题、状态、负责人。
  • Web 与旧版移动客户端共同调用 GET /tasks。
  • 数据库中已有真实用户数据。
  • 当前版本标签为 v1.0.0，错误率 0.3%。
V1.1 最小增量
  • 任务最多绑定 5 个标签。
  • 创建、重命名、绑定、解绑。
  • 默认关闭，通过功能开关逐步开放。
  • 旧客户端忽略新增字段仍能正常工作。

明确不做

标签层级、自动化规则、跨空间标签、复杂搜索、标签统计均不属于本次 V1.1。YAGNI 不是少做质量，而是拒绝尚未被需求证明的功能。

06 · PRODUCTION BASELINE

第一步不是写代码，是冻结 V1.0 事实

如果不知道当前生产版本“本来就是什么状态”，后面的失败无法归因：究竟是新改坏的，还是基线已坏。

确认代码与生产对应关系

git status --short
git branch --show-current
git tag --points-at HEAD
git log -1 --oneline

若生产并非从当前 HEAD 发布，先找出真实 SHA。不要用“main 大概就是线上”替代证据。

跑完整绿色基线

npm ci
npm test
npm run typecheck
npm run lint
npm run build

记录命令、时间、退出码、测试数量和已有警告。基线失败时，先决定调查还是明确接受，不能默默带病开始。

冻结生产合同

合同V1.0 事实V1.1 约束
APIGET /tasks 返回既有字段只能新增可忽略字段，不删除/改义
数据所有任务都没有标签记录迁移后旧行仍合法，空标签等价于旧行为
客户端存在尚未强制升级的旧版本旧客户端必须继续读取与更新任务
性能P95 为 180ms灰度阶段 P95 不高于 220ms
业务错误率 0.3%标签相关错误率须低于 1%
可复制：让 Codex 做只读基线审计 
这是一个已经上线的 MVP V1.0。现在只做只读审计，不修改文件、不创建分支、不安装依赖。

请确认：
1. 当前 Git 分支、HEAD、工作区状态及与生产版本的对应证据；
2. 项目的测试、类型检查、Lint、构建命令；
3. 公开 API、数据库迁移、客户端兼容和运行时配置的位置；
4. 现有功能开关、监控和回滚机制；
5. 任何会阻止安全增量开发的基线问题。

07 · DESIGN BEFORE CODE

用 brainstorming 把“想加标签”变成可批准设计

Superpowers 要求任何创意性变更先做设计，即使它看起来很小。对已有产品，这一步的重点不是发散，而是识别旧行为和新行为的接缝。

示例中的三种设计方案

A. JSON 塞进 tasks

改动小，但查询、约束和并发更新变难；数据增长后容易形成债务。

B. 标签表 + 关联表

推荐。模型清晰、可约束、可查询；通过 additive migration 保持回滚空间。

C. 仅前端本地标签

无需服务端改动，但无法跨设备同步，不满足真实用户目标。

给设计文档增加生产附录：兼容矩阵、迁移顺序、功能开关、观测指标、回滚路径、明确不做。它们不是替代 Superpowers 设计，而是线上存量系统必须补充的约束。

08 · ISOLATED WORKSPACE

复用宿主隔离，必要时才创建 worktree

Superpowers 6.2.0 的顺序是：先检测已有隔离，再用平台原生工具，最后才回退到手工 git worktree。不要与 Codex App 的工作区管理打架。

检测 
git rev-parse --git-dir
git rev-parse --git-common-dir
git branch --show-current
git rev-parse --show-superproject-working-tree

git-dir != git-common-dir 且不是 submodule，说明已在 linked worktree。

禁止直接假设
  • 不要凭目录名判断是否隔离。
  • 不要在 main/master 上直接实现，除非用户明确同意。
  • 不要跳过绿色基线。
  • 不要在宿主管理 worktree 内再创建“幽灵 worktree”。

没有原生工具时的 Git 回退

# 先保证 .worktrees/ 被忽略
git check-ignore .worktrees

# 若未被忽略：先把 .worktrees/ 加入 .gitignore 并提交
# 然后创建隔离分支
git worktree add .worktrees/feature-task-labels -b feature/task-labels

Set-Location .worktrees/feature-task-labels
npm ci
npm test
基线失败：报告具体失败并询问是先调查还是在已知失败下继续。后者必须把“已知基线失败”写入计划，避免后续把它误判为本次回归。
09 · PLAN THE CHANGE

让 writing-plans 把设计拆成可独立审查的任务

计划不是待办标题集合。每个任务必须写明准确文件、接口、测试、期望失败、最小实现、验证命令和提交边界。

本案例的任务切片

任务独立交付物核心 RED生产约束
1标签领域规则与兼容合同第 6 个标签被拒绝；旧任务仍合法不改变既有任务字段语义
2additive schema migration空库、V1.0 快照都能升级旧服务面对新库仍可运行
3服务/API并发绑定不丢失；未知标签报错新增字段可被旧客户端忽略
4前端 UI + feature flag关闭时 DOM 与 V1.0 等价默认关闭，未授权用户不可见
5发布演练与观测开关切换、回滚脚本和仪表盘验收达到阈值才扩大灰度

10 · EXECUTION

优先用 Subagent-Driven Development

每个任务交给新实现者，任务完成后同时取得“规格符合度”和“代码质量”两项结论，整分支结束前再做一次全局审查。

1
读取计划并做 pre-flight发现计划冲突先停，不要让实现者猜
Controller
2
为 Task N 生成精确 brief只给本任务、接口、全局约束和必要上下文
Controller
3
实现者按 TDD 开发、自审、提交实现任务不能并行，避免写冲突
Implementer
4
任务审查spec verdict + quality verdict，Important 未关闭不得前进
Reviewer
5
修复与 scoped re-review修复后只复审相关 finding 和新破坏
Loop
6
整分支 final review审查完整 merge-base..HEAD，而非最后一个 commit
Reviewer
防止上下文压缩后重复开发：Superpowers 6.2.0 的 SDD 使用每个 plan 独立的 .superpowers/sdd/<plan-name>/progress.md 账本。恢复时以账本和 Git 历史为准，不以 Agent 的模糊记忆为准。

什么时候改用 executing-plans

宿主没有子智能体能力，或你选择在另一个任务中按批次执行计划时使用。它仍要求先检查隔离工作区、批判性审阅计划、创建待办并逐步验证；只是没有独立实现者和逐任务独立 reviewer。

11 · RED GREEN REFACTOR

TDD 的关键证据是“亲眼看到正确的失败”

测试先写不是形式主义。它证明测试能捕获缺失行为，而不是为已经写好的实现补一层装饰。

RED

写一个行为

一次只表达一个可观察行为。运行后必须失败，而且因为功能缺失，不是拼写或环境错误。

GREEN

最小实现

只写让当前测试通过的代码，不顺手增加导出、搜索、颜色规则等未被要求的能力。

REFACTOR

保持全绿

绿灯后才清理重复和命名。每次重构都重跑覆盖范围和旧行为回归。

RED：第 6 个标签必须失败

it('rejects a sixth tag without changing existing assignments', async () => {
  const task = await givenTaskWithTags(5);
  const before = await repo.listTags(task.id);

  await expect(service.assignTag(task.id, 'tag-6', 'user-1'))
    .rejects.toMatchObject({ code: 'TASK_TAG_LIMIT' });

  await expect(repo.listTags(task.id)).resolves.toEqual(before);
});
npm test -- tests/tasks/tag-service.test.ts
# 期望：FAIL，原因是 assignTag 尚未实现限制
# 不接受：模块找不到、数据库没启动、测试自己语法错误

GREEN：只实现上限与原子性

async assignTag(taskId: string, tagId: string, actorId: string) {
  return this.db.transaction(async (tx) => {
    const current = await tx.taskTags.lockAndList(taskId);
    if (current.length >= 5) {
      throw new DomainError('TASK_TAG_LIMIT');
    }
    await tx.taskTags.insert({ taskId, tagId, actorId });
    return tx.taskTags.list(taskId);
  });
}
已有代码没有测试怎么办：先为即将接触的旧行为补 characterization test（特征测试），确认它描述当前真实行为；再为新增行为进入 RED。不要借机重写整个旧模块。
12 · REVIEW LOOP

审查不是一句“看起来不错”

每个任务至少需要两个明确结论：是否忠实实现计划，代码本身是否可靠。实现者自审不能替代独立审查。

严重级别动作能否进入下一任务
Critical立即修复并复审不能
Important修复并做 scoped re-review不能
Minor记录到账本，最终整分支审查再裁决可以，但不能静默丢弃
与已批准计划冲突把 finding 与计划原文交给用户决定哪个有效暂停

审查输入必须是完整范围

BASE_SHA=<任务开始前记录的 SHA>
HEAD_SHA=$(git rev-parse HEAD)

git log --oneline $BASE_SHA..$HEAD_SHA
git diff --stat $BASE_SHA..$HEAD_SHA
git diff -U10 $BASE_SHA..$HEAD_SHA

不能用 HEAD~1 代替任务基线，因为一个任务可能包含多个提交；这样会让 reviewer 漏掉前面的改动。

收到评审意见时，怎样避免盲目照改
  1. 完整阅读，不先表态。
  2. 用自己的话复述技术要求。
  3. 对照当前代码、兼容合同和测试验证。
  4. 正确的逐项修复并逐项测试；错误的用证据反驳。
  5. 如果与用户批准的架构冲突，停止并让用户裁决。
13 · WHEN THINGS BREAK

线上 Bug 路线：先根因，后修复

systematic-debugging 的铁律是：没有完成根因调查，不提出修复。时间紧更需要证据，而不是更快地猜。

Phase 1 · 根因调查

完整错误、稳定复现、近期变更、多组件边界证据、从坏值向上追踪来源。

Phase 2 · 模式比较

找同库工作的类似实现，完整阅读参考，列出每一个差异和依赖假设。

Phase 3 · 单一假设

写下“我认为 X 是根因，因为 Y”，用最小变化一次只测试一个变量。

Phase 4 · TDD 修复

先写最小复现失败测试，只修根因，再做新鲜全量验证。

三次修复都失败：停止叠加第 4 个 patch，讨论架构。连续失败通常说明共享状态、耦合或基础假设有问题。 
生产现象：5% 灰度用户偶发丢失一个标签。

不要先改代码。请使用 systematic-debugging：
1. 给出稳定复现或需要补充的观测；
2. 追踪请求 → service → transaction → database 的数据流；
3. 对比同仓库中正确的并发写入模式；
4. 一次只提出并验证一个根因假设；
5. 确认根因后，先写失败回归测试，再实施单一修复。

输出事实、假设、证据与下一次最小实验。
14 · EVIDENCE BEFORE CLAIMS

“完成”是一项需要证据支持的声明

verification-before-completion 要求在当前状态上重新运行能证明该声明的完整命令，读取退出码和失败数量，然后才能下结论。

15 · FINISH THE BRANCH

分支结束必须由用户选择

完整测试全绿后，finishing-a-development-branch 检测当前 Git 环境、确认基分支，再让用户决定如何集成。

1. 本地合并

合并回确认过的基分支，并在合并结果上再次运行完整测试。通过后才清理 Superpowers 自己创建的 worktree。

2. Push + PR

创建远端分支和 PR，保留 worktree 处理评审反馈。不能因为 PR 建好就提前清理。

3. 保持原样

保留分支与工作区，由用户稍后处理。报告准确路径和分支名。

丢弃不在标准菜单中：只有用户主动要求丢弃时，才列出将永久删除的分支、提交和 worktree，并要求输入精确的 discard 确认。拒绝 push 时也不能擅自 force-push。

Codex App detached HEAD

此时不能本地 merge。完成提交和验证后，使用 App 的 “Create branch” 建立分支，或 “Hand off to local” 转交本地检出；教程中所有 merge/push/PR 均仍是用户 Gate。

回滚顺序

  1. 关闭 task_labels，先停止用户继续进入新路径。
  2. 确认旧路径恢复，观察错误率和延迟。
  3. 如代码本身影响旧路径，回滚到上一稳定二进制。
  4. 保留 additive schema 和已写数据，除非有经过验证的数据回退方案。
  5. 建立事故记录，用 systematic-debugging 找根因；不要在生产上连续猜修。

Prompt 1：设计增量功能

Prompt 2：创建实施计划 
设计已批准，路径为 [spec path]。
请使用 Superpowers writing-plans 创建实施计划。

要求：
- 每个任务有独立、可测试的交付物；

- 每个行为按 RED → 验证 RED → GREEN → 验证 GREEN → 提交拆分；

- 把兼容、迁移、开关、观测、回滚写入 Global Constraints；

Prompt 3：执行已批准计划 
执行 [plan path]。使用 Superpowers subagent-driven-development。

先确认当前是否已经处于 Codex App 管理的隔离工作区；不要强行创建嵌套 worktree。
逐任务执行，不在任务之间重复询问我。每个任务必须：
- 由实现者按 TDD 实现并自审；
- 获得 spec compliance 和 code quality 两项审查结论；
- 修复 Critical/Important 并 scoped re-review；
- 把进度、提交和 deferred minor 写入该 plan 的 SDD ledger。

只在真实阻断、计划冲突、权限/凭证、不可逆操作或合并/推送/部署 Gate 暂停。
Prompt 4：调查线上 Bug 
线上出现：[可观察症状]。
请使用 Superpowers systematic-debugging。现在不修改代码。

先完成根因调查：错误全文、稳定复现、近期变更、跨组件数据流证据。
然后找同仓库工作的相似模式，提出一个可证伪的单一假设和最小实验。
确认根因后，再用 TDD 写失败回归测试、实施单一修复并验证。
如果已经有 3 次失败修复，停止并讨论架构。
Prompt 5：完成声明前验证 
请使用 verification-before-completion。
对当前 HEAD 重新运行能够证明以下声明的完整命令：
- 新功能测试通过；
- V1.0 回归无破坏；
- 类型检查、Lint、生产构建通过；
- 旧客户端契约通过；
- V1.0 数据快照迁移通过；
- 功能关闭时行为等价于 V1.0。

报告命令、退出码、通过/失败数量和未执行项。
未获得证据的事项必须标记“未验证”，不要使用“应该没问题”。
Prompt 6：发布 Gate 评审 
代码开发和分支验证已完成。现在只做发布就绪评审，不执行部署。

检查：
1. additive migration 是否已在 V1.0 数据快照演练；
2. feature flag 是否默认关闭并可紧急关闭；
3. 旧客户端与旧服务兼容是否有证据；
4. 1% / 5% / 25% / 100% 灰度阈值和观察窗；
5. 仪表盘、告警、负责人和回滚步骤；
6. 哪些动作不可逆、需要谁批准。

输出 READY / NOT READY，以及每项证据。不要把测试通过等同于上线批准。

19 · FAILURE MODES

最常见的十个错误

1. “改动很小，不用设计”

小改动最容易隐藏兼容假设。设计可以短，但必须批准。

2. 在 main 上直接改

污染稳定分支，使回退和评审边界变模糊。

3. 测试写在实现之后

测试直接通过，无法证明它能捕获缺失行为。

4. 只跑新增测试

证明了新功能，不证明 V1.0 没被破坏。

5. 把空库迁移当真实迁移

真实风险在旧数据、异常值、索引锁和长事务。

6. reviewer 只看最后一个 commit

多提交任务的早期改动会被静默漏审。

7. Agent 报告成功就相信

必须看 diff，并在当前 HEAD 上独立运行验证命令。

8. PR 建好就清理 worktree

PR 反馈仍需要原隔离环境继续修复和复验。

9. schema 与代码同一按钮硬切

失去旧服务兼容和低风险回滚能力。

10. “测试绿了，可以上线”

测试环境没有生产流量、真实配置、旧客户端和回滚压力。
