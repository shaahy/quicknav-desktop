01

先判断“装不装得下”

二者的分界不是“复杂产品与简单项目”，而是决策是否能在一次会话内收敛，以及路线是否仍然处于迷雾中。

Use Wayfinder when

路线还看不清

  • 工作明显超过一个 Agent 会话。
  • 研究、原型、人类决策之间存在依赖。
  • 当前只能描述目的地，还不能直接写可靠规格。
  • 需要多人或多 Agent 通过认领和阻塞关系协作。
Use grill-with-docs when

一个会话能够谈清

  • 已经在一个可安全写入的代码仓库中。
  • 变更边界大体明确，只存在若干软点。
  • 需要将术语和少数关键决定留在仓库中。
  • 结束后可以沿同一上下文立即进入规格阶段。
最短选择规则 已经能精确描述需求就跳过两者；一次会话装不下且路线仍模糊，用 /wayfinder；一次会话能收敛且有仓库，用 /grill-with-docs；没有仓库的独立想法才考虑 /grill-me。
02

共同前置：先让仓库会说话

/setup-matt-pocock-skills 是每个仓库运行一次的配置步骤。它配置工作流读写的位置，不安装技能，也不替代产品规划。

S0 /setup-matt-pocock-skills配置 Issue Tracker、领域文档与可选 Triage 标签 +

先探索 Git remote、现有 AGENTS.md/CLAUDE.md、领域文档、.scratch/ 和 monorepo 信号，再展示草案并等待确认。它不是无脑脚手架。

核心输入
  • 真实仓库结构与 Git remote
  • Issue Tracker 选择
  • 单上下文或多上下文布局
核心输出
  • docs/agents/issue-tracker.md
  • docs/agents/domain.md
  • 可选 triage-labels.md
  • Agent instructions 中的指针区块
G0 通过条件：工作流知道去哪里读写 Issue、领域词汇和 ADR；配置草案已由人确认，没有重复覆盖现有规则。
03A

路线 A：Wayfinder 从迷雾开图

这条路线先找到“怎么走”，再进入“怎么建”。Wayfinder 的票是决策问题，不是实现切片；默认规划，不实施。

A1命名 Destination/wayfinder 内部调用 grilling + domain-modeling+

先说清“地图完成时应得到什么”：可以是一份可交给 to-spec 的清晰路线，也可以是必须锁定的重大决策。Destination 固定本轮工作的范围。

输入
  • 大型但松散的想法
  • 现有仓库、历史决定与限制
  • 谁拥有最终产品决策权
输出
  • 1–2 行 Destination
  • Notes：领域、偏好、必用技能
  • 初步 Out of scope
门禁：目的地必须可判断“是否到达”，而不是“做一个更好的产品”这类不可验证表达。
A2Chart the map广度优先识别 frontier、blocked 与 fog+

创建一个标记为 wayfinder:map 的地图 Issue。能准确提问的内容建成子票；尚不能准确提问的内容保留在 Not yet specified，不要过早伪装成任务。

输入
  • Destination 与范围边界
  • 现有事实和依赖关系
  • Issue Tracker 的 Wayfinding 约定
输出
  • 一个 canonical map Issue
  • 可精确表述的 child tickets
  • native blocking edges
  • fog 与 Out of scope
AFKResearch外部知识阻塞决策；由研究 Agent 查一手来源。
HITLPrototype外观或行为无法靠文字决定；做低成本可反应原型。
HITLGrilling默认类型；用户回答取舍，Agent 查事实并校准术语。
AFK / HITLTask不是决策，但必须先完成才能继续判断的实际工作。
关键停止点：画图会话到此结束；除研究票外，不要顺手解决其他票。
A3逐票推进 Frontier每个会话原则上只认领并解决一张非研究票+

每次只加载地图的低分辨率视图，再选择开放、未阻塞、无人认领的票。先 claim，再工作；解决后把答案写入 resolution，关闭票，并在地图的 Decisions so far 增加一行指针。

每次会话输入
  • Map URL/编号
  • 一张 frontier ticket
  • 相关历史决策的按需链接
每次会话输出
  • 一条可追溯 resolution
  • 关闭并解除后续阻塞
  • 新票、重连依赖或 fog 升格
  • 地图中的上下文指针
并发纪律：认领是防重机制；HITL 票必须由真人回答，Agent 不得替用户做决定。
A4设计系统规范节点ui-ux-pro-max；UI 项目必经，纯后端可跳过+

当产品类型、用户、视觉方向和技术栈已经由地图决策明确后，生成并持久化设计系统。若“应该长什么样”仍未解决，先返回 Wayfinder 建立 prototype ticket，而不是让设计工具替产品负责人做决定。

输入
  • 已解决的产品与品牌决策
  • 目标受众和使用情境
  • 检测到的真实技术栈
  • 原型验证结论
输出
  • design-system/<slug>/MASTER.md
  • 可选页面覆盖文件
  • 无障碍、响应式和反模式约束
G2 通过条件：设计系统已确认，并作为后续 spec 的权威输入；已有 MASTER 不得被静默覆盖。
A5从地图折叠为 Spec/to-spec：综合既有决策，不重新访谈+

当地图不再有阻塞目的地的未决问题，使用 /to-spec 将分散在票据中的决策折叠成一份可实施规格。不要从 map 直接跳到 implement，否则会丢失跨票细节。

输入
  • Map 与所有 resolution 指针
  • 领域词汇、ADR、代码库现状
  • 设计系统 MASTER 与页面覆盖
输出
  • Tracker 中的完整 Spec
  • Problem / Solution / User Stories
  • Implementation / Testing Decisions
  • Out of Scope；ready-for-agent
G3 通过条件：测试 seam 已与用户确认；规格可追溯至地图决策和设计系统。
A6Tracer-bullet 拆票/to-tickets：把 Spec 变成可独立验证的实现切片+

每张票应纵向穿过必要层次并可单独演示，能够放入一个新上下文窗口。先展示拆分与 blocking edges，获得用户批准后再发布。

输入
  • 批准后的 Spec
  • 代码库 seam 与 prefactor 机会
  • 设计系统中的 UI 约束
输出
  • 每票一个 Issue 或 Markdown 文件
  • What to build + Acceptance criteria
  • Blocked by 关系
  • ready-for-agent 状态
G4 通过条件：没有“只做数据库/只做 UI”的横向切片；每票可演示、可验证、依赖真实。
A7逐票实施、体验验收与审查/implement → 建议 QA 门禁 → /code-review+

按 frontier 逐票实施。/implement 在预先约定的 seam 上使用 TDD，持续执行类型检查与单测，最后跑完整测试。UI 工作还必须在真实浏览器中验证，不能用绿测试代替视觉验收。

实施证据
  • 代码、测试、类型检查和 commit
  • 设计系统引用与页面覆盖
  • 真实浏览器截图、控制台和无障碍检查
审查输出
  • Standards 轴报告
  • Spec 轴报告
  • 交互 QA 形成的缺陷 Issue
  • 最终人工验收结论
当前官方顺序的已知断点implement 原文要求“先 code-review、再 commit”，但 code-review 只审固定点到 HEAD 的已提交 diff，可能看不到工作树变化。更稳妥的质量做法是：形成可审实现 commit → 新会话指定基准 fixed point 做独立 review → 修复并复审。真实项目中的 commit 仍须遵守项目授权规则。
G5–G7：机械检查、真实运行、人工视觉接受和双轴审查全部独立通过，才算交付。
03B

路线 B：一次会话收敛再构建

/grill-with-docs 是同一个 grilling 访谈引擎，加上 domain-modeling 的仓库持久化纪律。它不是完整工作流，只是主链入口。

B1/grill-with-docs设计树、frontier 分轮追问、领域语言即时落盘+

grilling 将方案视为决策树，每一轮只询问前置决策已经解决的 frontier；每题给出推荐答案。环境事实由 Agent 查询，真正的取舍由用户决定。domain-modeling 同时检查术语、边界和代码矛盾。

核心输入
  • 一个仓库内的想法、变更或设计
  • 现有 CONTEXT、ADR 与代码事实
  • 用户的范围与产品取舍
核心输出
  • 对话中的共同理解
  • 确认术语写入 CONTEXT.md
  • 极少数关键决定写入 docs/adr/
  • 明确 Out of scope
不要误判输出CONTEXT.md 只是词汇表，不是 Spec；普通决定仍只在当前会话中。frontier 为空后，还必须由用户确认“共同理解已经形成”，不得自动开始实施。
G1 通过条件：没有沉默假设；术语与代码事实不冲突；用户明确确认理解一致。
B2按需插入 Research / Prototype谈话不能替代事实与可运行答案+

外部资料不清楚时，让 /research 读取一手来源；UI 手感、状态模型或交互行为无法靠文字决定时，用 /prototype 制作一次性答案。获得事实或观察后回到原决策树，而不是把原型当成生产实现。

研究输出
  • 带一手来源引用的 Markdown
  • 回答事实，不替用户做决定
原型输出
  • UI route 或逻辑单 HTML
  • throwaway branch 上的 primary source
  • 问题、观察与结论指针
回环条件：新证据必须回到 grilling 形成用户决策；不能把工具输出默认为批准。
B3设计系统规范节点ui-ux-pro-max：把已收敛的产品方向变成可执行视觉规则+

从已确认的产品类型、用户情境、风格关键词和真实技术栈生成设计系统。先检查是否已有 MASTER；页面级差异写 overrides，不在组件中散落任意颜色和间距。

输入
  • grill 已确认的产品与交互决定
  • 从仓库检测的 stack
  • 品牌资产与已有视觉语言
输出
  • design-system/<slug>/MASTER.md
  • pages/<page>.md 可选覆盖
  • tokens、layout、a11y、motion 约束
G2 通过条件：设计系统由人确认，覆盖核心状态、响应式和无障碍，不与既有品牌语言冲突。
B4/to-spec留在同一会话，综合既有共识而不是重新访谈+

由于大多数普通决定没有写入 CONTEXT 或 ADR，最佳做法是在同一上下文中立即调用 /to-spec。若必须跨会话，使用 /handoff 引用已有产物，并明确下一会话目标。

输入
  • 完整 grill 对话上下文
  • CONTEXT、ADR、代码库事实
  • 设计系统 MASTER
输出
  • Tracker 上的 Spec
  • 广泛 User Stories
  • Implementation / Testing Decisions
  • 已确认 testing seams
G3 通过条件：规格没有重新发明决定；范围、验收、测试与 UI 规范均可追溯。
B5/to-tickets将已理解的 Spec 拆成纵向可验证切片+

先草拟 ticket 与阻塞关系，向用户确认粒度、依赖、合并和拆分，再发布。不要把 Wayfinder 的“决策票”和这里的“实现票”混为一谈。

输入
  • 已批准 Spec
  • 现有 seam 与 prefactor 机会
输出
  • Issue Tracker tickets
  • 本地模式：每票一个 Markdown
  • Acceptance criteria + Blocked by
G4 通过条件：每票一个新上下文可完成、可单独演示；宽重构使用 expand–migrate–contract。
B6实施、浏览器验收与双轴审查/implement → 建议 QA 门禁 → /code-review+

逐票实施；UI 必须检查设计系统一致性、断点、键盘、对比度、reduced motion、控制台和真实交互。当前 Matt 官方 main 已没有 /qa 技能，因此这里的 QA 是本教程建议的运行时与人工验收门禁；发现的问题应按项目 Tracker 规则形成 durable Issue。

核心证据
  • 测试、类型检查、full suite
  • 真实浏览器和人工视觉验收
  • QA 缺陷 Issue 及处理状态
最终输出
  • 代码与 commits
  • Standards / Spec 双轴报告
  • 确认通过或明确剩余风险
审查顺序建议官方 implement 与 code-review 的已提交 diff 前提存在衔接断点。建议形成可审 commit 后，在新上下文中明确 fixed point 独立审查；再处理发现并复审。
G5–G7：测试绿不等于体验通过；审查绿也不能覆盖用户拒绝的视觉结果。
04

设计系统节点不是“美化”

它把已经确认的产品方向压缩成后续规格、拆票、实施和审查共同遵守的视觉与体验契约。

ui-ux-pro-max · required for new UI

先生成 MASTER，再允许页面覆盖

推荐顺序：检测真实 stack → 读取已有 MASTER → 用多维关键词生成设计系统 → 持久化 → 按需增加页面 override → 进行 UX、stack 和交付检查。若查询返回 0 条结果，必须改用更宽关键词重试，不能虚构命中。

Product patternStyleColor tokensTypographySpacingResponsiveAccessibilityMotionAnti-patternsStack rules
必须先有
  • 产品类型与行业
  • 目标用户与使用情境
  • 已确认的视觉关键词
  • 从项目检测的技术栈
持久化文件
  • design-system/<project-slug>/MASTER.md
  • design-system/<project-slug>/pages/<page>.md
  • 页面覆盖优先于 MASTER，其余继承 MASTER
建议插入位置 在 G1“决策收敛”之后、G3“正式规格”之前。原因是它需要稳定的产品输入，而 Spec 又应引用它作为 UI 约束。纯后端任务可显式标记 N/A；有 UI 的任务不应跳过。

06

八个质量门禁

门禁的意义不是增加仪式，而是防止一种证据替另一种证据背书。绿测试、代码审查和人工接受各自回答不同问题。

G0

仓库准备

Agent + 人确认
  • Tracker、领域文档和标签位置明确
  • 现有 Agent instructions 未被重复或覆盖
  • 技能已安装与仓库已配置分开检查
G1

决策收敛

人负责
  • Wayfinder：目的地前无阻塞性 fog/票
  • Grill：frontier 为空且用户明确确认
  • 范围外内容与沉默假设已显式化
G2

设计系统

设计 + 人确认
  • MASTER 与页面覆盖层级清楚
  • 颜色、排版、间距、状态和组件一致
  • 响应式、键盘、对比度和 reduced motion 有规则
G3

规格完整

Agent 起草 + 人批准
  • Problem、Solution、User Stories 完整
  • Implementation / Testing Decisions 可执行
  • Out of Scope、seams 与设计系统引用明确
G4

实现就绪

人批准拆票
  • 每票是纵向、可演示的 tracer bullet
  • 一个新上下文可完成
  • Blocking edges 真实；宽重构使用 expand–contract
G5

机械验证

Agent
  • 预定 seam 上的测试通过
  • 类型检查、单测和 full suite 有新鲜证据
  • 没有用“应该能运行”代替实际命令
G6

真实体验

Agent + 人接受
  • 真实浏览器/应用生命周期验证
  • 关键断点、控制台、键盘和无障碍检查
  • 视觉结果由产品负责人明确接受
G7

最终审查

双轴 Reviewer
  • Standards 与 Spec 分开报告
  • 无未解释 scope creep 或缺失需求
  • QA Issue 已关闭、接受或明确延期
07

辅助技能按问题插入

不要把所有技能排成一条僵硬流水线。辅助技能是针对特定阻塞类型的分支，并在取得答案后回到主链。

/grilling

所有 grill 入口的底层机制；事实由 Agent 找，决策由用户做。

/domain-modeling

校准领域语言，维护 CONTEXT.md，并克制地记录 ADR。

/research

08

三个典型场景

同一个产品可能在不同尺度上选择不同入口。入口由当前决策范围决定，而不是由项目名决定。

Case 01 · 增量功能

桌面应用新增收藏视图

仓库与产品边界明确，一个会话能谈清数据模型、入口和空状态。

setup → grill-with-docs → design system/page override → to-spec → to-tickets → implement → browser acceptance → review
Case 02 · 平台级产品

从零建设数字人运营平台

业务角色、内容生产、资产、权限和交付链相互依赖，无法一次谈清。

setup → wayfinder map → research/prototype/grilling tickets → design system → to-spec → tickets → iterative delivery
Case 03 · 复杂但清晰

支付模块协议升级

技术实施很难，但目标和边界可能清楚。实现难度高不自动等于需要 Wayfinder。

grill-with-docs（如仍有取舍）→ to-spec → expand–migrate–contract tickets → implement → review
Final rule

先收敛决定，再固化规范，然后才允许拆票和实现。

Wayfinder 管“一个会话装不下的决策空间”；grill-with-docs 管“一个会话能谈清并需要留下仓库共识的变更”；ui-ux-pro-max 把已确认方向转成设计契约。三者都不能替用户承担最终产品决定。

迷雾未清，不写 Spec。设计未定，不拆 UI 票。证据未新鲜，不宣布完成。用户未接受，不以绿测试代替。
