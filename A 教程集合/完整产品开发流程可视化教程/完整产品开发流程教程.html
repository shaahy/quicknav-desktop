环境配置

CI/CD 环境准备

搭建 GitLab Runner、测试环境和自动化配置，使项目具备运行集成测试的能力。门禁：Runner 在线、测试环境可达。

技能GitLab RunnerShell ExecutorGitLab CI/CD

流程作用与目标

  • 注册可执行集成测试的 Runner
  • 准备测试环境、账号与连通性
  • 生成并提交 .gitlab-ci.yml

必要输入条件

  • contracts/ API 路由表
  • 测试环境地址与测试账号
  • Runner 机器 SSH 权限

输出物

  • .gitlab-ci.yml：定义项目 Pipeline、测试任务、制品和执行规则。
  • runner-registration-report.md：记录 Runner 注册、标签、执行器和在线验证结果。
  • test-environment-connectivity.md：记录测试环境、账号和依赖服务的连通验证。

建议执行角色

  • CI 负责人（主责）
  • 运维人员（Runner 机器）
  • 产品/开发（测试账号）

其它重要说明

  • Shell Executor 可规避部分 Docker 权限问题，但 Runner 主机仍需最小权限和隔离。
  • 一个 Runner 可服务同组多个项目；Runner 离线会使 Pipeline 长时间停留在 Pending。
  • 生产、预发布和演示环境必须分别配置，凭据与测试数据不得混用。
执行示例：读取 contracts/ → 注册 Runner → 创建并提交 .gitlab-ci.yml → 验证 Runner 在线 → 验证测试环境可达。
基线验证

CI 基线验证

首次 Push 自动触发集成测试，确认当前代码和环境基线全绿，区分历史问题与本次改动。门禁：Pipeline 全绿。

技能GitLab CI/CDGit

流程作用与目标

  • 触发完整集成测试
  • 确认开发前基线状态
  • 形成可归档的测试证据

必要输入条件

  • 已配置的 .gitlab-ci.yml
  • 提交至当前功能分支或团队规定的集成分支
  • 在线 Runner 与可达测试环境

输出物

  • pipeline-baseline-report.md：记录基线 Pipeline、Commit SHA 和最终状态。
  • test-results/baseline.log：保存基线集成测试的原始日志。
  • test-results/baseline.json：保存基线集成测试的结构化结果。

建议执行角色

  • 开发工程师（主责）
  • CI 负责人（环境异常时）

其它重要说明

  • 基线不绿时停止功能实现，先判断代码失败、环境失败还是 Runner 失败。
  • 基线报告应归档并绑定 Commit SHA，不能使用未知版本的旧报告。
执行示例：Push 当前开发分支 → 在 GitLab Pipeline 查看结果 → 归档原始日志与 JSON → 全绿后开始功能任务。
任务循环

逐任务 CI 验证

每次任务提交后自动运行集成测试，及时发现回归，并把当次 Pipeline 作为任务完成证据。门禁：当前提交 Pipeline 通过。

技能GitLab CI/CDGitJUnit XML

流程作用与目标

  • 每次 Push 自动运行集成测试
  • 及时发现对已有业务流程的破坏
  • 让 CI 结果成为任务验收证据

必要输入条件

  • 已生效的 .gitlab-ci.yml
  • 当前任务的代码提交
  • 已通过的本地测试

输出物

  • pipeline-task-report.md：记录当前任务、Commit SHA、Pipeline 地址和最终状态。
  • test-results/junit.xml：保存当前提交的 JUnit XML 测试报告。
  • commit-task-traceability.md：建立任务、提交和测试证据之间的对应关系。

建议执行角色

  • 开发工程师（主责）
  • 测试工程师（用例与报告口径）

其它重要说明

  • Pipeline 红色时不得进入下一任务或宣称完成；允许提交修复代码后重新触发。
  • 确定性失败不得靠重复运行制造绿灯，必须先定位根因。
执行示例：完成任务与本地测试 → Commit / Push → Pipeline 自动执行 → 绿色则归档证据，红色则修复并重新验证。
合并门禁

CI 发布门禁

把 Pipeline 全绿设为合并和发布前提，确保自动化测试证据可追溯到当前提交。门禁：Pipelines must succeed。

技能GitLab CI/CDProtected BranchGit

流程作用与目标

  • 用 CI 结果控制代码合并
  • 关闭 P0/P1 阻断问题
  • 为主流程第 29 步提供可信输入

必要输入条件

  • 已配置的 .gitlab-ci.yml
  • 当前 HEAD 对应的全绿 Pipeline
  • JUnit XML 与 JSON 测试证据

输出物

  • test-results/junit.xml：保存当前 HEAD 对应的 JUnit XML 测试结果。
  • test-results/results.json：保存当前 HEAD 对应的结构化测试数据。
  • release-approval.md：记录合并或发布门禁的检查项、审批人和批准结论。

建议执行角色

  • 技术负责人（主责）
  • 开发负责人
  • CI 平台

其它重要说明

  • 启用 Pipelines must succeed，Pipeline 红色时禁止强行合并。
  • P0/P1 必须在合并前清零；历史报告不能替代当前 Commit 的测试证据。
  • 门禁通过并完成合并后，进入主流程第 29 步构建不可变候选制品。
执行示例：核对当前 HEAD Pipeline → 检查 JUnit XML / JSON → 清零 P0/P1 → 批准合并 → 进入第 29 步。

集成测试结果分类

返回码分类含义与处理
200 / 201OK请求通过，无需处理。
400 / 429预期业务结果仅当测试用例明确预期业务规则或限流响应时通过，否则按异常处理。
401 / 403AUTH检查身份、权限、Token 与测试账号配置。
404TODO接口尚未实现或路由错误，补充实现并重新测试。
5xxFAIL优先修复代码或服务异常，不得进入下一任务。

四条执行纪律

流程不是文档清单，而是一组禁止静默越界的交付纪律。

原型不等于需求事实

原型里出现的新业务能力必须先回写 PRD；纯体验变化回写 experience，纯视觉变化回写 design。

下游不能覆盖上游

Spec、Plan、Tasks 和代码只能细化已批准事实。发现冲突就回到领域责任人裁决。

门禁失败必须回退

需求、体验、规格、测试或发布门任一失败，都回到产生问题的节点，不带病进入下一阶段。

完成必须有新鲜证据

完成声明需要本次执行的测试、审查和验收输出，不能引用旧日志或智能体口头结论。

任务保持双向追溯

从 BMAD 来源到需求 ID、任务、测试、提交和发布证据，每一层都能向上和向下定位。

人类保留关键裁决权

范围、体验取舍、架构例外、风险接受和生产发布，必须由明确责任人决定。
