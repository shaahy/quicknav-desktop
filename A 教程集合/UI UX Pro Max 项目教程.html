01 · What it is

它不是模板库，而是一条设计决策链

先理解产品、行业和技术栈，再检索风格、配色、字体、交互与实现规则，让智能体少凭感觉，多按证据设计。

解决“选得更对”

普通提示词容易把 UI 生成变成风格抽奖；这个项目把“专业一点”拆成可检索、可解释、可复用的规则。

01新页面先生成完整设计系统，再进入页面和组件。
02复杂问题按 color、typography、ux、chart 等知识域深入检索。
03根据项目文件识别 React、Vue、Flutter、SwiftUI 等技术栈。
04交付前按优先级检查无障碍、响应式、反馈与性能。
Capability boundary

它能做什么，也不能替代什么

它提供设计智能、决策规则与实现指导，但不等于 Figma，也不能自动替代需求确认、用户研究、真实可用性测试或人工审美判断。

不是固定模板库不是纯图像生成器不是发布审批不是用户研究替代品
i项目另含 74 组字体搭配、98 条 UX 指南、104 个图标条目、16 组 GSAP 动效预设与 25 类图表建议。

03 · Follow the path

沿着五步路径执行

新界面最重要的纪律：先形成全局判断，再补充局部规则，最后才进入实现。

1
ANALYZE

把任务说清楚

提取产品、受众、情境、风格、技术栈和不可突破的约束。

你提供业务目标、使用者、已有项目Codex 负责读取项目证据并补全 Brief
2
DESIGN SYSTEM

先确定全局判断

生成产品模式、视觉风格、配色、字体、效果、反模式和设计令牌方向。

3
DETAIL

只深入不确定的部分

需要时再补充图表、表单、无障碍、图标、动效或具体知识域规则。

4
IMPLEMENT

确认后再修改

先说明范围和风险，获得确认后才按检测到的技术栈落地界面与组件。

5
VERIFY

用真实证据验收

检查键盘、颜色模式、375/768/1440 视口、加载反馈、性能和核心用户流程。

04 · Capability map

请求如何变成实现约束

核心资产不是某一张页面，而是从需求到规则再到代码的五层能力链。

01 / REQUEST

用户请求

产品、行业、受众、风格、使用情境与目标技术栈。

02 / ENGINE

ui-ux-pro-max

分析需求，调用本地检索与推理规则生成设计系统。

03 / DOMAIN

专项知识域

product、style、color、typography、ux、chart、icons、gsap。

04 / STACK

栈级规则

React、Next.js、Vue、SwiftUI、Flutter、HTML/Tailwind 等。

05 / DELIVERY

设计与代码

页面、组件、令牌、品牌资产、横幅、演示与检查结果。

补充技能围绕核心链协作：design 做综合路由，brand 管品牌源，design-system 管令牌与组件，ui-styling 管前端落地。

05 · Where it fits

六类高价值场景

判断标准：任务是否改变界面的外观、感受、运动方式或交互方式？如果会，就值得启用设计技能。

07 · Practice

从一句需求到可验收结果

这里不展示命令行。重点是如何在 Codex 中提出任务、它应该怎样执行，以及你用什么标准验收。

Case 01

AI 客服 SaaS 转化型落地页

目标不是“生成漂亮首页”，而是建立能解释结构、配色与交互理由的设计系统。

1
输入B2B AI 客服、运营负责人、可信而不冷漠、Next.js、突出试用。
2
设计系统确定权威型结构、信任证据链与品牌令牌。
3
验收首屏 CTA、证据链、键盘、表单恢复和移动端。
你对 Codex 说

请使用 ui-ux-pro-max 技能，为一个面向企业运营负责人的 AI 客服 SaaS 设计转化型落地页。先检查当前 Next.js 项目和已有品牌规范；不要直接写页面，先给出完整设计系统、首屏信息层级、信任证据链和表单反馈规则。我确认设计方向后再实现，并用键盘、375/768/1440 视口和核心转化流程验收。

合理的 Codex 执行路径检查项目证据 → 形成 Brief → 生成设计系统 → 补充 landing/ux 规则 → 等待确认 → 实现 → 浏览器验收。
Case 02

连锁门店运营仪表板

把“信息很多”转成任务优先级、异常发现和可执行下钻。

1
输入区域经理、50 家门店、经营异常、桌面为主。
2
专项规则图表、数据表、筛选、空状态和加载反馈。
3
验收异常是否先被看到、筛选能否恢复、移动端是否可用。
你对 Codex 说

请使用 ui-ux-pro-max 技能，为连锁门店区域经理设计经营仪表板。先分析用户每天要完成的决策，再生成完整设计系统；重点补充 chart、table、filter、loading、empty state 和无障碍规则。先提交信息架构、指标层级、图表选择理由与交互流程，我确认后再修改项目。

合理的 Codex 执行路径梳理决策任务 → 设计信息层级 → 生成系统 → 查询 chart/ux → 给出可比较方案 → 确认后实现并验证。
Case 03

审查现有管理后台

审查先给证据与优先级，不直接用新风格覆盖既有设计。

1
读取现状页面、设计令牌、组件、截图和关键流程。
2
分级问题阻断、严重、一般、润色，并附定位证据。
3
修复 Gate先确认范围，再逐项修改与回归验证。
你对 Codex 说

请使用 ui-ux-pro-max 技能审查当前管理后台。先读取现有组件和设计令牌，在真实浏览器中检查桌面与手机视口、键盘导航、对比度、触控、加载反馈和核心任务流程。请按阻断、严重、一般、润色四级输出证据化报告；这一轮只审查，不修改代码。

合理的 Codex 执行路径读取现状 → 浏览器取证 → 按影响分级 → 给出修复范围与验收标准 → 停在修改 Gate 前。

四个常见误区

直接开始写代码新界面跳过完整设计系统，容易局部漂亮、整体失序。
硬编码默认技术栈应先检查项目证据；无法识别时再询问用户。
只依赖自动域识别结果偏题时应明确指定需要深入的知识域。
覆盖现有设计决策持久化前读取已有设计系统，并停在确认 Gate 前。
