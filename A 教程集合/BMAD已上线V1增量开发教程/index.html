BMAD METHOD · BROWNFIELD INCREMENTAL DELIVERY

已上线 V1，如何用 BMAD 开发 2–3 个小功能

一份双击即开的离线教程。目标不是重跑完整 V1，而是建立可追溯的 V1.1 变更集，选择性更新事实源，再按 Story 完成开发、审查、回归和发布。

1一个迭代级增量契约
2–3每个功能独立 Story
4层质量门禁
0不重写无关 V1 文档
先看结论

推荐采用“轻量完整增量链”

官方对既有项目的小改动优先推荐 bmad-quick-dev。但你要一次交付 2–3 个功能，而且默认可能涉及页面、API 和少量数据结构，所以更稳妥的方式是：以一个 V1.1 增量范围为总边界，每个功能独立开发和验收。

本教程的默认方案：冻结 V1 基线 → 形成 V1.1 增量 SPEC.md → 只更新受影响的 PRD/UX/Architecture → 生成增量 Epic/Stories → Readiness Gate → 逐 Story 开发与对抗式 Review → Epic 回归 → 发布并建立 V1.1 新基线。
保留

V1 仍是基线

已上线且未被本次变更触及的业务规则、交互、接口和架构决定继续有效。

新增

V1.1 是变更集

只描述新增、修改、废弃及明确不变的内容，不复制整套 V1 文档。

阻断

冲突必须先解决

SPEC、PRD、UX、Architecture 与现有代码不一致时，不允许开发 Agent 自行选一个版本。

关于 SPEC：BMAD 里存在两类名字相近的产物。正式的 SPEC.md 是意图契约；Quick Dev 常产生 spec-*.md。本教程用前者管理 V1.1 总边界，用 Story 管每个功能的实现边界。
事实源

先建立单一事实链，避免“文档互相打架”

层级回答的问题V1.1 的处理方式不能做的事
V1 Release Baseline现在生产环境到底是什么冻结版本号、提交、数据库迁移、接口、监控与已知问题把旧规划文档当成比生产代码更“真实”
PRD / Addendum为什么做、业务规则和验收是什么只有业务范围或 FR/NFR 变化才更新把技术实现细节写成产品事实
DESIGN / EXPERIENCE用户看到什么、如何操作、异常如何反馈只有新增页面、状态或关键交互才更新简单文案修改也重跑整套 UX
Architecture / ADR系统边界、数据、API、权限和部署如何实现只有架构决定变化才写增量 ADR为局部代码调整重写总架构
V1.1 SPEC.md这次迭代改什么、不改什么、怎样算成功作为本次增量的导航和范围合同未经确认反向覆盖正式上游事实
Story 文件当前一个可交付单元具体怎么验收每个功能一个主 Story，必要时再拆把三个独立功能塞进一个巨型 Story
优先级规则：生产现状用于描述“现在是什么”；已确认 PRD/UX/Architecture 用于描述“为什么和应该怎样”；V1.1 SPEC 只表达本次变更。若三者冲突，先报告并确认，不让开发过程暗中改写事实。

尚未判断。请按一个功能的实际影响勾选。
A级

Quick Dev

单一目标、局部文件、无数据/权限/核心状态变化。每个功能单独一次 Quick Dev。

B级

轻量完整增量链

小型跨层功能。写 V1.1 SPEC、选择性更新文档、独立 Story、Readiness、Review 和回归。

C级

正式变更链

权限、核心状态、合规、跨系统或架构变化。必须更新正式 PRD/UX/Architecture 并执行完整门禁。

New Baseline
步骤 1

冻结 V1 生产基线

增量开发首先要回答“当前真实系统是什么”。如果正式文档与生产代码已经漂移，先运行项目文档梳理，而不是让新功能基于旧图纸开发。

创建迭代工作区

建议新建 iteration-v1.1 目录，存放本次增量产物。不要修改或删除 V1 的定稿目录。

确认基线证据

按需刷新 Project Context

如果 project-context.md 不存在或明显过时，在 AI IDE 的新对话中调用：

bmad-generate-project-context

审核生成结果，确保它描述的是现有代码约定，不是 Agent 想象中的“最佳实践”。

停止条件：无法确认生产基线、关键文档明显过时、测试无法运行，或数据库迁移历史不清楚。此时先补项目现状文档和验证证据，不进入功能实现。
步骤 2

建立一个 V1.1 增量 SPEC

这份 SPEC 不是复制 PRD，而是锁定本次迭代的 WHAT。它把 2–3 个功能放在同一个发布边界中，同时明确每个功能仍需单独验收。

调用方式

在新的 AI IDE 对话中调用 bmad-spec，并提供 V1 基线、正式上游文件和本次功能清单。下面文字可直接复制：

使用 bmad-spec 为已上线 V1 创建 V1.1 增量规格。

目标：增加以下 2–3 个小功能：[填写功能清单]。
基线：V1 已上线，现有 PRD、UX、Architecture、project-context.md 和生产代码继续有效。

要求：
1. 只描述相对 V1 的新增、修改、废弃和明确不变项；不要重写完整 V1。
2. 读取生产代码和最终上游文档，发现冲突先报告，不自行选择事实源。
3. 每个功能分别写 Why、Capability、约束、非目标、成功信号和回归影响。
4. 明确数据、API、权限、状态、UX、NFR、迁移、可观测性和回滚影响。
5. 给出功能间依赖与建议交付顺序。
6. 输出 SPEC.md，并保留来源与待确认项。

SPEC 最小结构

# V1.1 Increment SPEC

## 1. Baseline
- V1 production version / commit / release date
- Authoritative PRD / UX / Architecture / project-context
- Known gaps between documents and production

## 2. Why
- 本次迭代解决的用户或业务问题

## 3. Capabilities
- CAP-1：功能一
- CAP-2：功能二
- CAP-3：功能三（如有）

## 4. Constraints
- 必须兼容 V1 数据与接口
- 不破坏既有权限、状态机和关键用户路径
- 数据迁移必须可回滚或具备前向修复方案

## 5. Non-goals
- 本次明确不做的重构、平台化、顺手优化和历史缺陷

## 6. Success Signals
- 每项能力的可观察业务结果与技术验收指标

## 7. Change Matrix
- 新增 / 修改 / 废弃 / 明确不变

## 8. Regression Surface
- 受影响的 V1 页面、API、任务、权限、数据和监控

## 9. Open Decisions
- 未决项、负责人、截止点；未关闭不得进入相关 Story
SPEC Gate：只有当所有功能都能用可判定的成功信号表达，并且 Non-goals、兼容边界、回归范围清楚后，才能进入上游更新。模糊的“优化体验”“支持导出”不算合格。

PRD 更新提示词
使用 bmad-prd 的 Update 意图处理 V1.1 增量。
输入：V1 最终 PRD、V1.1 SPEC、生产基线与变更影响分析。
要求：只修改受影响的业务规则、FR/NFR、验收和范围；保留未受影响的 V1 内容；输出变更清单；发现冲突先报告并等待确认。
UX 更新提示词
使用 bmad-ux 的 Edit/Update 路径处理 V1.1。
输入：V1 最终 DESIGN.md、EXPERIENCE.md、V1.1 SPEC、受影响页面和现有实现。
要求：只修改新增页面、组件、状态、反馈与可访问性；明确复用现有模式；不得自行改变产品业务规则或未受影响视觉事实。
Architecture 更新提示词
使用 bmad-architecture 对 V1.1 做增量架构评估。
输入：V1 架构、V1.1 SPEC、更新后的 PRD/UX、生产代码与 project-context.md。
要求：优先复用现有组件和模式；只记录新增或改变的架构决定；覆盖数据迁移、API 兼容、权限、失败恢复、可观测性和回滚；无架构变化时明确写“无需更新”及依据。
编辑边界：不要让 Architecture 修改产品范围，不要让 UX 修改业务状态，不要让 SPEC 偷偷成为更高优先级的 PRD。每类事实只由对应文档负责。
步骤 4

生成一个增量 Epic，每个功能独立成 Story

在新的 AI IDE 对话中运行：

bmad-create-epics-and-stories

建议输入 V1.1 SPEC、所有被更新的正式事实源、V1 架构与 Project Context，并明确要求“只生成 V1.1 增量内容”。

推荐拆法

  • Epic：V1.1 小功能增强
  • Story 1：功能 A 的端到端用户价值
  • Story 2：功能 B 的端到端用户价值
  • Story 3：功能 C 的端到端用户价值
  • Story 4：仅当共享迁移/基础设施无法归属任一用户 Story 时新增

避免的拆法

  • 按“前端 Story / 后端 Story / 测试 Story”横向拆散价值
  • 三个功能共用一个大 Story
  • 把历史缺陷和顺手重构塞入本迭代
  • 把测试推迟到 Epic 结束才补
  • 没有明确依赖却强行串行

每个 Story 必须包含

业务契约

用户角色、目标、价值、可验证 AC，以及对应 SPEC/PRD 引用。

实现约束

架构模式、触碰模块、数据/API/权限边界、兼容与迁移要求。

验证契约

单元、集成、E2E、回归、NFR、监控和回滚验证。

拆分原则：一个 Story 完成后应当产生独立可验证的用户价值。若必须等待另一个 Story 才能验收，必须显式写依赖和集成验收，不要假装独立。
步骤 5

执行增量 Implementation Readiness

在新的 AI IDE 对话中调用：

bmad-check-implementation-readiness

这次检查不是重新审计整个 V1，而是检查 V1.1 变更集是否与 V1 基线一致。

范围一致SPEC、PRD 增量和 Stories 的功能集合一致，Non-goals 没有被偷偷实现。必须通过
UX 完整关键状态、空态、错误态、权限不足和成功反馈都可验收。必须通过
架构可行数据/API/权限/迁移/回滚/监控均有实现路径。必须通过
Story 可做每个 Story 有清晰 AC、依赖、技术约束、文件范围和测试要求。必须通过
回归明确受影响 V1 路径与测试责任已映射，发布门禁可判定。必须通过
准入规则：FAIL 不开发；CONCERNS 必须逐项确认风险接受者和关闭方式；只有 PASS 或被明确接受的低风险 Concern 才进入 Sprint。
步骤 6

逐 Story 开发，不在一个长对话里连续做完

BMAD 推荐每个工作流使用新对话，减少旧上下文污染。人工控制模式下，每个 Story 至少经历 Create、Dev、Review 三次明确的工作流。

初始化或刷新 Sprint

bmad-sprint-planning

确认只纳入 V1.1 的增量 Epic/Stories，并写出依赖顺序。已有 sprint-status.yaml 时应更新，不要无故覆盖历史状态。

Create Story：把当前 Story 准备到 ready-for-dev

bmad-create-story

检查 Story 是否引用了 V1.1 SPEC、相关上游章节、前一 Story 的经验、现有代码模式和测试标准。若故事仍有产品决策空缺，退回上游，不让 Dev 猜。

Dev Story：按 AC 编码并同步测试

bmad-dev-story

要求 Dev 按任务顺序实现，运行相关测试，只勾选实际完成的任务，并维护 Dev Agent Record、Completion Notes 和 File List。

Code Review：对照实际变更做对抗式审查

bmad-code-review

审查必须比较 Story 声明、AC、任务勾选、实际 Git 变更、文件列表、项目约定和测试证据。Critical/High 问题必须修复后再审。

关闭 Story，再进入下一项

只有代码、测试、Review、Story 记录和 Sprint 状态一致时才关闭。Story 关闭不代表可以发布，Epic 级回归仍未完成。

Quick Dev 的用法：若某个功能被判定为 A 级，可在单独新对话中运行 bmad-quick-dev。一次只给一个目标。不要把三个独立功能作为一次 Quick Dev 输入；无关发现应进入 deferred work，而不是扩大当前范围。
步骤 7

Epic 完成后做回归与发布门禁

Story 测试证明“局部实现正确”；发布测试要证明“多个增量组合后，V1 仍然可用”。

内置 QA 路径

适合中小项目。Epic 中所有 Story 实现并 Review 后，运行：

bmad-qa-generate-e2e-tests

用于补充 API 和 E2E 覆盖，并实际执行测试。

TEA 路径

涉及权限、合规、复杂数据或正式发布门禁时，使用 TEA 的 Test Design、ATDD、Traceability、NFR Assessment 和 Release Gate。

TEA 是可选模块；未安装时用现有团队测试体系补齐相同门禁。

四层发布证据

代码层Lint、类型检查、构建、单元测试、静态与依赖安全检查。全绿
服务层API/契约/集成测试，数据库迁移与兼容性，失败重试与幂等。全绿
用户层每个 Story AC、跨 Story 组合路径、关键 V1 回归和权限差异。全绿
运营层监控、日志、告警、灰度、数据校验、回滚或前向修复演练。有证据
发布禁区：“Agent 说测试通过”不是证据。保留测试输出、制品版本、迁移结果、关键路径截图/日志、监控验证和签字结论。权限、计费、数据不可逆迁移不得仅依赖 AI Review。

上线后

  1. 运行 Smoke Test 和关键业务校验。
  2. 观察错误率、延迟、任务积压、关键业务指标和异常日志。
  3. 确认数据迁移数量和约束。
  4. 关闭发布观察窗口后，将 V1.1 标为新生产基线。
  5. 运行 bmad-retrospective，记录经验与遗留项。
异常路径

中途发现变化时，先判断错在第几层

发现正确回退层动作
用户真正想要的不是当前功能SPEC / PRD停止 Story，修正意图和业务规则，再重做受影响下游
操作路径或状态反馈不成立UX更新体验事实，重新核对 Story AC 和 E2E
现有架构无法安全支持Architecture新增 ADR、迁移和回滚方案，再执行 Readiness
需求正确，但实现出现 BugDev Story修代码和测试，不改上游来迁就错误实现
发现无关历史缺陷Deferred Work记录并单独排期，不扩大当前 Story

当变化会影响多个 Story、Sprint 范围或上游事实时，运行：

bmad-correct-course

输出应说明：触发原因、受影响产物、已完成工作如何处理、哪些 Story 作废/重写/新增、重新进入哪个 Gate。

完整示例

示例：V1.1 增加三个小功能

假设 V1 是一个已上线的运营管理应用。本次希望增加筛选记忆、CSV 导出和导出权限控制。

功能影响级别推荐处理
F1：列表记住上次筛选现有页面 + 用户偏好持久化BUX 局部更新；确认存储位置；独立 Story；单元 + E2E
F2：当前结果导出 CSV页面、API、异步任务、性能BPRD 增量 + UX 状态 + Architecture ADR；独立 Story
F3：只有特定角色可导出权限、审计、安全CPRD/UX/Architecture 全部核对；权限负向测试；审计证据

建议 Epic 与顺序

Epic V1.1：运营列表效率与受控导出

Story 1：用户重新进入列表时恢复其上次有效筛选
Story 2：有权限的用户导出当前筛选结果
Story 3：系统按角色限制导出并记录审计事件

推荐顺序：Story 1 → Story 3 → Story 2
理由：先稳定筛选合同，再建立权限边界，最后开放使用该边界的导出能力。

示例验收标准

Story 2：正向 AC

  1. 导出内容与当前有效筛选、排序和用户可见字段一致。
  2. 大数据量走既定异步机制，并给出可理解状态。
  3. 文件生成成功、失败和过期均有明确反馈。
  4. 导出不会暴露用户无权查看的数据。

Story 2：负向与回归

  1. 无权限用户无法从 UI 或直接 API 绕过。
  2. 筛选条件失效时安全拒绝或回退，不导出错误全集。
  3. 导出失败不影响列表查询和 V1 既有操作。
  4. 重复请求、超时和任务重试不会生成错误审计或重复扣费。
可见结果：即使三个功能规模都不大，仍由一个 V1.1 SPEC 管理组合边界，三个 Story 分别关闭。这样某个功能延期时，不会让另外两个功能的完成状态变得含糊。
操作台

可直接复制的工作流提示词

以下内容应输入 AI IDE 对话，而不是在 PowerShell 或终端中执行。每个工作流建议开启新对话。

0. 先让 BMad Help 识别项目状态
bmad-help

这是一个已经通过完整 BMAD 流程开发并上线的 V1 项目。现在计划以 V1.1 增加 2–3 个小功能。请检查现有 BMAD 产物、project-context.md、生产代码和 Sprint 状态，判断本机安装版本中可用的增量工作流，不要重跑无关的 V1 阶段。
1. 创建 V1.1 SPEC
bmad-spec

请为已上线 V1 创建 V1.1 增量 SPEC。只表达相对 V1 的变更；以生产代码和已确认最终文档为输入；发现冲突先报告；覆盖 Non-goals、兼容、回归、迁移、监控、回滚和每个功能的成功信号。
2. 生成增量 Epic 与 Stories
bmad-create-epics-and-stories

仅针对 V1.1 SPEC 生成一个增量 Epic 和可独立验收的 Stories。读取 V1 架构、受影响的 PRD/UX 增量、project-context.md 和生产代码。不得重复生成已上线 V1 的历史 Story。
3. Readiness Gate
bmad-check-implementation-readiness

只审计 V1.1 变更集与 V1 生产基线的一致性。检查范围、UX、架构、数据/API/权限、Story AC、依赖、测试、回归、迁移、监控和回滚。输出 PASS / CONCERNS / FAIL；任何冲突不得自行修正。
4. 开发单个 Story
bmad-create-story

目标 Story：[填写编号与名称]。读取 V1.1 SPEC、相关正式上游、project-context.md、前序 Story 和现有代码。生成 ready-for-dev Story，补全可测试 AC、任务、架构约束、文件范围、测试和回归要求。
bmad-dev-story

实现 Story：[填写 Story 文件路径]。严格按 AC 和任务执行；不处理无关缺陷；同步实现测试；运行验证；更新完成说明、调试记录和文件清单；无法确定的产品或架构决策必须停止并报告。
5. 审查单个 Story
bmad-code-review

审查 Story：[填写 Story 文件路径]。对照实际 Git 变更逐项验证 AC、任务勾选、文件清单、project-context、架构约束、测试和 V1 回归。Critical/High 未清零不得批准；无关历史问题进入 deferred work。
6. Epic 发布前验证
bmad-qa-generate-e2e-tests

针对 V1.1 增量 Epic 生成并运行 API/E2E 测试，同时覆盖受影响的 V1 关键路径。输出测试范围、运行结果、失败修复和仍未覆盖的风险，不得把“测试已生成”当作“测试已通过”。

FAQ

常见误区与处理

2–3 个小功能必须重新跑 PRD、UX、Architecture 吗？

不需要。先做影响分析，只更新被改变的事实源。局部 UI 调整可能只需要 Quick Dev；业务规则、数据、权限或架构变化才逐级提高流程强度。

必须生成正式 SPEC.md 吗？

官方对小更新允许直接 Quick Dev。本教程为“一个版本同时交付 2–3 个功能”增加迭代级 SPEC，是为了锁定组合边界和发布范围。若三个功能完全独立，也可以各自用 Quick Dev 生成 spec-*.md，但仍要有一个发布清单和回归门禁。

为什么不建议一次 Quick Dev 做完三个功能？

Quick Dev 强调一个连贯目标。多个独立目标会模糊完成状态、扩大审查面，并让无关问题混入当前交付。每个功能单独运行，更容易回滚、Review 和延期。

旧 BMAD 规划产物应该删除吗？

不要在本次任务中直接删除。既有项目指南允许归档或依赖版本历史，但这是清理操作，应先只读审计、确认恢复方式后单独执行。当前教程推荐保留 V1 定稿并新建 V1.1 增量目录。

代码现状和 V1 文档不一致怎么办？

先记录漂移。生产现状描述“现在是什么”，正式文档描述“已确认的意图”。判断漂移是未回写的合法变化还是产品缺陷，再更新正确的事实源。不要让新 Story 隐式选择一方。

何时必须使用 Correct Course？

当变化影响多个 Story、Sprint 范围、上游产品事实、关键 UX 或架构决定时使用。单纯编码 Bug 留在 Dev Story 内修复。

BMAD 能保证上线质量吗？

不能。BMAD 提供上下文、门禁和审查流程，真正的质量仍依赖可执行测试、独立 Review、CI、人工验收、监控、迁移与回滚证据。把推荐步骤设成强制 Gate，才形成工程质量体系。

最终记忆句：已上线产品做增量，不是“重新规划整个产品”，也不是“直接让 Agent 改代码”。正确做法是：冻结当前事实，锁定增量意图，只更新受影响的事实源，然后按独立 Story 开发、审查、回归和发布。
