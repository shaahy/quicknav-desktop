# Architecture Addendum：本地文件导航工具

本文件保存已明确移交给 Architecture 的实现议题，不构成 PRD 产品决策。

## 已推迟的技术选择

- 桌面框架：Electron、Tauri 或其他方案均未决定。
- 应用数据存储格式：JSON、数据库或其他机制均未决定。
- Windows 与 macOS 的构建、签名、安装包和升级机制未决定。
- 同一源文件的跨平台路径规范化与唯一性判定算法未决定。
- 数据升级迁移、原子写入、损坏恢复和备份策略未决定。
- 源文件唯一性的等价判定机制未决定，包括路径规范化、平台大小写规则、符号链接或别名、网络位置表达等。责任方为 Architecture；必须在进入 Epic/Story 与 QA 用例拆解前确定，并保证“同一源文件只对应一张卡片”的产品语义可测试。

## Architecture 必须满足的产品约束

- Windows 与 macOS 均可安装和运行，能力与业务规则一致。
- 用户数据在正常关闭、系统重启和应用正常升级后保留。
- 不扫描磁盘或目录；点击卡片时直接请求操作系统处理文件，不实现主动文件状态检查。
- 支持操作系统可访问的内置、外接、网络和云盘同步位置。
- 支持任意文件类型，包括可执行文件与脚本；不得绕过系统安全提示。
- 卡片操作不得修改、移动或删除用户原始文件。
- 两台设备数据完全独立，V1 不实现导入导出、迁移或同步。

## 已讨论但未选定的方向

- 脑暴阶段讨论过 Tauri 与 Electron；用户已明确两者均不在 PRD 阶段冻结。
- 脑暴阶段讨论过跨设备路径映射；V1 已决定两台设备完全独立，因此不形成产品需求。

## 技术取舍背景

- 用户在脑暴阶段关心的首要结果，是 Windows 与 macOS 均能获得可直接安装、运行的桌面应用，而不是偏好某个具体框架。
- Tauri 方向曾因开发工具链复杂度受到质疑；即使最终产物可以按普通桌面应用安装，也不能因此在 PRD 中视为默认选择。
- Electron 加常规 Web 技术曾作为开发熟悉度更高的备选方向被讨论，同时伴随安装体积和资源占用等待评估取舍。
- 上述内容只保存选项背景。Architecture 应基于跨平台交付、开发维护成本、安装体验、资源占用和文件系统能力进行正式比较，不继承预设结论。
