# PRD：本地文件导航工具

## 0. 文档目的

本文档定义“本地文件导航工具”V1 的产品目标、术语、功能规则、异常处理、范围与验收标准，供后续 UX、Architecture、Epic/Story 拆解和研发验收使用。本文档以脑暴 memlog 和本轮逐项确认结果为事实来源；Electron、Tauri、存储格式、打包方式等实现选择不在 PRD 中冻结，统一记录在 `addendum.md`。

## 1. 产品愿景

本地文件导航工具是一款个人使用的跨平台桌面工具。它把分散在本机内置磁盘、外接磁盘、网络位置和云盘同步目录中的常用文件，转化为可命名、可备注、可分类、可排序和可搜索的卡片，降低记忆路径、翻找目录和重复定位文件的时间成本。

产品坚持“用户主动收录、应用只做导航”的边界：只处理用户通过系统文件选择器明确选中的文件，不扫描磁盘或目录；点击卡片后由操作系统处理文件，应用不预览、编辑或改动原始文件。

V1 面向同一位用户在一台 Windows 设备和一台 macOS 设备上的独立使用。两端能力与业务规则一致，但各自维护本地数据，不迁移、不同步。

## 2. 目标用户与任务

### 2.1 目标用户

- 单一用户：需要频繁打开分散本地文件、希望用低操作成本建立个人快捷入口的人。
- V1 不服务团队协作、共享资料库、管理员集中配置或多用户权限场景。

### 2.2 Jobs To Be Done

- 当我需要某个已收录文件时，我希望不用回忆它的磁盘和目录位置，在 5 秒、2 次核心操作内打开它。
- 当文件数量增加时，我希望用自建类别、多类别归属、手动顺序和名称搜索保持可找性。
- 当文件打开失败时，我希望看到明确反馈，并能重新关联文件而不丢失分类和排序。
- 当我需要补充识别信息时，我希望在卡片上记录简短纯文字备注，并在首页直接看到摘要。

### 2.3 关键用户旅程

- **UJ-1：首次建立导航库。** 怡哥首次打开空应用，主动选择一个本地文件，在确认步骤中创建第一个类别、确认卡片名称并保存；首页立即出现该卡片。
- **UJ-2：日常快速打开。** 怡哥打开应用后从“全部卡片”出发，通过当前视图、切换类别或全局搜索定位目标卡片，点击后由操作系统默认方式处理文件。
- **UJ-3：整理同一张卡片。** 怡哥将一张卡片加入多个类别，并在各类别中分别调整顺序；从一个类别移出时，其他类别中的同一张卡片不受影响。
- **UJ-4：修复失败入口。** 怡哥点击卡片后，操作系统未能打开源文件；应用明确提示失败，怡哥通过文件选择器重新关联文件，原卡片名称、备注、类别关系和各视图顺序保持不变。

## 3. 术语表

- **源文件**：用户主动选择、由操作系统可访问的本地文件；可位于内置磁盘、外接磁盘、网络位置或云盘同步目录。
- **卡片**：应用内指向一个源文件的唯一导航对象，包含展示名称、可选备注、文件关联和类别关系。
- **用户自建类别**：用户创建、命名、排序和删除的一级分类对象。
- **全部卡片**：不可重命名或删除的系统视图，汇总全部卡片，每张卡片只出现一次。
- **未分类**：删除类别后用于接收失去全部用户自建类别的卡片的系统恢复类别；用户不能主动选择、重命名或删除。
- **当前类别**：首页卡片主展示区当前展示的类别或系统视图。
- **主打开动作**：用户点击卡片后，应用请求操作系统按默认方式处理源文件。
- **视图顺序**：卡片在“全部卡片”、某个用户自建类别或“未分类”中的独立手动顺序。
- **备注**：卡片上最多 500 个字符的可选纯文字内容。

## 4. 功能需求

### 4.1 文件收录与卡片管理

#### FR-001：主动选择单个文件

用户可以通过系统文件选择器一次选择一个任意类型的源文件。

**验收结果：**
- 文件可来自操作系统可访问的任意位置。
- 不支持多文件选择、选择文件夹导入或自动扫描发现。
- 选择器取消后不创建任何记录。

#### FR-002：保存前确认

用户选择源文件后，产品必须显示保存前确认步骤，允许确认或修改卡片展示名称，并选择一个或多个用户自建类别。

**验收结果：**
- HTML 文件优先采用页面标题；无法读取 `<title>`、缺少 `<title>`、标题为空或仅含空白时视为无效，并采用不含扩展名的文件名。
- 有效 HTML 页面标题去除首尾空格后作为默认卡片名称。
- 非 HTML 文件采用不含扩展名的文件名。
- 没有用户自建类别时，可在当前确认步骤创建第一个类别；创建后自动选中。
- 用户明确保存后才创建卡片；取消时不留下卡片或临时记录。

#### FR-003：源文件唯一性

一个源文件只能对应一张卡片。

**验收结果：**
- 重复选择已收录源文件时，不创建第二张卡片。
- 产品提示“该文件已收录”，并提供查看或编辑原卡片的入口。
- 文件身份的跨平台规范化方式留给 Architecture，但不得改变产品唯一性语义。

#### FR-004：卡片名称规则

卡片展示名称须为单行纯文字，最多 80 个字符；去除首尾空格后不能为空，且不得与现有卡片名称完全相同。

**验收结果：**
- 不允许换行；超过 80 个字符时不得保存，并提供明确长度提示。
- 大小写不同的名称视为不同名称。
- 新增和重命名使用同一规则。
- 名称冲突时不得保存，并提示或定位同名卡片。

#### FR-005：查看与编辑卡片

用户可以查看并编辑卡片名称、备注、类别和关联源文件。

**验收结果：**
- 管理界面只读显示完整文件路径，并支持复制路径和在文件管理器中显示。
- 用户不能直接编辑路径文本；更换源文件必须使用系统文件选择器。
- 主动更换源文件时保留名称、备注、类别关系和各视图顺序。
- 新源文件已被其他卡片收录时，不保存更换，继续关联原文件。

#### FR-006：全局删除卡片

用户可以从应用中全局删除卡片。

**验收结果：**
- 删除前必须确认卡片将从全部类别移除，但原始文件不会被删除、移动、重命名或修改。
- 确认后删除卡片及其全部类别关系和视图顺序。
- 取消后全部应用状态保持不变。

### 4.2 类别、视图与排序

#### FR-007：用户自建类别

用户可以创建、重命名、删除和手动排序用户自建类别。

**验收结果：**
- 类别名称须为单行纯文字，最多 30 个字符；超过限制时不得保存，并提供明确的长度提示。
- 名称去除首尾空格后不能为空。
- “全部卡片”和“未分类”为保留名称，不可使用。
- 去除首尾空格后完全相同的类别名称不得重复；大小写不同可以并存。
- 新建和重命名遵循同一规则。

#### FR-008：多类别归属

一张卡片可以同时属于一个或多个用户自建类别，并在每个所属类别中展示。

**验收结果：**
- 正常新增或编辑时必须至少保留一个用户自建类别。
- “移出当前类别”只解除当前关系，不影响其他类别和卡片本身。
- 卡片只属于当前类别时，不得执行“移出当前类别”。

#### FR-009：删除类别

用户可以删除用户自建类别，删除只影响类别及其关系，不删除卡片或源文件。

**验收结果：**
- 任何类别删除前均需确认，包括空类别。
- 确认信息显示类别中的卡片总数，以及将进入“未分类”的卡片数量。
- 仍属于其他用户类别的卡片继续保留；失去全部用户类别的卡片进入“未分类”。
- 取消后类别、关系和顺序保持不变。

#### FR-010：未分类恢复类别

产品必须提供恢复专用的“未分类”。

**验收结果：**
- 仅在存在卡片时显示，并固定在类别导航底部。
- 用户不能主动加入、重命名或删除“未分类”。
- 卡片加入任一用户自建类别后自动离开“未分类”。
- 卡片进入“未分类”时追加到其末尾。

#### FR-011：首页工作界面

首页由常驻类别导航和当前类别卡片主展示区组成，一次只展示一个当前类别。

**验收结果：**
- 切换类别不进入新的页面层级。
- 类别导航具体位于左侧或顶部由 UX 决定。
- 每次启动均进入“全部卡片”，不恢复上次类别，也不支持自定义启动类别。

#### FR-012：全部卡片与首次空状态

“全部卡片”固定在类别导航顶部，汇总全部卡片且不因多类别归属重复。

**验收结果：**
- 首次启动不预置用户类别，只显示空的“全部卡片”。
- 无卡片时显示主动选择文件的引导。
- “全部卡片”不可重命名或删除。

#### FR-013：类别排序

用户可以手动调整用户自建类别顺序。

**验收结果：**
- “全部卡片”始终固定顶部。
- “未分类”显示时始终固定底部。
- 用户自建类别位于二者之间，并保留用户顺序。

#### FR-014：卡片视图顺序

“全部卡片”、每个用户自建类别和“未分类”分别保存独立的卡片手动顺序。

**验收结果：**
- 同一卡片在不同类别中的位置可以不同。
- 新卡片追加到“全部卡片”及每个所属类别末尾。
- 调整一个视图的卡片顺序不改变其他视图。

### 4.3 搜索与打开

#### FR-015：全局名称搜索

用户可以从全部卡片中按展示名称搜索，搜索范围不受当前类别限制。

**验收结果：**
- 备注、路径和类别名称不参与搜索。
- 同一卡片在结果中只出现一次。
- 输入首尾空格忽略，英文字母不区分大小写。

#### FR-016：匹配与结果排序

搜索采用名称包含匹配。

**验收结果：**
- 完整名称匹配优先，其次名称开头匹配，最后其他包含匹配。
- 同一层级内沿用“全部卡片”的手动顺序。

#### FR-017：主打开动作

用户点击卡片后，产品不预判源文件状态，直接请求操作系统按默认方式处理源文件。

**验收结果：**
- 普通文件由默认应用打开；可执行文件和脚本可按系统规则直接运行。
- 产品不在应用内预览、渲染或编辑文件内容。
- 打开动作不得修改原始文件。

#### FR-018：没有默认打开应用

文件存在但没有默认关联应用时，产品调用操作系统的“选择打开方式”。

**验收结果：**
- 用户可选择应用后继续打开。
- 用户取消时，不改变卡片、类别、顺序或文件状态。

#### FR-019：在文件管理器中显示

每张卡片始终提供“在文件管理器中显示”辅助操作；产品不预判源文件状态，直接请求操作系统定位源文件。

**验收结果：**
- Windows 在资源管理器中定位，macOS 在 Finder 中定位。
- 辅助操作不替代主打开动作，也不修改卡片或源文件。
- 操作系统无法定位源文件时，产品明确提示失败，并提供“重新选择文件”和“删除卡片”。
- 定位失败及用户关闭提示时，卡片名称、备注、类别关系和各视图顺序保持不变。

### 4.4 打开失败与修复

#### FR-020：打开失败反馈

产品既不在启动时检查源文件状态，也不在执行主打开动作前检查；用户点击卡片后，产品直接请求操作系统按默认方式处理源文件。

**验收结果：**
- 操作系统未能处理打开请求时，产品必须提供明确失败反馈，不得静默。
- 失败反馈提供重新选择源文件和删除卡片两个后续动作。
- 产品不显示“检查中”，不预先标记“文件不可用”，也不维护自动恢复状态。

#### FR-021：失败后保留卡片

打开失败后，产品保留原卡片及其应用内数据。

**验收结果：**
- 不自动删除或隐藏卡片。
- 保留展示名称、备注、全部类别关系和各视图顺序。
- 用户关闭失败提示后可以再次点击卡片重试。

#### FR-022：重新关联修复

用户可以在打开失败后的处理入口或卡片编辑界面，通过系统文件选择器重新选择源文件。

**验收结果：**
- 修复保留名称、备注、类别关系和各视图顺序。
- 新文件已被其他卡片收录时阻止修复，提示“已收录”并提供原卡片入口。
- 冲突时原卡片继续关联原路径，用户可改选或删除。

### 4.5 纯文字备注

#### FR-023：卡片备注

每张卡片可以保存一段可选纯文字备注。

**验收结果：**
- 最多 500 个字符，换行计入字符数；纯空白按未填写处理。
- 用户可以新增、编辑或清空备注；这些操作不修改源文件。
- 首页在名称下方展示最多两行摘要，超出部分省略；无备注时不保留占位。
- 管理界面显示完整备注。
- 不支持富文本、Markdown、图片、链接预览或附件；备注不参与搜索。

### 4.6 跨平台与持久化

#### FR-024：Windows 与 macOS 产品一致性

产品必须分别提供可在 Windows 与 macOS 安装和运行的桌面应用，并保持能力和业务规则一致。

**验收结果：**
- 系统文件选择器、系统提示、默认应用和文件管理器遵循各平台原生规范。
- 产品不得绕过或屏蔽操作系统针对文件打开或代码执行显示的安全提示。

#### FR-025：设备数据独立

Windows 与 macOS 分别维护独立的卡片、备注、类别、顺序和文件关联。

**验收结果：**
- V1 不提供两台设备之间的数据迁移、导入、导出或持续同步。

#### FR-026：本地数据持久化

正常关闭、重新打开、操作系统重启和应用正常升级后，全部应用数据必须保留并可用。

**验收结果：**
- 保留卡片、名称、备注、类别、关系、视图顺序和文件关联。
- V1 不保证卸载后保留数据，也不要求重新安装后自动恢复。

## 5. 跨功能质量要求

- **NFR-001｜效率：** 在应用已启动并显示首页、目标卡片已收录、源文件有效且系统已配置默认处理方式的前提下，从用户开始执行查找动作，到源文件成功交给操作系统处理，用时不超过 5 秒、核心操作不超过 2 次。选择或切换类别计 1 次，输入一条完整搜索词计 1 次，点击目标卡片计 1 次；移动鼠标、滚动、等待结果不计。系统“选择打开方式”属于异常流程，不纳入本指标。
- **NFR-002｜打开可靠性：** 主打开动作必须成功交给操作系统，或明确提示无法打开及可执行后续动作；不得静默失败。
- **NFR-003｜源文件安全：** 应用不得因卡片新增、编辑、删除、排序、备注或修复而删除、移动、重命名或修改原始文件。
- **NFR-004｜持久化：** 正常关闭、系统重启和应用正常升级不得导致应用数据丢失。
- **NFR-005｜跨平台一致性：** Windows 与 macOS 的能力、业务规则和验收结果一致，原生系统交互可存在平台差异。
- **NFR-006｜系统安全边界：** 应用允许收录和运行可执行文件或脚本，不增加自身额外警告，但不得绕过操作系统安全提示。
- **NFR-007｜容量声明：** V1 不声明卡片或类别数量上限，也不承诺无限容量；实际可承载规模由 Architecture 与实现验证确定。

## 6. V1 范围与非目标

### 6.1 范围内

- 单文件主动收录、卡片唯一性、名称、纯文字备注和文件关联管理。
- 用户自建类别、多类别归属、“全部卡片”、“未分类”和独立手动顺序。
- 全局名称搜索、系统默认方式打开、选择打开方式、在文件管理器中显示。
- 打开失败反馈、失败后保留卡片和重新关联修复。
- Windows 与 macOS 独立运行及本地数据持久化。

### 6.2 明确排除

- 文件管理器、文件搜索引擎或磁盘索引能力。
- 自动扫描、文件夹导入、多文件批量添加。
- 收藏、最近打开、标签、备注搜索。
- 富文本或 Markdown 备注、图片、链接预览、附件。
- 团队共享、多用户、权限或协作能力。
- 数据导入导出、设备迁移、跨设备同步或共享目录。
- 应用内文件内容预览、渲染或编辑。
- 管理、修改或删除用户原始文件。

## 7. 成功指标

- **SM-001｜快速打开：** 在 NFR-001 前提下，目标文件在 5 秒、2 次核心操作内成功交给操作系统处理。类别路径可为“切换类别 + 点击卡片”，搜索路径可为“输入完整搜索词 + 点击结果”。验证 FR-011、FR-015 至 FR-018。
- **SM-002｜打开结果明确：** 已定义的主打开测试中，每次操作均得到“成功交给系统”或“明确失败及后续动作”，不得出现无反馈。验证 FR-017、FR-018、FR-020。
- **SM-C001｜不以收录量为目标：** V1 不以卡片数量、类别数量或使用频率作为成功指标，避免为扩大数据量引入自动扫描、批量导入或行为追踪。

## 8. 风险与约束

- **可执行文件风险：** 用户已确认可执行文件和脚本与普通文件相同处理，产品不增加额外警告；必须保留操作系统原生安全提示。
- **外部位置可用性：** 外接磁盘、网络位置和云盘同步目录可能暂时不可访问；产品不主动检查，只有实际打开失败时提供明确反馈与重新关联入口。
- **无备份能力：** V1 无导入导出、迁移或同步；卸载后的数据不保证保留。
- **无容量承诺：** 未定义容量上限，Architecture 和实现阶段不得把“无上限指标”解释为“无限容量”。
- **技术选型边界：** 框架、存储格式、文件身份规范化、打包和安装方式均由 Architecture 决定，但必须满足本文产品行为。
